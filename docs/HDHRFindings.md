# HDHomeRun API Findings

Research and live testing notes. Updated as new things are confirmed or disproved.

---

## Two Streaming Paths

### Port 5004 — Direct Device HTTP Stream

The device serves raw MPEG-TS directly. This is what hdhr_VCR uses for all recording and in-app playback.

```
http://<device_ip>:5004/auto/v<channel>
http://<device_ip>:5004/auto/v<channel>?duration=<seconds>&transcode=<profile>
```

- Tuner allocated when TCP connection is accepted; released when connection closes
- No session state between connections — purely connection-lifetime based
- `auto` picks any free tuner; `tunerN` targets a specific one

### Port 4999 — Record Engine (SiliconDust DVR daemon)

The HDHomeRun DVR software runs a separate daemon that buffers live TV and serves time-shifted streams. Not present unless the user has the HDHomeRun app installed and running.

```
http://<record-engine-ip>:4999/auto/v<channel>?ClientID=<UUID>&SessionID=<hex32>
```

ClientID and SessionID belong to this path only (see below).

**Note:** The SiliconDust documentation wiki calls this path "Old-Live-TV" — there may be a newer protocol. The findings here are based on the documented `Old-Live-TV.md` spec.

## ClientID and SessionID

**These are Record Engine parameters, not port 5004 parameters.**

| Field | Format | Generated by | Lifetime |
|---|---|---|---|
| ClientID | UUID string | Client app, once at launch | Per player instance |
| SessionID | Random hex32 (8 hex chars) | Client, fresh per channel request | Per channel session |

**Purpose:** The Record Engine tracks which ClientID holds which tuner. Sending the same ClientID with a new SessionID tells the engine to free the previous tuner and allocate a new one — enabling seamless channel switching without a gap. Without them, the old connection must fully close before the new tuner can start.

**Multi-instance:** if two player windows are open simultaneously (picture-in-picture), each gets its own ClientID so they don't interfere with each other's tuner allocation.

**Channel change pattern:**
- Same `ClientID` across the whole session
- New `SessionID` each time the channel changes
- Seek within a channel: same `ClientID` + same `SessionID` + `Range: bytes=<offset>-` header

**Seek response:** The device returns a `Content-Range` header with the actual byte offset granted — it may differ from what was requested if the seek point is before the oldest buffered data or past the live edge.

### Confirmed on port 5004 (2026-05-31)

Tested passing both params on port 5004:

```
GET /auto/v2.4?ClientID=F2BB2E67-E338-40A9-9D79-40D21340A9D5&SessionID=0796e75c
→ HTTP/1.1 200 OK, video/mpeg, ~370 KB/s
```

The device accepted the request without error. **Unknown whether the device processed or ignored them** — the response is identical to a request without them. Further testing needed to confirm whether they affect tuner allocation behavior on port 5004.

## Response Headers (port 5004)

### X-HDHomeRun-Resource

Returns the specific tuner that was allocated:

```
X-HDHomeRun-Resource: tuner1
```

Confirmed present in live testing. More reliable than polling `/status.json` and matching by channel number, which is fragile when two recordings share a channel. **Implemented:** captured at stream start from the curl dump-header file (`RecordingManager.readHDHRResource`), stored on `Show.show_tuner_resource`, and used for direct `/tunerN/vstatus` targeting in `AppState` (preferred over channel-number matching).

### X-HDHomeRun-Error

Returned when the stream request fails at the device level. **Implemented:** parsed from the curl dump-header file (`RecordingManager.readAndClearHDHRError`) and mapped to a human-readable `show_fail_reason` via `hdhrErrorLabel` (codes 804–811 below). Earlier versions only logged a generic "curl exited unexpectedly".

| Code | Meaning |
|---|---|
| 801 | Unknown Channel |
| 802 | Unknown Transcode Profile |
| 803 | System Busy |
| 804 | Tuner In Use |
| 805 | All Tuners In Use |
| 806 | Tune Failed |
| 807 | No Video Data |
| 808 | DVR Failure |
| 809 | Playback Connection Limit |
| 810 | DVR Full |
| 811 | Content Protection Required |

## Tuner Lockkey (UDP Control Protocol)

A separate mechanism used by apps like MythTV and TVHeadend that bypass port 5004 and configure the device directly via `libhdhomerun` (TCP/UDP port 65001).

- Generate a random `uint32` as the lockkey
- Send `SET /tunerN/lockkey <value>` before any tuner configuration
- All subsequent `SET` commands on that tuner must be signed with the key; other clients get "resource locked"
- Release: `SET /tunerN/lockkey none` (signed); or `SET /tunerN/lockkey force` (any client can steal it)
- Keepalive: send the 4-byte lockkey as a UDP packet to device port 5004 every ~1 second while streaming
- Idle timeout: ~30 seconds if no keepalive and no active stream

**GET vs SET:** `GET` commands on the control protocol are always permitted without a lockkey — only `SET` commands (channel change, PID filter, etc.) require it.

**Stale lock recovery:** If the app crashes without releasing the lock, the ~30s idle timeout should free it. TVHeadend found this unreliable and added startup logic to detect locks held by the local IP and force-release them (`SET /tunerN/lockkey force`).

**libhdhomerun function names** (for reference if ever implementing): `hdhomerun_device_tuner_lockkey_request`, `hdhomerun_device_tuner_lockkey_release`, `hdhomerun_device_tuner_lockkey_force`.

**Not relevant to hdhr_VCR's curl approach.** Only needed if implementing direct device control without going through port 5004.

## Transcode Profiles (port 5004 `?transcode=`)

| Profile | Meaning |
|---|---|
| `none` | Raw stream, no transcode (MPEG-2 or H.264 as broadcast) |
| `heavy` | High-quality H.264 |
| `mobile` | Low-bitrate H.264 for mobile |
| `internet720` | 720p H.264 for internet streaming |

hdhr_VCR passes the user's `Default_transcode` config value directly. VLC handles MPEG-2 natively so `none` works without forced transcode for OTA.

**On-wire container (verified 2026-07-18, device 105404BE ch 4.1):** every profile returns an **MPEG-2 Transport Stream** — 188-byte packets, sync byte `0x47` at each boundary (`file(1)` → "MPEG transport stream data"). Transcoding is a **video-only re-encode inside the same TS container**; the container never changes to MP4/MKV:

| Profile | Video (PMT `stream_type`) | Audio | ~2 s size (ch 4.1) |
|---|---|---|---|
| `none` | MPEG-2 (`0x02`) | AC-3 ×2 (`0x81`) | ~1.84 MB |
| `heavy` | H.264/AVC (`0x1b`) | AC-3 ×1 (`0x81`) | ~0.79 MB |

Because the recorder writes the HTTP body verbatim (`curl -o`, no remux), the correct extension for **both** profiles is a TS one — the app uses `.ts` (`Show.outputPath`), matching the `video/mp2t` MIME the disk relay serves and the `.ts` convention used by Plex/Emby/Jellyfin/MythTV/TVHeadend. `.mkv`/`.mp4` would require an actual remux step the app doesn't do. Regression-locked by `TranscodeStreamFormatTests` (real PAT+PMT fixtures). *(History: before 2026-07 the app wrote `.m2ts` for `none` and `.mkv` for transcoded — both container mislabels; those extensions remain recognized by the recording-file scans for backward compatibility.)*

### Transcode capability: `Transcode` field exists, but only on a CGNAT-unsafe cloud endpoint (corrected 2026-08-27)

**Superseded finding, kept below for context — the "no endpoint exists" conclusion was wrong.**
It was reached by checking only local-device endpoints; a real field exists, but on a *cloud*
endpoint that's unsafe to use (see below) and was never tried in the original investigation.
Corrected here rather than deleted, per this repo's own docs-are-source-of-truth convention (stale
entries get flagged and fixed, not silently dropped).

**`GET https://ipv4-api.hdhomerun.com/discover`** — SiliconDust's cloud discovery API. No auth, no
params — it identifies "your" device purely by the **public IPv4 address the request comes from**.
Live-tested 2026-08-27 against a real EXTEND (HDTC-2US, DeviceID 105404BE):

```json
[{"DeviceID":"105404BE","LocalIP":"10.0.2.101","Transcode":1,"BaseURL":"http://10.0.2.101","DiscoverURL":"http://10.0.2.101/discover.json","LineupURL":"http://10.0.2.101/lineup.json"}]
```

A literal **`"Transcode": 1`** field, straight from SiliconDust's own cloud inventory of the
device — not inferred from `ModelNumber`, not a curated UI list. Found by reading the old
AppleScript app's (`identd113/hdhr_VCR`) git history: its `HDHRDeviceDiscovery` handler called this
exact endpoint and read `Transcode of item i of hdhr_device_discovery` directly (commit `a152b54`,
2024-09-07).

**Do not use this endpoint — it's unsafe under CGNAT, not just occasionally unreliable.**
Public-IP-keyed lookup with no auth means that under carrier-grade NAT (very common — many cable,
DSL, and most cellular ISPs share one public IPv4 across many unrelated households), a call to this
endpoint can return **a different household's device** as if it were yours, silently and with no
way to detect the mismatch client-side. This is exactly why the AppleScript app dropped it: commit
`0dd177d` (2025-12-08) silently replaced this call with local `http://hdhomerun.local/discover.json`
and added the `ModelNumber` `"HDTC"`-prefix heuristic specifically to recover the `Transcode`
signal the cloud endpoint used to provide, without going back through it. No commit message
explains why, but the timing and same-purpose swap-in point squarely at this. The field is real,
but the endpoint that carries it should be treated as **not usable for anything**, not just
transcode capability — a wrong answer sourced from a stranger's device is worse than no answer.

Only one real device available to test either way (an EXTEND, `Transcode: 1`) — the negative case
(a non-transcoding device correctly reporting `Transcode: 0`) is unverified regardless.

**Practical takeaway:** two safe signals available, in order of preference: (1) `ModelNumber`'s
`"HDTC"` prefix from local `/discover.json` — a heuristic, but local/per-device with no shared-IP
risk, live-confirmed to match on this device; (2) reactive `X-HDHomeRun-Error` detection after a
recording attempt (what the app already surfaces via `hdhrErrorLabel`). The cloud `Transcode` field
is deliberately excluded from this list — it exists, but is not safe to call.

<details>
<summary>Original (incorrect) 2026-08-09 finding, kept for context</summary>

SiliconDust's official **HDHomeRun HTTP Development Guide** (`hdhomerun_http_development.pdf`, 20140407 — cited above as one of this file's primary sources) states plainly: `transcode=<profile>` is a **"PLUS models only"** feature — support is a hardware/model-tier fact, not something negotiated per-request. The doc defines only `heavy`, `mobile`, `internet720`, `internet480`, `internet360`, `internet240` as profiles (`none` isn't a formal profile — it's just omitting the parameter). Its only documented error responses for the streaming endpoint are bare HTTP status codes — `404 Not Found` (unknown channel), `503 Service Unavailable` (busy / tune timeout / unauthorized content-protected channel) — **no mention of the `X-HDHomeRun-Error` header or numeric codes like 802** ("Unknown Transcode Profile," see the table above); that mechanism is newer/undocumented in this primary source.

**There is no endpoint that reports which transcode profiles a device supports.** Investigated live (2026-08-09) against a real EXTEND (HDTC-2US, DeviceID 105404BE, firmware 20260313):
- `/transcode.html` is a real, human-facing config page (linked from the device's own root menu, not previously documented here) — but its `<select name="transcode">` dropdown is a **curated UI list, not a capability manifest**. This device's dropdown offered `none, heavy, mobile, internet540, internet480, internet360, internet240` — **no `internet720`**, and `internet540` isn't in the 2014 official doc at all (a firmware-added tier). Despite that, requesting `?transcode=internet720` directly against the streaming endpoint **worked fine** (1.08 MB streamed in 4s, same as `mobile`) — so the page's option list cannot be trusted to enumerate what actually works, only what the stock config UI happens to expose.
- `/discover.json`, `/lineup.json`, and `/lineup_status.json` carry no transcode-capability field of any kind.
- `?transcode=<any of the 4 app-offered profiles>` all returned `200 OK` immediately even before checking whether they'd actually work — a device rejecting an unsupported profile doesn't fail at the HTTP-status level, consistent with the 802-via-header behavior documented above, not the *statically-known* "PLUS models only" gate this doc describes.

Practical takeaway at the time: the only two signals available were thought to be (1) a hardcoded PLUS-tier model list (not built) or (2) reactive `X-HDHomeRun-Error` detection. Both still valid as fallbacks — just not the only options, per above.

</details>

## Duration Parameter

`?duration=<seconds>` causes the device to close the stream after N seconds. hdhr_VCR calculates this as `show_end - now` at recording start so the device self-terminates if curl dies unexpectedly. Without it, the stream runs until the TCP connection is closed.

## Guide API

### Device tested

HDHomeRun EXTEND, Model HDTC-2US, Firmware 20260313, DeviceID 105404BE, at 10.0.2.101. Tested 2026-06-03.

### Local `/guide.json` — Not present on EXTEND

The local HTTP server on this device returns **404 Not Found** for `/guide.json`. The device does not serve guide data locally. Guide data requires the cloud API authenticated via DeviceAuth.

### Cloud API — `https://api.hdhomerun.com/api/guide.php`

Supports an optional `Start` epoch parameter that controls the beginning of the guide window:

- **Without `Start`**: response contains shows starting from approximately now.
- **With `Start=<epoch>`**: response starts from that epoch. Shows that were airing at that moment are included — the window begins at the given timestamp, not at the show's StartTime.

Confirmed: `Start=now-3600` returned shows with StartTime going back ~2 hours (i.e., shows that were airing at the start time), while a no-Start call returned only shows from current time onward.

`Duration` remains in hours and controls the window length forward from `Start`.

**URL formats:**

```
# No Start (window begins now)
https://api.hdhomerun.com/api/guide.php?DeviceAuth=<auth>&Duration=<hours>

# With Start (window begins at epoch)
https://api.hdhomerun.com/api/guide.php?DeviceAuth=<auth>&Start=<epoch>&Duration=<hours>
```

### Backward Start limit (~48–55h) — confirmed 2026-06-18

`Start` values older than ~55 hours return **400 Bad Request**. Tested: `now-48h` succeeds, `now-60h` fails. The official wiki claims "2 weeks backward" — this is wrong; the real limit is under 2.5 days. The JSON guide's lookback is therefore bounded, not open-ended.

### Per-call window cap (~29h) — confirmed 2026-06-11

The cloud API **ignores large `Duration` values** beyond a per-call cap of roughly ~28–30h from `Start`. Tested on device 105404BE:

| Requested `Duration` | Latest data returned |
|---|---|
| `25` (GuideHours 24) | ~29h ahead |
| `37` (GuideHours 36) | ~29h ahead — byte-identical response |

So raising `GuideHours` past ~28 in Settings changes the URL but yields the **same** data; a single call cannot return more.

**The data beyond ~29h does exist** — it's paginated. Moving `Start` forward to +28h returned programming out to ~53h ahead. To genuinely support a longer window, `GuideStore.load()` would need a pagination loop: fetch, take the max `EndTime`, refetch from there, and merge per-channel `Guide` arrays by `GuideNumber` until `GuideHours` is covered. **Not currently implemented** — `load()` makes a single call, so it is structurally capped at ~29h regardless of the `GuideHours` setting.

### Cloud API — `https://api.hdhomerun.com/api/episodes` — confirmed 2026-06-11

```
https://api.hdhomerun.com/api/episodes?DeviceAuth=<auth>&SeriesID=<id>
```

**Undocumented** (not in the official HTTP API docs — used by SiliconDust's own DVR apps; referenced in community docs). Returns the **full upcoming airing schedule for one series** across all channels carrying it. Verified twice on 2026-06-11 with fresh DeviceAuth and different SeriesIDs: 67 and 30/31 airings, reaching **~17 days ahead** — far beyond guide.php's ~29h cap. `SeriesID` is already present on every `GuideEntry`; `DeviceAuth` rotates, so fetch it fresh from `discover.json`.

**Differences vs `guide.php` entries** (same airing compared field-by-field):

| | `guide.php` | `/api/episodes` |
|---|---|---|
| Shape | Array of channels, each wrapping `Guide[]` | **Flat array** of airings |
| Channel info | Channel level: `GuideNumber`, `GuideName`, `Affiliate`, `ImageURL` | Inlined per entry: `ChannelNumber`, `ChannelName`, `ChannelImageURL` (sometimes absent) |
| `Filter` (genre tags) | ✅ present — drives **Bonus Time** sports detection and genre coloring | ❌ **absent** |
| `ProgramID` | ❌ absent | ✅ present — per-episode identity; cleanly distinguishes new episodes from repeats (same `ProgramID` appears once per repeat airing) |
| Time window | ~29h, **includes** currently-airing | ~17 days, but **today's already-started airing can be missing** (one test showed earliest entry = tomorrow despite the series airing at fetch time; another included a −0.5h entry — near-edge behavior is unreliable) |
| Optional fields | per existing `GuideEntry` optionals | `EpisodeNumber`/`EpisodeTitle`/`Synopsis` absent on generic placeholder listings (3/30 in test) — decode nil-safe |

**`Start` param — tested 2026-08-10:** silently ignored, same as `xmltv`. `episodes?...&Start=<any epoch>` returns a byte-identical response to the call without it — no pagination/backdating control on this endpoint.

**Usage guidance if ever adopted for series scheduling:** far-window only. Keep the guide scan authoritative for the next ~24h (reliable near edge + has `Filter` for Bonus Time); use episodes to pre-schedule beyond the guide horizon, then re-resolve against the real guide entry once the airing enters the ~29h window to pick up genre/Bonus Time. `ProgramID` would let Series shows skip repeat airings, which `SeriesID`+title matching cannot do. Being undocumented, guard with a fallback to the current guide-scan behavior if the endpoint 400s or changes shape.

### SeriesID format

Every `GuideEntry` carries a `SeriesID` string that uniquely identifies the series. Format:

```
C<numeric-id>EN<4-char-suffix>
```

| Segment | Example | Meaning |
|---|---|---|
| `C` | `C` | Content prefix — all series entries use this |
| numeric ID | `30042336` | Gracenote / Tribune Media Services series identifier. Prepend `SH0` for the Gracenote tmsId format: `30042336` → `SH030042336` |
| `EN` | `EN` | Language code (English) |
| 4-char suffix | `VAEE` | Variant/version code in SiliconDust's system (not a hash of anything external; appears to be a base-36-style sequence) |

The numeric ID length varies (6–8 digits in practice). The full `SeriesID` string doubles as the **image filename** on SiliconDust's CDN — `https://img.hdhomerun.com/titles/<SeriesID>.jpg` — so the same value is the series key, the poster key, and the episodes-endpoint parameter with no transformation needed.

**Cross-referencing external databases:** the numeric portion maps to a Gracenote series ID, but translating to TVDB/TMDB IDs requires Gracenote API access. Within hdhr_VCR and the HDHomeRun API ecosystem the ID is self-contained — guide, episodes endpoint, and image CDN all use it natively.

### Infomercial / paid programming detection

**`Filter: []` is not usable** — infomercials carry an empty Filter array in `guide.php` JSON, identical to many legitimate no-genre entries (PBS documentaries, etc.). The XMLTV API uses a different field; the JSON API does not.

**Detection strategy (three layers, JSON source uses 1-2 / XMLTV source also gets 3):**

1. **SeriesID blocklist** — `C459763EN3L6D` covers all generic "Paid Programming" slots (title + SeriesID are both `"Paid Programming"`). `C11809220ENAPZK` covers a second recurring generic slot. Both are hardcoded in `WebServer.swift` (`infSIDs`) and `AppState.swift` (`knownInfSIDs`).

2. **Title == "Paid Programming" fallback** — catches any generic paid-programming slot that appears with a new or unknown SeriesID. Added alongside the blocklist check in both detection sites.

3. **`<category>Shop`/`Shopping` (XMLTV only)** — implemented 2026-08-10 in `WebServer.swift`'s guide-grid `infDA` check (case-insensitive `Filter` scan). Unlike JSON's ambiguous empty `Filter:[]`, this is an explicit, reliable signal SiliconDust's own XMLTV categorization already provides — catches *new* infomercials automatically instead of waiting for a `[NowAiring]` sighting to get manually added to the blocklist. Only fires for XML-sourced entries (`guide.php` never populates this category); layers 1-2 remain the only detection for JSON-sourced entries.

**Product-specific infomercials** (named shows that are actually paid content — e.g. "Under Eye Bags? SOLUTION!") have unique SeriesIDs and unique titles. They are invisible to both layers above and can only be caught by expanding the blocklist. The `[NowAiring]` log (idle loop, no-genre entries) is the right feed: check it after an overnight run to find new SeriesIDs. Known-infomercial entries are suppressed from that log to reduce noise.

### XMLTV Cloud Endpoint — `https://api.hdhomerun.com/api/xmltv` — verified 2026-06-18

```
GET https://api.hdhomerun.com/api/xmltv?DeviceAuth=<auth>
```

**Format:** SiliconDust's response is the official [XMLTV format](https://wiki.xmltv.org/index.php/XMLTVFormat) (the same `<tv>`/`<channel>`/`<programme>` DTD used by XMLTV grabbers generally), not a bespoke schema — every element `XmltvParser.swift` reads (`<lcn>`, `<display-name>`, `<icon src>`, `<title>`/`<sub-title>`/`<desc>`, `<category>`, `<date>`, `<episode-num system=…>`, `<previously-shown/>`) is a standard DTD element. One vendor extension: `<series-id system="cseries">` is SiliconDust's own `system=` value, not part of the baseline spec's example systems (`onscreen`, `xmltv_ns`, `dd_progid`) — safe to keep relying on it, just don't expect other XMLTV sources to emit it.

- **All query parameters are silently ignored** — exhaustively tested 2026-06-18: `Start`, `start`, `Duration`, `Days`, `days`, `Hours`, `Offset`, `Channel`, `SynopsisLength`, `V=2`, `Count`, `Category` all return byte-identical 3.9 MB responses. Server controls the window entirely; no backdating is possible via this endpoint.
- **Forward window measured live, 2026-08-10 (free tier, no DVR subscription): a hard, uniform ~48 hours.** Per-channel latest `EndTime` across 91 channels: min 48.10h, 25th/median/75th percentile *all exactly* 48.26h ahead of fetch time — a real server-side cutoff, not a soft/varying one. (A handful of channels showed up to 53.26h — one long-running program's `EndTime` spilling a few hours past the common wall, not deeper real coverage.) Confirms the "~2 days free" marketing claim is accurate and is the actual floor for this account, not just an approximation.
- **"Lookback" isn't a window at all — it's just the currently-airing program's own StartTime.** Corrected 2026-08-10 (earlier wording implied a deliberate per-channel lookback setting; it isn't one). Same mechanism `guide.php` documents ("shows that were airing at that moment are included"): whatever program is airing *right now* on a channel is always present in the feed, so the earliest `<programme start>` on that channel is simply `now - (however long that program has been running)`. A channel mid-way through a 4-hour block shows a start ~2-4h back; a channel on a 30-min show shows a start within the last ~30min. Verified 2026-08-10: the 8 earliest entries across the whole feed (spanning 1.8h–2.8h back) were all live, in-progress long-form programs (4h local-origination/infomercial blocks, a movie, MMA event coverage) — none were short shows artificially extended. Confirmed all were `[AIRING NOW]` (start ≤ now ≤ stop), not stale/leftover entries. Do not assume the XMLTV window covers the guide's 1-hour `winStart` for all channels — a channel between programs (nothing long currently airing) may have no coverage before "now" at all.
- **Alternative auth** (`Email=` + `DeviceIDs=`) not tested for time-window differences; unlikely to change server behavior.
- gzip encoding handled automatically by URLSession
- Response: standard XMLTV XML; free tier tested at 106 channels, 4,929 programmes, 3.7–3.9 MB

**Field mapping to `GuideChannel` / `GuideEntry`:**

| Our field | XMLTV source | Notes |
|---|---|---|
| `GuideNumber` | `<lcn>` text | Reliable; e.g. "11.1" |
| `GuideName` | Display-name starting with `lcn + " "`, suffix stripped | e.g. "11.1 KARE-HD" → "KARE-HD"; falls back to first display-name |
| `GuideChannel.Affiliate` | Last `<display-name>` | Network name e.g. "NBC" — present in XMLTV but absent in JSON |

| `EndTime` | `<programme stop>` attr | Same format |
| `Title` | `<title>` text | |
| `EpisodeTitle` | `<sub-title>` text | |
| `Synopsis` | `<desc>` text | |

| | JSON `guide.php` | XMLTV `api/xmltv` |

| `SeriesID` | ✅ full `C{n}EN{s}` format | ✅ `<series-id system="cseries">` — identical format, 100% coverage |
| `EpisodeNumber` | ✅ onscreen `"S01E13"` style | ✅ `<episode-num system="onscreen">` — same style/format, parity confirmed via real scheduled-show test 2026-08-10 |
| `Affiliate` | ✅ present | ✅ last `<display-name>` — present in XML, **absent from JSON entirely** |
| `episodes`/`up_next` `Start` param | ✅ `guide.php`'s own `Start` works; `up_next`'s `Start` also works going forward | ❌ `episodes`'s `Start` also silently ignored — same pattern as `xmltv` |

**Implementation:** `XmltvParser.swift` (Foundation `XMLParser`, no extra dependencies); routed from `GuideStore.loadXMLTV(for:)` when `Guide_use_xml = true`. Devices without `DeviceAuth` always fall back to JSON even when the flag is on.

### Consistency check vs `guide.php` — what breaks/is lost if `Guide_use_xml` becomes the default — 2026-08-10

Requested audit: does the XMLTV path actually behave equivalently to the JSON `guide.php` path it's meant to substitute for? Compared both feeds live, same moment, matched entries by (channel, StartTime). Two real regressions found — both silent, not crashes:

**1. Genre vocabulary mismatch broke Bonus Time auto-detection and genre coloring — fixed 2026-08-10.** `guide.php`'s `Filter` uses a single blunt tag, `"Sports"` (plural). XMLTV's `<category>` list is richer and uses `"Sport"` (singular) as the first/broad tag, e.g. `Filter=['Sport','Mixed martial arts']` vs JSON's `Filter=['Sports']` for the *same airing* (verified: Bellator MMA, World Poker Tour, Prairie Sportsman — all `"Sport"` in XML, `"Sports"` in JSON). `GuideEntry.firstGenre` picks the first non-"series" tag, so an XML-sourced sports entry's `firstGenre` was `"Sport"`, not `"Sports"`. Fixed at all four points:
   - `AddShowView.swift:353` and `Models.swift`'s legacy-config decode fallback — `.contains("sports")` → `.contains("sport")` (a substring of both spellings).
   - `Resources/guide.js:240` (`_isSports`, drives the Add/Edit modal's Bonus Time checkbox) — same substring narrowing.
   - `Resources/guide.js`'s `gc()` now runs the genre through the already-existing `_ggAlias` map before the color lookup, instead of looking it up raw (that alias map already had `'sport':'sports'`, `'documentary':'doc'`, etc. — it just wasn't being consulted here).
   - `Views/GuideViewHelpers.swift`'s `_genreColorMap`/`guideEntryColor` — added a matching `_genreAlias` map (mirrors `WebServer.swift`'s server-side `ggAlias`) plus the 16 category buckets (`crime`, `romance`, `thriller`, `action`, `mystery`, `doc`, `science`, `nature`, `history`, `music`, `food`, `travel`, `gameshow`, `home`, `health`, `faith`) that the web guide grid already recognized via `guide.css`'s `--gg-*` custom properties but the native app and `guide.js`'s `gc()` didn't — both previously only had ~8-9 categories and fell back to gray for anything else. `guide.js`'s `_gcDk`/`_gcLk` extended with the same 16, using `guide.css`'s literal HSL values so all three color surfaces (native SwiftUI, web JS popups/modals, web CSS grid) agree.
   - Sample size that surfaced this: 575 entries matched by (channel, StartTime) across both feeds in one live comparison; 528 had a `Filter`/`category` set mismatch (most because JSON had no `Filter` at all where XML had rich categories — XML's coverage is *better*, just differently spelled).

**2. XMLTV has no backfill for already-ended programs — degrades the web guide's past-hour display.** `guide.php` with `Start=now-3600` (see `guideURL(for:hours:)`) returns every entry with `EndTime > Start`, including short shows that already aired and ended within that hour — a complete timeline. XMLTV, per its own spec, only ever contains the *currently airing* entry per channel plus future — never something that already ended, no matter how recently. Live comparison, same moment: of 103 channels with a `guide.php` entry overlapping the past hour, **110 individual past-hour entries (already-ended shows) were completely absent from the XMLTV feed** — e.g. a channel's currently-airing show (started 25min ago) is present, but the show before it (ended 25min ago) is not, even though it's well within the ~1h window `WebServer.swift`'s `guideWindow(state:)` (`winStart = now - 3600`) wants to render. Practical effect: the just-past portion of the web guide grid would render `.g-gap` blocks instead of real programs for most channels, most of the time — not a crash, just a visibly emptier grid for the last ~30-60 minutes. Forward-looking data (now onward) is unaffected — XMLTV always includes whatever's airing *at fetch time* per channel, so `currentEpisode`/scheduling logic (which only cares about now-or-later) is fine.

**Unaffected / already fine:**
- Infomercial detection — the two feed-agnostic layers (SeriesID blocklist + Title=="Paid Programming" fallback) rely on `SeriesID`/`Title`, which are identical/100%-covered in both feeds; XML additionally gets a third layer (`<category>Shop`/`Shopping`) — see "Infomercial / paid programming detection" above.
- `EpisodeNumber`/skip-already-recorded (`SxxExx` tag matching) — both feeds provide onscreen-style `"S01E13"` text in the same field.
- Series/next-episode scheduling (`GuideStore.nextEpisode`/`currentEpisode`) — no dependency on past-hour data, only now-or-future.
- `GuideHours` setting and local-device (no-`DeviceAuth`) fallback — both already correctly handled by existing fallback logic in `GuideStore.load(for:hours:useXML:)`; not a new risk, just a known limitation already in the table above.

**Bottom line:** `Guide_use_xml` is fine as an opt-in for its intended purpose (extending the *forward* window past `guide.php`'s ~29h cap on paid-tier accounts). Genre vocabulary (#1) is fixed as of 2026-08-10, so that's no longer a blocker to wider use. The past-hour web-guide gap (#2) is still open and would need an explicit product decision before `Guide_use_xml` could safely become a default (accept the gap, or keep `guide.php` for the display window even when XML is used for scheduling) — nothing changed there.

**End-to-end verification with `Guide_use_xml = true` live — 2026-08-10.** Flipped the flag on the real running app (`loadXMLTV()` confirmed in the log: 94 channels, 4,924 entries) and drove the actual production code paths, not just curl:
- Full `swift test` (157 tests/27 suites) + `RUN_WINDOW_NAV_TESTS=1 swift test --filter WindowNavigationTests` (5 real Accessibility-driven native-window tests) — all passed against the XML-backed live app.
- Web guide manual sweep: genre filter dropdown correctly showed all 59 real XML categories (vs. `guide.php`'s ~9); `filterGenre()` dim counts matched exactly; entries with an empty genre string didn't crash; `/api/airings/{seriesId}` and `/vertical` both returned correct real data; zero console errors.
- **Scheduled one show of each type** (Single, DateTime, SeriesID(Channel), SeriesID(All), plus a dedicated Sports-genre Single) through the real `doRecord()`/`confirmRecord()` → `/api/record` path against live XML entries, then read the persisted records straight from the config file. Every type produced the correct `show_is_series`/`show_use_seriesid`/`show_use_seriesid_all`/`show_air_date` combination, `show_genre` carried the raw XML vocabulary through uncorrupted (`News`, `Children`, `Action`, `Sport`), and the Sports entry persisted `show_bonus_time: true` — confirming the genre-vocabulary fix holds all the way to disk, not just in the DOM. All 5 test shows deleted afterward via `/api/delete` and confirmed gone by exact `show_id`.
- No errors, crashes, or XML-specific breakage found anywhere in this pass.

### Backdating `xmltv`/`episodes`/`up_next` — exhausted, confirmed dead end 2026-08-10

Multiple live rounds against the real device (105404BE, fresh `DeviceAuth` pulled from `/discover.json` each time) plus external research, all converging on the same answer: **there is no way to make these three endpoints return older-than-current data.** Full trail, so this doesn't get re-litigated:

- **Parameter sweep** — every plausible param name tried against `xmltv`, one at a time, all byte-identical to the no-param baseline: `Start`, `start`, `Duration`, `Days`, `days`, `Hours`, `Offset`, `Channel`, `SynopsisLength`, `V=2`, `Count`, `Category`, `Date`, `d`, `Time`, `t`, `From`, `Since`, `TZ`, `Window`, `History`, `Lookback`, `Past`, `backfill`, `startTime`, `start_time`, `WindowStart`, `Age`, `MaxAge`. Tried as positive epoch, epoch 3 days back, and negative-delta epoch (`-259200`) — no format changed the outcome. `episodes` ignores `Start` the same way (see above).
- **`guide.php` used as a control** — same backdated epoch values that `xmltv` silently swallows correctly return `400 Bad Request` on `guide.php` (its real ~55h backward limit), proving the params were reaching the server and being parsed at all — `xmltv`/`episodes` genuinely discard them rather than something swallowing the query string in transit.
- **HTTP-level spoofing** — forged `Date:` request header (RFC 7231 defines `Date` as a *response* header; servers aren't obligated to honor a client-supplied one, and this one doesn't) and `curl -z`/`If-Modified-Since` (no `304`, ever) — both no-ops.
- **Cache-bypass proof** — response headers show `xmltv` sits behind an nginx cache (`Age`, `Cache-Control: max-age=86400, max-age=1800`, short/inconsistent TTL suggesting multiple edge nodes). Appending never-before-seen bogus query params (`totally_bogus_param_xyz=...`) forced genuine cache misses (`Age: 0` — confirmed fresh origin compute), and the origin *still* returned identical content. Rules out "the CDN is hiding real per-request behavior" — the origin itself ignores these params.
- **Alt hosts/paths/UAs** — `my.hdhomerun.com/api/xmltv` → `403`. `/api/xmltv/v2` and `/api/xmltv.php` both resolve (`200`) but return byte-identical content to the canonical path — aliases, not different implementations. Spoofed `User-Agent` (`Channels DVR`, `TVHeadend/4.3`, `Plex Media Server`, `SiliconDust-DVR/2.0`, etc.) made no difference.
- **`up_next?V=2` correction** — `docs/HDHRFindings.md` previously claimed a past `Start` returns `500` (see the "Endpoints Not Yet Used" table above). Retested 2026-08-10: it now returns `200` with body `null`, not `500`. Behavior changed since the original finding, or the original finding was wrong — either way, it's still functionally forward-only (no usable past data), just via `null` rather than an error status.
- **Format verification — retried everything with a positive control, 2026-08-10:** every "ignored" result above used a plain epoch-seconds integer for date-shaped params. To rule out "wrong format" as the reason nothing worked, retried every date/time param name (`Start`, `Date`, `Time`, `Since`, `From`) against `xmltv` in **five** formats — epoch-seconds, epoch-**milliseconds**, the XMLTV body's own native datetime string (`"yyyyMMddHHmmss +0000"`, i.e. the same encoding `<programme start>` uses), ISO 8601 date (`YYYY-MM-DD`), and ISO 8601 datetime (`YYYY-MM-DDTHH:MM:SSZ`) — 25 combinations, all byte-identical to baseline. Also retried the count/window-style names (`Days`, `History`, `Lookback`, `Window`, `MaxAge`) as small positive day/hour counts (`3`, `72`) instead of the earlier arbitrary values, and `TZ` as both a UTC offset (`-0500`) and an IANA zone name (`America/Chicago`) — still no change. `episodes?...&Start=` retried in all three date formats too — still ignored.
  **The crucial positive control: `up_next?V=2&Start=<epoch-seconds>` genuinely works going *forward*** — `Start=now` returns slot key `1786393800`, `Start=now+6h` returns a different slot key `1786415400` with different content. This proves epoch-seconds is unambiguously the *correct* format for a `Start` param on SiliconDust's own guide APIs (same encoding `guide.php` uses) — so `up_next`'s `null` response for a past `Start`, and `xmltv`/`episodes` ignoring `Start` entirely regardless of format, are confirmed to be real server behavior, not us feeding it a format it doesn't recognize.
- **External research** — SiliconDust's own wiki/forum, five third-party open-source consumers (`HdHomeRunEpgXml`, `HDHomeRunXmlAPI`, `HDHomeRun2XMLTV`, `HDHomeRunEPG-to-XmlTv`, the Jellyfin `hdhomerun-jellyfin-guide` plugin), and the official `XMLTV/xmltv` reference toolset (no HDHomeRun grabber exists there at all) — none document or implement any backdating trick. The only "extend the window" technique anyone uses is **forward** pagination on `guide.php` via `Start`+`Channel`+`SynopsisLength` in a loop (same idea already listed as an unimplemented candidate above) — nobody, anywhere, fetches the past through these endpoints.

**Conclusion:** this is a hard server-side limitation, not a gap in how we're calling it. If historical guide data is ever needed, the only viable approach is **local archiving** — have `GuideStore` persist its own periodic `guide.php`/`xmltv` pulls over time — not a request parameter, since none exists.

### Backdating retest — five new angles, all dead ends, 2026-08-26

Re-opened specifically to try angles the 2026-08-10 sweep above didn't cover — not a re-run of the
same param-name sweep. Same device (105404BE), fresh `DeviceAuth` pulled live from `/discover.json`.
Result is unchanged: **still no way to backdate `xmltv`.**

1. **TCN content negotiation** — `xmltv`'s response headers include `TCN: choice` (Apache
   Transparent Content Negotiation is active on the resource). Sent `Negotiate: vlist` to list
   variants: server returned `HTTP 300` with exactly one variant —
   `Alternates: {"xmltv.php" 1 {type application/x-httpd-cgi}}`. Confirms `xmltv` is a plain
   Apache CGI script (`xmltv.php`) behind nginx caching, not a parameterized API with hidden
   alternate-window resources. `HEAD`/`OPTIONS` both echo the same single-variant headers. Dead end.
2. **`guide.php` output-format switch** — since `guide.php` already has *real* `Start`-based
   backdating, tested whether it has an undocumented flag to emit XMLTV-shaped/richer output while
   keeping that real `Start` support: `Format=xmltv`, `Format=xml`, `Output=xml`, `Output=xmltv`,
   `Type=xmltv`, `V=xmltv`, `V=2`, and an `Accept: application/xml` request header. Every one
   returned `HTTP 200` with a byte-identical response to the plain call (same `Start`/`Duration`,
   no extra param) — `Content-Type` stayed `application/json` regardless of the `Accept` header.
   No format switch exists; `guide.php` unconditionally emits JSON. Dead end.
3. **POST instead of GET** — `xmltv` requires `DeviceAuth` in the query string specifically; a
   `POST` with `DeviceAuth` only in a form-encoded or JSON body (not the query string) returns
   `403 Forbidden`. A `POST` with `DeviceAuth` in the query string *and* backdate params
   (`Start`/`Duration`) in a JSON body returns `200` with a response byte-identical to the GET
   baseline (`3966236` bytes) — the body is silently ignored entirely; behaves exactly like GET.
   Dead end.
4. **Custom request headers** — tried `X-HDHomeRun-DeviceAuth`, `X-HDHomeRun-Start`,
   `X-HDHomeRun-Window` (modeled on the `X-HDHomeRun-Resource`/`X-HDHomeRun-Error` response headers
   documented elsewhere in this doc), `X-Requested-With`, `X-Forwarded-For` — every one returned a
   byte-identical `3966236`-byte response to baseline. (`Range: bytes=0-1000` correctly returned a
   `1001`-byte partial response — confirms `Accept-Ranges: bytes` isn't a lie, but a byte range of
   the same fixed document isn't a different window.) Dead end.
5. **Alternative auth (`Email=` + `DeviceIDs=`)** — flagged as untested in the 2026-08-10 sweep.
   Discovered a real, previously-undocumented endpoint while probing this:
   **`GET https://api.hdhomerun.com/api/account?DeviceAuth=<auth>`** → `HTTP 200`,
   `{"AccountEmail": null, "AccountDeviceIDs": ["105404BE"]}` (403 without `DeviceAuth`). This
   device's `AccountEmail` is `null` — **it isn't linked to any SiliconDust account**, which is
   exactly what "free tier, no DVR subscription" means in practice: there's no account email to
   pair with `Email=`+`DeviceIDs=` auth at all for this device, so the alt-auth path can't be
   positively exercised here. `Email=test@example.com&DeviceIDs=105404BE` (an unlinked/bogus email)
   returns `403 Forbidden`, as expected for an email with no relationship to the device — this
   doesn't confirm or rule out whether alt-auth would behave differently on a *linked* account, only
   that it can't be tested without one. Genuinely inconclusive, not a dead end — revisit if this
   device (or another) is ever linked to an account, ideally one with an active DVR subscription so
   the tier-difference question from 2026-08-10 could also finally be tested instead of assumed.

**Conclusion unchanged:** `xmltv`'s server-side window (no backdating, ~48h forward on this
account) is fixed by the origin regardless of transport (GET/POST), headers, content negotiation,
or `guide.php`-style format params. The only unresolved thread is account-linked alt-auth,
which needs credentials this device doesn't have — not something further guessing can resolve.
