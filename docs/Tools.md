# Tools — full reference

Full, verbatim descriptions for every script in `tools/` (and the bundled terminal client). `CLAUDE.md`'s Tools table carries a one-line summary of each; add new tools to both. Per `.claude/CONVENTIONS.md`: script repeatable tasks, give them `--help`.

| | |
|---|---|
| `tools/setup_signing.sh` | One-time: Developer ID cert + notarization creds (run before first `deploy_release.sh`) |
| `tools/mock_hdhr.py` | Fake HDHomeRun device for discovery/guide/fault-injection testing. `--guide-file PATH` serves a fully custom, hand-authored guide.json (re-read on every request) instead of proxying to the real device/cloud — deterministic EPG content (custom SeriesIDs, titles, air times) for scheduling tests, independent of what's actually airing. Forces DeviceAuth off on the mock so `GuideStore` actually fetches from it rather than going straight to the cloud API. Pair with `mock_scenario.py plant`. |
| `tools/mock_tuner.py` | Standalone, high-fidelity HDHomeRun **emulator** (no real device; root only to bind port 80 — the app fetches a device guide from :80 regardless of the advertised port): UDP discovery on 65001, HTTP API on :80, streams on :5004, answering byte-for-byte like the real EXTEND per `docs/HDHRFindings.md`'s "Device Emulation Ground Truth" (header set, key order, lineup.json/.xml/.m3u, timed channel scan, favorites, 801/805 errors, tuner occupancy in status.json, rotating DeviceAuth, UDP filter/`0x2D` quirks). Logs every client request with IP + User-Agent and decodes every UDP probe, so it doubles as a third-party-client probe. `--mirror IP` copies a real device's identity + lineup (never its ID/auth); `--ts-file` streams real TS; `compare A B` diffs two devices field by field (e.g. the real tuner vs. another candidate device). Unlike `mock_hdhr.py` (a proxy in front of a real device, used by `run_test_scenarios.sh`), nothing upstream is needed. |
| `tools/mock_scenario.py` | Plant mock app states via the live guide API to demo/test behavior, then clean up. Subcommands: `duplicate` (fake "already recorded" file → green skip flag), `conflict` (schedule >tuner-count overlapping shows → conflict), `record-test` (schedule a now-airing entry, verify it records, self-clean), `start` (same, but leave the `[MOCK]` recording running for UI tests — exit 2 = nothing to start; remove with `clean`), `ensure` (idempotent `start`: no-op if a `[MOCK]` recording is already running) and `status` (exit 0 if one is recording, 1 if not), `plant --file X.json` (schedule arbitrary custom shows by matching title/channel/device against whatever guide is currently loaded — pair with `mock_hdhr.py --guide-file` for full control over what's there), `list`, `clean`. Safety markers: planted files carry the `19700101_0000` date signature; scheduled shows are titled `[MOCK] …`; `clean` removes only those. Needs the app running (web server on); `duplicate` also needs Series-subfolders + Skip-already-recorded on. |
| `tools/test_favorite.sh [device-ip] [channel]` | Manual diagnostic against a **real** HDHomeRun device (not a mock) — toggles a channel's favorite via `/lineup.post`, verifies via `/lineup.json`, restores the original state. Standalone bash+curl+python3, no app instance needed. Useful for confirming the device's own favorite-toggle API still behaves as expected, independent of this app's code. |
| `tools/run_test_scenarios.sh [--port N]` | End-to-end scheduling-engine scenario test — orchestrates `test_scenarios/build_scenarios.py` (generates a custom guide + matching `mock_scenario.py plant` file covering edge cases like seriesChannel/seriesAll cross-channel scoping, Bonus Time genre matching, title-only fallback, dateTime anchors), `mock_hdhr.py --guide-file` (serves it), and a real app restart so it picks the mock device up fresh, then plants the scenario shows via the live `/api/record` path. **Stops and restarts the real running app** (refuses if anything is `show_recording`) and needs `sudo` (mock device needs port 80 + a loopback alias); leaves `mock_hdhr.py` running in the background on exit — see its own teardown instructions. Reversible any time with `mock_scenario.py clean`. Generated fixtures/log under `tools/test_scenarios/` are gitignored (regenerated fresh per run, timestamped relative to "now" — a committed copy would go stale immediately); only the two scripts are tracked. |
| `tools/ui_events.swift` | Synthetic right-click + key events (`ui_events rightclick X Y` / `keys CODE…`, keys posted to the app's pid) for UI tests — the PiP's native NSMenu isn't reachable via AX (`AXShowMenu` does nothing, a popped NSMenu isn't in the AX tree). Compiled on demand by `WindowNavigationTests.pipFullWorkoutOverLiveRecording`. Note: on macOS 27 `entire contents of <window>` returns an empty list while a recursive `UI elements` walk works — that test uses the latter. |
| `tools/ax_query.swift` | Fast Accessibility queries for UI tests — native `AXUIElement` (`ax_query windows` / `find WINDOW MATCH [--last] [--press]` (prints `role|title|help|x,y,w,h|path`) / `count` / `text`; MATCH = `id=`/`help^=`/`help$=`/`role=`/`title=` joined by `&`), ~0.07 s where a System Events walk of Watch Now / the PiP picker took minutes. Compiled on demand by `WindowNavigationTests` (`axQueryPath`); see `docs/LiveUITests.md`. | **Also (2026-10-15):** `row WINDOW ANCHOR BUTTON [--press]` finds the BUTTON whose vertical centre is closest to the ANCHOR element's (e.g. the Run button of the Settings row labelled "Preview Launch Splash": `row '' 'text=Preview Launch Splash' 'role=AXButton&title=Run' --press`), and MATCH accepts `text=VALUE` (value, title or description equals VALUE).
| `tools/build_dmg.sh <version> <path-to-app>` | Assembles the release installer DMG (app + `Applications` alias + `Read Me.rtfd` + custom background) via `create-dmg` (`brew install create-dmg`) — called automatically by `deploy_release.sh`, but directly runnable against any `.app` (a plain `./deploy.sh` dev build included) to iterate on the DMG layout without a real signature/notary round trip. See `docs/Distribution.md`'s "DMG assembly" section. |
| `tools/build_readme_manual.swift` | Builds the DMG's `Read Me.rtfd` fresh from `docs/screenshots/` every run, via Cocoa's own `NSAttributedString` RTFD writer (`swift tools/build_readme_manual.swift <repo_root>`) — called by `build_dmg.sh`, not run standalone in practice. |
| `tools/apply_finder_icon.swift` | Sets a file/folder's custom Finder icon via `NSWorkspace` (`swift tools/apply_finder_icon.swift <icon.icns> <target>`) — `cp -R` does not reliably preserve this attribute on a bundle/folder, so `build_dmg.sh` re-applies it at each staged copy rather than trusting a copy to carry it. |
| `tools/generate_favicon.py` | Builds `Resources/favicon.ico` (16×16 + 32×32) from two source PNGs — `python3 tools/generate_favicon.py <16px.png> <32px.png> <out.ico>`. Shared by `deploy.sh`/`deploy_release.sh`'s "Generating app icon" step (previously a ~13-line heredoc duplicated verbatim in both). |
| `tools/feed_diagnostics/` | Toolkit built 2026-09-12 to root-cause the (now-resolved) VLC-side FEED playback-stall bug — see `issues_resolved.md`'s "VLC-side FEED playback stalls" entry. `feed_capture_tagger.py` runs as a second, independent FEED reader tagging wall-clock time to cumulative byte offset as it captures; `watch_and_extract.sh` tails a client's log for real `[VLC] STALL —`/`STALL resolved` pairs and auto-slices the corresponding window out of that capture (`extract_window.py`) on each one; `analyze_pcr.py` is a from-scratch TS parser that extracts PCR values from the sliced window and flags backward jumps, spec-violating gaps, discontinuity flags, and continuity-counter breaks. Not a one-off — kept tracked since it's directly cited as evidence in that resolved-issue writeup and is the fastest path to re-diagnose a similar future stall. |
| `hdhrVCRplus.app/Contents/Helpers/hdhr_guide` | Bundled terminal client for the guide (not in `tools/`) — see `docs/TUIGuide.md`. |
| `tools/release_checklist.py <preflight|stamp|notes|publish> <version>` | The paperwork around a release — everything except the build (`./deploy_release.sh` stays the build). `preflight` = read-only readiness report (version vs last tag, clean tree, CHANGELOG Unreleased/stamped + bundled copy identical, RELEASES entry + 3–4 README bullets, Developer ID cert, notarytool profile, create-dmg, gh login, disk, no `[MOCK]` shows, nothing recording/due in 45 min; `--tests` runs build + unit tests, `--ui` the live UI suite). `stamp` turns CHANGELOG's `## Unreleased` into `## v<version> — <date>` (no empty Unreleased is left behind — the next change adds one again, as at v2.5.0/v2.6.0), syncs `Sources/hdhr_VCR/CHANGELOG.md` and RELEASES' date; re-running keeps the stamped date unless `--date` is given. `notes` writes `dist/release-<version>/notes.md` from RELEASES.md. `publish` creates the GitHub Release from `dist/hdhrVCRplus-<version>.dmg` (dry run unless `--yes`; a DRAFT unless `--live`; `--live` also updates README's "Latest" heading + download link and commits it; the bullets under it stay manual and the tool reminds you). A README check (Latest heading, What's New headline, and that `origin/main`'s README equals the working copy, i.e. the front page is pushed) runs in `preflight` as warnings and after `publish --live` as failures. Never pushes or builds. `RELEASE_REPO_ROOT` points it at a copy for testing. |

## `tools/perf_baseline.py`
Release-to-release performance baseline: `prime` (once per build, lets macOS ask for Local Network access), `run` (launches the build 3×
in the GUI session with a temp home and a staged copy at `~/Library/Caches/hdhrVCRplus-perf/<label>/`, measures launch time, launch
CPU, idle CPU, memory and web timings, saves `docs/perf/<label>.json`) and `compare` (table with change vs the previous row). Uses the
real tuner read-only — run it when nothing is recording or due. Each result also records the connection (Ethernet link speed, or Wi-Fi band/signal/noise/link rate) and ping round trips to the tuner and gateway (`--tuner-ip`, else read from the real app's `[Discovery]` log line), shown in `compare`'s `network` column — compare builds on the same connection, since Wi-Fi adds a few ms and jitter. Results and how to read them: `docs/PerformanceHistory.md`.

## `tools/apple_bug_repro/` — AVFoundation MPEG-TS timestamp bug (2026-10-28)
`make_samples.sh [--help]` uses ffmpeg to generate three 60-second 720p59.94 MPEG-2 + AC-3 transport streams that differ only in where their 90 kHz timestamps start: `before.ts` (stays below 2^32), `across.ts` (crosses 2^32 = 47,721.86 s, 29 s in) and `after.ts` (above it). `read_samples.swift` (`swiftc -o read_samples read_samples.swift && ./read_samples <file>`) reads the video track with `AVAssetReader` over the first and last 5 seconds and prints the frame counts: about 300 for `before` and `after`, 3 for `across`. The generated files are 48 MB each and are not kept (`.gitignore`d). Evidence for the Feedback Assistant report in `docs/AppleBugReport_TS_2e32.md`; the app's workaround is `TSRebaser` (`docs/WebStreaming.md` "Timestamp rebasing").
