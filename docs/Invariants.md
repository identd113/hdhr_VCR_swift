# Invariants & Gotchas — full text

The complete, verbatim text of the invariants that `CLAUDE.md` summarizes in one line each. Moved here unchanged so `CLAUDE.md` stays scannable; the two highest-stakes invariants (**Tuner occupancy**, **Virtual tuner relay guardrails**) and the short ones stay in full in `CLAUDE.md` itself. Rules here are as binding as there.

## Web guide genre filter and show search share one dim function and are mutually exclusive

**Web guide genre filter and show search share one dim function and are mutually exclusive** — `applyFilterDim()` (`guide.js`, renamed from `applyGenreDim` 2026-08-28) is the single place that toggles `.g-prog-dim`, checking `_searchShow` (show search) before `_genreFilter` (genre/new/infomercial). Selecting a show search result clears `_genreFilter`, and picking a genre clears `_searchShow` — at most one is ever active. A future change to either filter must go through this shared function; adding a second, parallel dim pass would let the two drift out of sync (e.g. both applying at once, or a `setDev`/`refreshGuide` reapply only catching one). See `docs/WebServer.md`'s "Show search" section.

## Web guide managed markers are tuner-scoped, and channel-scoped for seriesChannel

**Web guide managed markers are tuner-scoped, and channel-scoped for `seriesChannel`** — the blue `.g-st-sched` status ring + ⏱ badge (see `docs/WebServer.md`'s "Status ring + badge") is driven by `ManagedGuideMatcher.owner(for:)`, whose matching scope now mirrors each type's actual scheduling scope exactly, not just its tuner: `seriesAll` uses device-only keys (`"deviceId:SeriesID"` / `"deviceId:title"`, `seriesKeys`/`seriesTitles`) and matches any channel on its tuner (reruns/affiliates often shift channels — this is the point of `seriesAll`); `seriesChannel` uses device-*and-channel* keys (`"deviceId:channel:SeriesID"` / `"deviceId:channel:title"`, sharing the same `seriesKeys`/`seriesTitles` dictionaries — a channel-scoped key can never collide with a device-only one, so `owner(for:)` just tries the channel-scoped shape first) and matches only the one channel it was added from — a same-series rerun airing on a *different* channel (e.g. a syndicated rebroadcast on another station) does not get badged, matching what `AppState.resolveSeriesAir`/`nextGuideEpisode`/`scheduleNextAir` would actually schedule/record from (a `channelNum` filter that's `nil` only for `seriesAll`, `deviceId` always pinned to the show's own tuner for both). Neither type can ever match/record on more than one tuner. Before 2026-08-15 both types shared the same device-only keys, so a `seriesChannel` show's badge could appear on channels it would never actually record from — see `issues_resolved.md`. `dateTime` slot keys include weekday (`"device:channel:Weekday:HH:MM"`) so a Wednesday-only show doesn't flag Friday reruns. When **Skip already-recorded episodes** is on (with Series subfolders), a managed block whose `SxxExx` is already on disk shows the slate `.g-st-skip` ring + ⏭ badge (`data-skip=1`) *instead of* the blue `.g-st-sched` one — computed in `buildGuideGridHTML` via `AppState.recordedEpisodeTags(...)`, one scan per managed series per build.

(As throughout this doc, "tuner" here means the HDHomeRun **device** identified by `hdhr_record`/`deviceId` — every show is scoped to the one device it was set up on, never to an individual physical tuner port within it. A multi-tuner device's own tuner capacity is pooled and undifferentiated to this app — see "Tuner occupancy" above — so nothing here or elsewhere tracks a show against "tuner0" vs "tuner1" on the same device.)

## Web guide offline devices

**Web guide offline devices** — devices referenced in `show.hdhr_record` but absent from `state.devices` get a dashed "not detected" button in the guide device bar, and its ▾ dropdown still lists that tuner's own shows. Never silently omit them. Opening a show assigned to an undetected tuner from that dropdown shows an amber `#em-dev-warn` banner in the edit modal ("Tuner HDHR-XXXX is no longer detected…") and hides the Pause button (pausing a phantom tuner's show does nothing useful) — Cancel/Delete stay as the only meaningful actions.

## Web guide is per-tuner

**Web guide is per-tuner** — no global schedule popover. Each tuner gets a box in `#dev-bar` (`tunerBox`): name (a `setDev` guide filter when active), live count badge (→ `#t-pop`), and a **▾** that toggles a per-tuner dropdown (`#tdrop-{devId}`) of that tuner's own Recording/Up Next/Scheduled/Paused, built by `buildTunerShowsHTML(state:, deviceId:)`. With >1 tuner there is no combined "All" view; the grid bootstraps to `defaultDev` (first device with lineup+guide data) via `setDev('<id>')`. Inactive tuners — not in `state.usableDeviceIDs` (offline/absent or unreachable) — render dimmed (`.tuner-off`) with a non-clickable name and an "offline" badge, but their ▾ still lists assigned shows. As of 2026-08-15, a previously-discovered device (in `state.devices`) that goes unavailable is only rendered at all if at least one show still references it (`hdhr_record`) — an unavailable device nothing depends on is omitted entirely rather than left as a permanently-dimmed, empty tuner box. This is distinct from — and doesn't affect — the "Web guide offline devices" case just below (a device *never* discovered at all but referenced by a show), which is always shown per that invariant's own "never silently omit them" rule. Dropdowns update via `refreshGuide` (swaps each `.tdrop` body) and the recording-event SSE (`tdrop`/`tdropDev` → swaps `#tdrop-{device}`).

## Web guide now-line origin

**Web guide now-line origin** — the live now-line plots `Date.now()` against JS `_winStart`/`_winSec`. `applyGuidePayload` (used by `refreshGuide()` and by SSE guide-change events) swaps in a grid the server rendered against a *fresh* `winStart` (it advances every 30 minutes), so it must re-read `data-winstart`/`data-winsec` from the new `.g-hdr` to resync those vars **and call `updateNowLine()`** — else the now-line drifts ahead on the new grid. The server's cached grid/pages are rebuilt by every guide-changing event *and* by `WebServer.refreshCachesIfGuideWindowMoved` (checked on GET `/`, `/vertical`, `/api/guide-refresh`) when the window has advanced; the periodic `guide_refreshed` event only fires every `GuideHours/divisor` (2–3 h by default, not hourly). Every grid payload goes through the `nextEvtSeq()`/`applyGuidePayloadSeq` ordering guard so a slow older fetch/decode can't overwrite a newer grid, and the page re-syncs with `refreshGuide()` when its EventSource re-opens or a hidden tab wakes.

## Per-show runtime tracking

**Per-show runtime tracking** — the show_id-keyed "what's currently going on with this show" state (conflict flags, notification-dedup epochs, retry backoff, the Discord card task chain, etc.) lives in one `AppState.showRuntime: [String: ShowRuntimeState]` dictionary, not a dozen+ independent `Set<String>`/`[String: X]` fields (that was the pre-2026-08-30 shape — see `issues_resolved.md`). `deleteShow` clears a show's entry with a single `showRuntime.removeValue(forKey:)`. A new field on `ShowRuntimeState` needs no separate `deleteShow` wiring — it's covered automatically by that same removal. Exception: `tunerStatus` stays its own separate `@Published` dict, deliberately not folded in — see `ShowRuntimeState`'s own doc comment in `AppState.swift` for why (folding it in would make every other field's mutation also fire `objectWillChange`, reintroducing the "Menu rebuild churn" class of bug below).

## Transcode capability gate

**Transcode capability gate** — `HDHRDevice.supportsTranscode` (`Models.swift`, `ModelNumber` starting with `"HDTC"` — nil/unknown ModelNumber, e.g. a UDP-only-discovered device, conservatively means `false`) is checked once, right before `AppState.startRecording` calls `recordingManager.start(...)`: `effectiveTranscode = device.supportsTranscode ? show.show_transcode : "none"`. This is the *only* place the override happens — `show.show_transcode` itself is never mutated by it, so the Transcode picker (native `ShowFormSection`, web `#rm-transcode`/`#em-transcode`) still shows the user's actual saved choice even on an unsupported tuner. A new recording call site must reapply this same gate itself; it will not inherit it by calling through `startRecording`'s existing plumbing unless it *is* `startRecording`. Both native (`ShowFormSection`) and the web guide's Record and Edit modals (`#rm-no-transcode`/`#em-no-transcode`, gated on `tuners[devId].nt` — see `docs/WebServer.md`) show a proactive warning when the picked profile would be overridden — informational only, the real enforcement is server-side and reruns unconditionally regardless of what any UI warned about. See `docs/HDHRFindings.md`'s "Transcode capability" section for why the real per-device capability field (a `Transcode` JSON field) is deliberately never queried — it only exists on a CGNAT-unsafe cloud endpoint.

## Web UI push

**Web UI push** — after any state change the web UI should reflect, call `webServer.broadcastEvent(...)`; a tuner-count change goes through `AppState.broadcastTunerOccupancyChange` — the tiny `tuner_update` badge push is **never** throttled, only the grid-rebuild half is (15 s cooldown + a trailing rebuild so a change inside the window isn't dropped); don't put a cheap push behind the expensive one's cooldown, and any code that removes a show must re-run `updateVirtualTunerPresence()` (a deleted last recording otherwise leaves the FEED relay advertising); for recording start/stop use `broadcastRecordingEvent(...)` (embeds pre-rendered HTML fragments). External browsers and in-app WKWebView windows share the same SSE stream. `addShow`/`updateShow`/`deleteShow`/`pauseShow`/`resumeShow` broadcast themselves — don't rely on the caller to do it.

## Guide page CSS/JS/HTML live in Resources/guide.css/guide.js/guide-shell.html/guide-vertical.css

**Guide page CSS/JS/HTML live in `Resources/guide.css`/`guide.js`/`guide-shell.html`/`guide-vertical.css`** — real files, not Swift string literals, loaded once via `Bundle.main` (`WebServer.swift`'s `cachedGuideCSS`/`cachedGuideJS`/`cachedGuideShellHTML`/`cachedGuideVerticalCSS`) and stitched together in `buildHTML()` via `fillTemplate(_:_:)` — a single left-to-right pass that substitutes `{{TOKEN}}` placeholders for the ~18 dynamic values (tuner JSON, guide window, config flags, pre-rendered fragments, etc) without rescanning already-substituted content, so a value containing literal `{{...}}`-shaped text (e.g. a user-entered show title) can't trigger an accidental second substitution. `guide-vertical.css` is a second, separate `<style>` block (not concatenated into `guide.css`) holding only vertical time-axis mode's rules, every selector scoped under `@media (orientation:portrait)` (automatic, no manual toggle) — and it's a distinct file specifically so editing horizontal-mode CSS can't accidentally touch vertical-mode CSS or vice versa. It's per-route, not global: `buildHTML(includeVerticalCSS:)` only embeds it (and bakes `guide.js`'s `VT_ELIGIBLE` token as `true`) on `GET /vertical`; `GET /` never ships it at all, so `/` shows the standard horizontal grid regardless of device orientation — only `/vertical` responds to rotation. See `docs/WebServer.md`'s "Vertical time-axis mode" section. Normal JS/CSS escaping rules apply — no more Swift-string double-escaping — but `node --check Resources/guide.js` fails as-is since the raw template still has unfilled `{{TOKEN}}` placeholders; validate JS syntax against the *served* output instead (`curl -s localhost:1980/ | awk '/^<script>$/{f=1;next}/^<\/script>$/{f=0}f' | node --check /dev/stdin`), or strip tokens first. `deploy.sh`/`deploy_release.sh` must copy all four into `Contents/Resources/` alongside the other bundled resources; a `#if DEBUG` fallback in `templateURL(_:_:)` lets a plain `swift build` + direct binary run still find them via a source-relative path when there's no `.app` bundle. **No auth beyond LAN-subnet matching** on any endpoint — validate inputs defensively (paths, IDs, ranges) on any new mutating route rather than trusting the caller. The one extra gate is `WebServer.requestRejectionReason` (2026-10-01): it refuses requests whose `Host` isn't this machine as a LAN client names it (blocks DNS rebinding), and POSTs that are cross-site or not `Content-Type: application/json` — so any new client (script, tool, test) that POSTs must send `application/json`.

## New cached page variant in prebuildPageHTML/buildHTML

**New cached page variant in `prebuildPageHTML`/`buildHTML`** — adding another full-page variant (another `GET /...` route with its own `cachedXHTML`/`cachedXHTMLGzip` pair, the way vertical time-axis mode added a second one alongside the original) multiplies `prebuildPageHTML`'s per-rebuild cost, which runs on `@MainActor` on every add/delete/pause/resume/edit/favorite-toggle and recording start/stop — not just page load. Keep sharing the expensive grid build (`buildGuideGridHTML`, already computed once and reused across variants) and run the independent, non-actor-isolated per-variant work (currently just `Self.gzip`, pure over plain `Data`) concurrently via `DispatchQueue.concurrentPerform` rather than adding it as another sequential step — don't let variant count silently multiply MainActor blocking time. The `buildHTML` calls themselves *do* have to stay sequential (they read MainActor-isolated `AppState` synchronously); only genuinely actor-free work belongs in the concurrent part.

## Appearance sync (native ↔ embedded guide) is one-directional per call, never a single shared function

**Appearance sync (native ↔ embedded guide) is one-directional per call, never a single shared function** — `AppConfig.Appearance_mode` drives `.preferredColorScheme` on every native `Window` (`hdhr_VCRApp.swift`) and, two-way, the web guide when it's loaded inside this app's own `AddShowWebView` (`docs/AddShowView.md`'s "Appearance sync"). `Resources/guide.js` deliberately has two entry points, not one: `applyNativeTheme(m)` (native → web, called from Swift on load and on every live Settings change) never posts back through the `appearanceChanged` WKScriptMessage bridge; `setTheme(m)` (the guide's own theme-switcher buttons — a genuine user click) calls `applyNativeTheme` *and* posts back. Collapsing these into one function would let a native-pushed theme loop back through the bridge and get treated as a fresh user choice — a resolved `"auto"` silently overwriting itself as a concrete `"dark"`/`"light"` in Settings the instant a page merely loads, with no user action at all. A browser connecting to Sharing over the LAN never reaches either path — `window.webkit` (and therefore the message handler) only exists inside a real `WKWebView`, so a remote session's own theme choice stays independent by construction, not by an explicit check.

## Auto-pause-on-missing-tuner marker

**Auto-pause-on-missing-tuner marker** — `idleLoop()` auto-pauses any active show whose `hdhr_record` isn't in `usableDeviceIDs`, and auto-resumes it once that device is usable again, by writing/checking the exact `show_fail_reason` string `"Tuner not detected"` (`AppState.autoPauseTunerMissingReason`). Pass 2's separate, older generic "paused window expired" auto-resume (same function, keyed off `show_end`/`show_next` looking stale rather than tuner state) explicitly skips any show carrying that marker — without that exclusion the two mechanisms fight: the window-expiry pass un-pauses it, the tuner check re-pauses it next tick, forever. Any future pass that iterates `pausedShows` and unconditionally flips `show_paused` must add the same exclusion, or reintroduce that loop.

## Menu rebuild churn

**Menu rebuild churn** — frequent `@Published` mutations while the NSMenu is open cause rebuild glitches; batch/coalesce assignments (see `prefetchChannelIcons`). `AppState.menuIsOpen` is true for *any* open root NSMenu (`NSMenu.didBegin/EndTrackingNotification`, installed in `startup()`), not just the menu-bar one — new high-frequency `@Published` writers must gate on it. The same begin/end notifications are how a double-click on the menu-bar icon is recognised (a root menu that opens and closes within 0.6 s with the pointer still on the icon — `isIconDoubleClick` → `surfaceOpenWindows()`), so keep them root-menu-only and keep recording `menuTrackingBegan`. A SwiftUI `.contextMenu` inside a view that observes `VLCBridge`/`AppState` is rebuilt on every publish (the player's PiP menu reloaded every few seconds), so menus there are native `NSMenu`s built at click time via `NativeContextMenuHost` (`Views/NativeContextMenu.swift`) — don't convert them back to `.contextMenu`.

## Guide service outages

**Guide service outages** — `GuideStore` records *why* a fetch failed (`lastFailure`: certificate/TLS, network, HTTP status, bad response; `classify(_:)`), a zero-channel reply counts as a failure, and a device with no guide in memory falls back to the newest on-disk copy (≤ 36 h, still covering now) instead of sitting empty — 2026-10-09 SiliconDust's `*.hdhomerun.com` certificate expired and every guide call failed TLS, which on a restart would otherwise have skipped every guide-confirmed series recording ("guide no longer confirms"). Keep it so: `needsRecovery` (empty *or* last-fetch-failed) — not "channels empty" — is what drives `ensureGuideLoaded`'s backed-off retries, so a restored saved guide keeps being retried until a fetch succeeds; a certificate failure alerts once per outage ("Guide Service Certificate Problem") and a recovery alert follows (`handleGuideLoadFailure`/`handleGuideLoadSuccess`, `Discord_on_guide_error`). See `docs/GuideStore.md`, `docs/AppState.md`.

## SwiftUI Menu is not a styleable button on macOS

**SwiftUI `Menu` is not a styleable button on macOS** — macOS draws a `Menu` as a pop-up and ignores `.borderedProminent`/`.tint` unless Accessibility → Display → "Increase contrast" is on (and strips a custom label to plain icon + text), so the same code looked red on one Mac and grey on another. Watch Now's Record is therefore a real `Button` (`quickRecordButton`) that pops a native `NSMenu`; the player toolbar's icon-only Record still uses `quickRecordMenu`. Don't rebuild a styled control as a `Menu`. Also: macOS accessibility settings change rendering — compare the two Macs' `defaults read com.apple.universalaccess` before assuming a code difference.
