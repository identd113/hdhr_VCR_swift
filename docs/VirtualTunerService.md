# VirtualTunerService.swift — Recording-relay virtual tuner

**Hidden as of 2026-09-10** behind a new master switch, `AppConfig.FEED_feature_enabled` (default `false`, config-file only — no UI sets it anywhere on purpose). While it's off: `AppState.remoteRelayEntries` short-circuits to `[]` (so MenuContent's "Recording on Another Mac" section and the menu bar's blue `feedAvailable` blink never appear, even if another Mac's relay is genuinely discovered on the LAN), `updateVirtualTunerPresence()` never starts the relay regardless of `Virtual_tuner_relay_enabled`'s own value, and both the Settings → Sharing "Recording FEED (Beta)" section and `FirstRunWizardView`'s Recording FEED step are skipped entirely (the wizard's `orderedSteps` simply omits `.recordingRelay`). Reason: the feature needs more work (VLC playback stalls, audio/CC track switching — see `TODO.md`/`ISSUES.md`) — hidden rather than removed so it's a one-flag flip back, not a revert. Everything below describes the feature as it behaves once `FEED_feature_enabled` is `true`; none of that mechanism changed.

While ≥1 show is actively recording, this app presents itself as an additional, temporary HDHomeRun-like tuner — discoverable via the real binary UDP protocol plus the standard `/discover.json`/`/lineup.json`/`/status.json` HTTP shape — whose channel(s) relay the in-progress recording(s) straight from disk. Any HDHomeRun-aware client on the LAN, and in particular **another instance of hdhrVCRplus**, can discover and watch what's currently being captured without opening a second real tuner session against the actual device. See `TODO.md`'s "Virtual tuner relay: real VLC-based H.264 transcode (Phase 2)" entry for the deferred follow-up work; this (Phase 1) shipped 2026-09-02.

This reuses the Watch Now relay's existing disk-tailing mechanism (`docs/WebServer.md`'s "Recording playback relay") rather than tapping the live tuner feed a second time, so viewer count for the relayed channel is not tied to any physical tuner slot — it's N HTTP readers of one growing file, not N tuner sessions.

**User-facing toggle**: `AppConfig.Virtual_tuner_relay_enabled` (default `false` — changed 2026-09-04, was `true`) — Settings → Sharing → "Rebroadcast In-Progress Recordings", and explained on its own dedicated first-run wizard step (`FirstRunWizardView`'s Recording FEED step — see `docs/FirstRunWizardView.md`). `AppState.updateVirtualTunerPresence()` treats it as an equal condition alongside `isRecording` (`if isRecording && config.Virtual_tuner_relay_enabled`), and both `SettingsView.save()` and the wizard's `finish()` call `updateVirtualTunerPresence()` directly when the value changes, so toggling it off tears the relay down immediately if a recording happens to already be in progress, rather than waiting for that recording to end.

## Components

- **`VirtualTunerService.swift`** — owns only the UDP discovery socket lifecycle. As of 2026-09-06, exactly one socket per process ever binds `INADDR_ANY:65001` (`SO_REUSEPORT`, so it coexists with a real device or another instance's own responder), and it binds once at app startup — `AppState.init()`'s unconditional `beginPassiveListening()` call — independent of whether this instance ever relays anything itself: two sockets on the same host both bound there (a passive listener plus a separately-relaying instance's own responder) would let SO_REUSEPORT's per-flow hash silently route some real discovery requests to whichever socket isn't actually advertising, dropping them. `start(deviceID:baseURL:tunerCount:onBindResult:)` reuses that same socket (binding it first only if `beginPassiveListening()` somehow hasn't yet) and starts actually replying to DISCOVER_REQUESTs with a DISCOVER_REPLY carrying the given `deviceID`/`baseURL`/`tunerCount` (see "Wire protocol" below) — gated on an internal `isAdvertising` flag so a passively-bound-but-not-relaying socket never answers a real probe with stale/zeroed-out fields. `stop()` clears `isAdvertising` and the advertised fields but leaves the socket bound (it keeps listening for other instances' announces — see below) — it no longer closes the socket at all. Deliberately dumb — it doesn't track the lineup, doesn't know about `Show`, and exposes no readable state back to callers; `AppState` remembers its own copy of the ID/baseURL/tunerCount it started the service with.
  **Bind retry, added 2026-09-11** — `beginPassiveListening()`'s one-shot bind used to just give up on a transient failure (e.g. a quick relaunch before the OS releases the prior process's own socket), silently degrading this instance to the ~10s idle-loop discovery poll for its whole run with nothing prompting a retry unless it later started recording itself (`start()`'s own `bindSocketIfNeeded` call gets a fresh attempt then, independent of this one). `beginPassiveListening()` now retries the bind up to 3 times with backoff (`bindSocketWithRetry(attemptsRemaining:delay:)`) before giving up for good.
- **Unsolicited FEED announces, added 2026-09-06** — `VirtualTunerService.broadcastAnnounce()` broadcasts the currently-advertised DISCOVER_REPLY (reusing `HDHRManager.subnetBroadcastAddresses(interface:)`'s own target list, now `internal` rather than `private` for this reuse) to the LAN instead of unicasting it to one requester, called right after every `start(deviceID:...)` (fresh start or refresh-in-place) and once more, before clearing the advertised fields, inside `stop()`. `handleReadable()` recognizes an inbound unsolicited DISCOVER_REPLY (type `0x0003`, as opposed to a request it should itself answer) via `isDiscoverReply(_:)`/`deviceID(fromReplyPacket:)`, self-filters it out when the announced DeviceID matches `lastBroadcastDeviceID`, and otherwise fires `onFeedAnnounce(String, Bool)` — `AppState.init()` wires this to an immediate `probeForNewDevices()` call. Net effect: another hdhrVCRplus instance on the same LAN learns "a FEED appeared/changed/disappeared" within about a second, instead of only on its next ~10s idle-loop discovery poll. This only speeds up *cross-instance* discovery — it cannot and does not help a non-hdhrVCRplus client (a real HDHomeRun's own firmware never proactively pushes state either) discover anything faster, since only this app's own instances know to send/listen for the extra announce.

  **Goodbye short-circuit, added 2026-09-12.** The plain re-probe nudge above only sped up *when* `probeForNewDevices()` next ran — it still had to accumulate 3 consecutive missed probes (`AppState.swift`'s `missedProbes`/`missed == 3` check) before actually marking the device unavailable, the same threshold an ordinary unprompted idle-loop poll would eventually hit on its own. `stop()`'s final `broadcastAnnounce()` call now passes `goodbye: true`, which sends `tunerCount: 0` and sets the `0xF0` TLV described in "Wire protocol" below. `AppState.onFeedAnnounce`'s closure checks the `Bool` this carries through to `handleReadable()`'s `onFeedAnnounce?(hex, goodbye)` call and, when true, pre-sets that device's `missedProbes` to `max(current, 2)` *before* calling `probeForNewDevices()` — so the very next probe (which will legitimately not find a relay that just told everyone it stopped) hits the existing `missed == 3` branch and marks it unavailable on this same cycle, rather than waiting ~2 more idle-loop ticks for the threshold to elapse the slow way. `max(...)`, not a flat assignment, so this can never *lower* an already-higher miss count from prior real misses.
  **Self-filter, fixed 2026-09-07**: the self-filter originally compared the announced DeviceID against `isAdvertising && advertisedDeviceID` — but `stop()` calls `broadcastAnnounce()` *then* immediately clears both fields in the same serial-queue closure, so a delayed loopback of `stop()`'s own "goodbye" broadcast arrived after that state was already cleared and got misread as a genuine remote announce (a real, confirmed bug — see `issues_resolved.md`). `broadcastAnnounce()` now sets a dedicated `lastBroadcastDeviceID` field at the moment it actually sends, and `handleReadable()` compares against that instead — correct regardless of `isAdvertising`'s current value or how much later a loopback packet arrives.
  **Bounded lifetime, added 2026-09-11**: `lastBroadcastDeviceID` used to never be cleared at all — but `relayDeviceID(sourceDeviceID:)` is deterministic per *source* device, so an unbounded lifetime could silently self-filter a genuinely later, different relay session for the same physical tuner (this instance restarting its own relay after a stop/restart, or — since multiple hdhrVCRplus instances can point at the same physical device — a different Mac starting to relay it) as a false self-match forever, not just absorb the one real near-term loopback this field exists to filter. `broadcastAnnounce()` now clears it again ~2s after each broadcast (long enough for a genuine loopback, bounded so it can't persist past that).
- **`AppState.virtualTuner`** — the one shared `VirtualTunerService` instance. **One shared virtual device, not one per recording** — if two shows are recording on two different real tuners, the same virtual device's lineup simply grows to two channels rather than standing up two fake devices.
- **`AppState.activeVirtualTunerDeviceID`** — `nil` when nothing is recording; otherwise the currently-advertised fake `DeviceID`. As of 2026-09-03, `"FEED" + the source tuner's own last 4 hex digits` (`VirtualTunerService.relayDeviceID(sourceDeviceID:)` — the real tuner actually being relayed; same `FEED` sentinel prefix `makeDeviceID()`'s own random scheme uses, for one consistent brand across every DeviceID this app ever mints), falling back to that random scheme (`VirtualTunerService.makeDeviceID()`, distinct from the project's own unrelated `FFFF0001` fake EXTEND test device) only when no source device can be resolved. Not private: `WebServer`'s JSON route handlers read it directly to know whether to answer or 404. `MenuContent`'s own "FEED: N watching" header row (`docs/MenuContent.md`) is gated on this being non-nil, separate from the count itself below.
- **`AppState.relayRawViewerCount`, added 2026-09-04** — `@Published private(set)`, count of currently-connected outbound relay viewers on the raw-passthrough path only. `relayRawViewerConnected()`/`relayRawViewerDisconnected()` (the latter clamped at 0) are called by `WebServer.handleVirtualTunerStream` — connected right before each `streamGrowingFile(...)` call for a raw (non-transcoded) relay request, disconnected via that call's `onStreamEnded` closure once the stream actually ends (see `docs/WebServer.md`'s "Recording playback relay" section for `onStreamEnded`'s own mechanics). Both hops land on MainActor via `Task { @MainActor in ... }`, since `WebServer`'s `fileIOQueue`/`queue` aren't MainActor-isolated. Never touched by local Watch Now (`handleWatchRecording` doesn't pass `onStreamEnded`), so this counts only genuine outbound-to-another-machine viewers, not this Mac's own playback. Deliberately **not** unified with `VLCBridge.shared.transcodeViewerCount(showId:)` (the separately, already-correctly ref-counted transcode-viewer count) into one running total — `MenuContent` sums both only at display time, since each half already has its own correct source of truth.
- **`AppState.updateVirtualTunerPresence()`** — internal, not private (both `SettingsView` and `FirstRunWizardView` call it directly on a settings-toggle change, see "User-facing toggle" above). Starts/stops the service and (re)generates the ID whenever `isRecording && config.Virtual_tuner_relay_enabled` flips. The ID is deterministic per source tuner (see `relayDeviceID`'s own doc comment below), not fresh-per-restart — so it's reused across sessions on purpose, deliberately reversing this doc's own previous "never reused across a stop/start cycle" claim (see `relayDeviceID`'s doc comment for why that's now safe). Called from `startRecording(index:)`, `teardownRecordingState(index:alsoRebuildGrid:)`, `skipRecording(showId:)` (the last doesn't route through `teardownRecordingState`, so it needs its own call), `reattachRecordings()` (a relaunch — deploy, or "Keep Recording & Quit" — while a show is recording reattaches its curl process without going through `startRecording`, so without this call the relay would never start for it until an unrelated recording elsewhere happened to start/stop), and the two settings-toggle save paths above. When already active, a repeat call re-derives `baseURL`/`tunerCount` (via `WebServer.virtualTunerBaseURL(preferredInterface:)` and `state.recordingShows.count`) and passes them to `virtualTuner.start(deviceID:baseURL:tunerCount:)` again — which updates the UDP responder's advertised TLVs in place without a rebind or a new ID — so TunerCount stays accurate as a second/third show starts or stops recording after the relay is already up. Passes an `onBindResult` closure only on the fresh-start path: if the UDP bind actually fails (port 65001 already in use — another instance, or a real libhdhomerun-based tool), it backs `activeVirtualTunerDeviceID` out to `nil` again (and releases the web-server claim below) rather than leaving the HTTP JSON routes advertising a "live" relay no UDP client can ever discover. Also holds an `ensureWebServerRunning()`/`releaseInternalWebServer()` claim (the same refcounted internal-use mechanism `watchRecordingInApp` uses for the Watch Now relay, tracked in its own `virtualTunerWebServerClaimActive` flag) for as long as the relay is active — without it, the relay's HTTP JSON routes and stream endpoint would be unreachable (the underlying `NWListener` simply isn't running) whenever `Web_server_enabled` (Web LAN) is off and no other window happens to be using the internal server.
- **`AppState.recordableDevices`** — `devices.filter { !$0.isVirtualRelay }`. This is the one accessor essentially every device-facing list in the app builds from instead of raw `devices` — see the Guardrails section below for the (long, and still possibly incomplete — new call sites should default to this rather than raw `devices`) list of call sites. Single-device backstop checks on an already-known device (`addShow`/`updateShow`/`handleRecord`/`handleToggleFavorite`/`vlcOccupiesTuner`) check that device's own `isVirtualRelay` flag directly instead, and stay separate from this accessor — `addShow`/`updateShow`/`vlcOccupiesTuner` funnel through the shared `AppState.isVirtualRelayDevice(_:)` deviceId-keyed lookup rather than each re-deriving it; `handleRecord`/`handleToggleFavorite` already hold a resolved `HDHRDevice` from their own lookup and just read `.isVirtualRelay` off it directly. **Lineup fetch is the one deliberate exception** — `fetchAllLineups(for:)` and its callers (`refreshGuides`, the idle loop's Local-Network-confirm retry, `ensureLineupLoaded`) intentionally do NOT filter to `recordableDevices`: a relay device's own `/lineup.json` is exactly what feeds the "Recording on Another Mac" menu entry (see below), so fetching it is required, not a bug. Guide fetch is the opposite case — see Known limitation below.

## Wire protocol

UDP discovery request parsing mirrors `HDHRManager.swift`'s existing client-side `udpDiscoverSync` byte-for-byte, and matches `tools/mock_hdhr.py`'s own reference responder:

- Request (real client → this app, port 65001): `[0x00,0x02][len hi][len lo][TLV payload]` — validated as loosely as `mock_hdhr.py` itself (≥4 bytes, leading type `0x0002`), no TLV/CRC parsing required.
- Reply (this app → client, unicast): `[0x00,0x03][len hi][len lo][TLV payload][crc32 of everything before it, little-endian]`, TLVs in order: `0x01` DeviceType (`0x00000001` = tuner), `0x02` DeviceID (big-endian u32), `0x2A` BaseURL (ASCII, e.g. `http://10.0.2.100:1980`), `0x10` TunerCount (1 byte), `0x27` LineupURL (ASCII, `<BaseURL>/lineup.json`), and — only on `stop()`'s own final unsolicited broadcast, never a real reply to a real request — a trailing non-standard `0xF0` "goodbye" TLV (1 byte, value `1`). `0xF0` sits well outside the real protocol's own observed tag range above, so a real client just skips over it like any other unknown TLV; only this app's own `isGoodbye(fromReplyPacket:)` reader looks for it. See "Unsolicited FEED announces" above (Components) for what it's for.

**Corrected 2026-09-02** — the reply used to carry *only* the DeviceID TLV (14 bytes total, no DeviceType/BaseURL/TunerCount), on the theory that "real device metadata lives in `/discover.json` instead, per the real protocol's own division of labor." That theory was never verified against a real device and turned out to be wrong: a live discovery probe sent directly to a real EXTEND (`105404BE`) shows its actual DISCOVER_REPLY carries DeviceType/DeviceID/DeviceAuth/BaseURL/TunerCount/LineupURL TLVs, not just DeviceID. This app's own client (`HDHRManager.udpDiscoverSync`) never needed BaseURL from the UDP reply because it always went straight to the HTTP JSON routes for everything else — but a genuine third-party HDHomeRun client (Plex, Channels DVR, TVHeadend, SiliconDust's own apps) reads BaseURL from the UDP reply itself to know where the device's HTTP API lives. Without it, such a client has no way to learn this relay runs on a non-standard port (`Web_server_port`, default 1980, not the real protocol's usual 80) and either assumes port 80 (connection refused) or discards the reply outright — this is why the relay was invisible to real third-party discovery even though this app's own instances, and a direct `curl` of `/discover.json`, always worked fine. Fixed by adding the DeviceType/BaseURL/TunerCount/LineupURL TLVs to match the real shape; DeviceAuth (`0x2B`) is deliberately omitted — this relay has no such secret to advertise, it isn't a real tuner with cloud-guide access.

`VirtualTunerService.isDiscoverRequest(_:)`/`buildDiscoverReply(deviceID:baseURL:tunerCount:)` are the pure, unit-tested halves of this (`Tests/hdhr_VCRTests/Network/VirtualTunerServiceTests.swift`) — `handleReadable()` is just socket plumbing around them. `start(deviceID:baseURL:tunerCount:onBindResult:)` updates all three advertised fields in place on a repeat call while already bound (no rebind) — `AppState.updateVirtualTunerPresence()` relies on this to keep TunerCount current as shows start/stop recording after the relay is already up, not just at the moment it first comes up.

`makeDeviceID()` mixes this Mac's hostname (crc32) with a fresh random value on *every* call — the fallback path only, used when `relayDeviceID(sourceDeviceID:)` (below) has no source device to derive a stable ID from.

**`relayDeviceID(sourceDeviceID:)`, added 2026-09-03, explicit user request** — the primary path: `"FEED" + the source's own last 4 hex digits`, e.g. `105404BE` → `FEED04BE`, when a real tuner is actually being relayed (`AppState.updateVirtualTunerPresence()` passes `recordingShows.first?.hdhr_record`). **Not `"<sourceDeviceID>_Relay"`** — a first version of this literally appended `_Relay` to the DeviceID, but `VirtualTunerService.start(deviceID:)` parses this string via `UInt32(deviceID, radix: 16)` to build the real UDP wire protocol's binary DeviceID TLV (see "Wire protocol" above) — a `u32` has exactly 8 hex digits of room, full stop, and `_Relay` isn't valid hex, so `start()` rejected it outright and the relay failed to bind at all, caught live within minutes via `"invalid deviceID ... — not starting"` in the log, mid-recording (an active MLB Baseball recording at the time). A middle version tried a leaner `"FE"` 2-digit marker (to show 6 of the source's 8 real digits instead of 4) but was reverted the same day in favor of keeping the *same* `FEED` sentinel `makeDeviceID()`'s own random scheme already uses — one consistent "known-fake" DeviceID brand across everything this app ever mints, rather than two slightly different reserved prefixes. `FEED` spends 4 of the 8 available digits on that marker, leaving room for the source's own last 4 — the human-readable "which tuner" connection still lives primarily in `FriendlyName` (`"<source>-FEED"`, no hex constraint), this is just a bonus. Deterministic on purpose, replacing the fully-random-every-restart scheme this doc previously described: a fresh random ID minted on every relay restart (a plain relaunch, or just normal daily recording start/stop) left yet another now-permanently-unavailable `FEED####` entry behind in every other instance's device list, with nothing to ever clean it up — reported live after a dev machine relaunched repeatedly during testing had accumulated 18 such stale rows, none with a show ever assigned to any of them. Reusing the same ID across sessions is safe here specifically *because* it's now tied to a real, stable source tuner (whose own DeviceID never changes between sessions either) instead of being an arbitrary session marker — the original concern the random scheme guarded against (a client confusing a later, unrelated recording session for one it already knew about) doesn't apply when the ID means "the relay for tuner X" and X is genuinely the same tuner both times. Two Macs relaying the exact same real tuner ID at once would collide on this ID — accepted as unlikely, since a tuner only allocates one connection per recording, so normally only one machine is ever actually recording from a given real tuner at a time. See `AppState.probeForNewDevices()`'s stale-device pruning (`deviceUnavailableSince`/`staleDeviceForgetAfter`, `docs/AppState.md`) for the other half of the same fix — forgetting an unavailable device with no show assigned to it after a grace period, for devices (relay or real) that still end up stale despite the now-stable ID.

## HTTP routes

No second HTTP listener — everything is added to the existing `WebServer` on its existing port (`Web_server_port`, default 1980). `BaseURL` in `/discover.json` (and, since the above fix, in the UDP reply itself) is `http://<lan-ip>:<port>`, built by the shared `WebServer.virtualTunerBaseURL(preferredInterface:)` helper; a compliant client resolves everything through it plus `/lineup.json`'s own per-channel `URL`, so there's no protocol requirement to match a real device's port-80/5004 split.

All five routes below — the four JSON routes plus `/auto/v<channel>` itself — 404 the instant nothing is recording (`activeVirtualTunerDeviceID == nil`):

- **`GET /discover.json`** — `buildVirtualTunerDiscoverJSON(state:deviceID:)`: `DeviceID`, `FriendlyName`, `ModelNumber` ("HDVR-RELAY"), `BaseURL`, `LineupURL`, `TunerCount` (= number of currently-recording shows), `LocalIP`, plus the non-standard `HdhrVCRplusVirtualRelay: true` marker. A real client ignores an unknown field; this app's own `HDHRDevice` decodes it into `isVirtualRelay` (see that property's doc comment in `Models.swift`).

  **`FriendlyName` is `"<source device's own FriendlyName>-FEED"`, added 2026-09-03 as `"-Relay"`, renamed to `"-FEED"` 2026-09-04 alongside the rest of the user-facing "Relay"→"FEED" rename** — e.g. "HDHomeRun EXTEND-FEED" — so the relay reads as clearly related to the real unit it's relaying from in a third-party client's device list, per explicit request, rather than a generic, unrelated-looking label. Looked up via the currently-recording show's `hdhr_record` against `state.devices`; `HDHRDevice.FriendlyName` (`Models.swift`) is a new field added alongside this, decoded the same way `ModelNumber` already is — present from a real HTTP `/discover.json` fetch, absent (nil) from a UDP-only-discovered device with no FriendlyName TLV read. Falls back to the original generic `"hdhrVCRplus (Recording FEED)"` name when the source device's own name isn't known (a UDP-only source, or — rare, since a race is unlikely, but possible if nothing happens to be recording at the exact instant this is built) no show is currently recording at all.

  `FirmwareName`/`FirmwareVersion`/`DeviceAuth`, a second listener on the real tuning port (5004), and `ScanPossible:1`/`SourceList`/`/lineup.post` were all tried and reverted during the same 2026-09-03 Channels DVR investigation — see `FAILED_APPROACHES.md`'s "Channels DVR compatibility for the virtual-tuner relay" entry for the full trail and why each was backed out.
- **`GET /lineup.json`** — `buildVirtualTunerLineupJSON(state:)`: one entry per currently-recording show — `GuideNumber`, `GuideName` (looked up from the real lineup, falling back to the bare channel number if unavailable), `URL` (`.../auto/v<channel>?dev=<hdhr_record>`), plus the non-standard `HdhrVCRplusShowTitle` field carrying the real show title, `HdhrVCRplusTranscodeViewers` (omitted unless >0) reflecting an already-active remote transcode session, `HdhrVCRplusSignalQualityPercent` (added 2026-09-04, omitted when not yet known) carrying the *source* tuner's own estimated signal — see "Estimated signal for FEED consumers" below — and `HdhrVCRplusSourceHostname` (added 2026-09-07, always set — `ProcessInfo.processInfo.hostName`, unlike the other non-standard fields there's no "not yet known" case for this one) carrying this Mac's own hostname. `HdhrVCRplusShowTitle` is what lets a discovering instance's menu bar say "Recording on *\<title\>*" instead of just a channel number — see "Remote watch menu entry" below; `HdhrVCRplusSourceHostname` is what lets that same row also say *which* Mac, once more than one is relaying at once. **Added 2026-09-12**: `HdhrVCRplusEpisodeTitle`/`HdhrVCRplusEpisodeNumber`/`HdhrVCRplusSynopsis` (each omitted when empty) mirror `AppState.DiscordEpisodeSnapshot` exactly — the same per-show snapshot already captured once at "Recording Started" for Discord cards, reused here rather than a second capture mechanism, for the identical staleness reason (a live guide lookup can silently resolve to the wrong episode later in a recording's lifecycle once `scheduleNextAir` moves `show_next` on). `HdhrVCRplusImageURL` (omitted when empty) reuses `show.show_logo_url` — the channel logo, same as Discord's embed thumbnail, not a true per-episode image (this app has no such concept anywhere else). Together these are what let `VLCPlayerView`'s poster overlay show real show identity during a FEED session's buffering wait instead of a blank icon — see `docs/VLCPlayerView.md`'s own note. Returned as a top-level JSON *array*, matching the real protocol (not wrapped in an object). The `dev=` query param disambiguates two real devices that happen to share a channel number (e.g. two tuners fed from the same cable lineup) — without it, two simultaneous recordings on the same channel number would produce byte-for-byte identical URLs, and a remote viewer picking the second lineup entry would always resolve to the first show's video.
- **`GET /status.json`** — `buildVirtualTunerStatusJSON(state:)`: one `{"Resource", "VctNumber", "TargetIP", "SignalQualityPercent"}` row per currently-recording channel (the last omitted when not yet known — added 2026-09-04, see "Estimated signal for FEED consumers" below), returned as a top-level JSON *array* — matching the real device's own `/status.json` shape (`docs/HDHRFindings.md`, and this app's own client-side `[DeviceTunerInfo]` decode of it in `AppState.swift`), not wrapped in an object, same as `/lineup.json` above.
- **`GET /lineup_status.json`** — static `{"ScanInProgress": 0, "ScanPossible": 0, "Source": "Cable"}`.
- **`GET /auto/v<channel>?dev=<deviceId>&duration=<seconds>&transcode=<profile>`** — `handleVirtualTunerStream(channel:deviceId:durationSeconds:transcode:conn:)`: finds the show currently recording on `channel` (and, when `dev` is present, on that specific device — the same disambiguation `/lineup.json`'s own `URL` field carries; falls back to a channel-only match when absent, e.g. a hand-typed URL). With no `transcode` (or `none`), relays `show_recording_path` via the same `streamGrowingFile`/`pumpGrowingFile`/`handleGrowingFileChunk` pipeline the Watch Now relay uses (`docs/WebServer.md`), generalized with an optional wall-clock `deadline` derived from `duration` — the connection is closed once the deadline passes, matching the real device's own `duration=` behavior (`RecordingManager.swift`'s `streamURL`). With a real profile, routes to the headless transcode pipeline — see "Real transcode (Phase 2)" below — *unless* the on-disk recording is already a modern codec (H.264/HEVC), in which case it's relayed as-is regardless of the requested profile (see that section's "Already-modern-codec skip"). `duration=` is honored on the transcode path too, as of 2026-09-04 (see that section's own note) — `handleVirtualTunerStream` threads `durationSeconds` through to `beginTranscodeRelay`/`pumpTranscodeProxy` unchanged from what it already passed the raw-passthrough path.

  **Master-flag gate, fixed 2026-09-11** — unlike the four JSON routes above, this route had no `activeVirtualTunerDeviceID` check anywhere in its body until this fix: it only required a `Show` with `show_recording == true` matching the given channel/device. With `FEED_feature_enabled` off (the shipped default), a LAN client that already knew or guessed a `deviceId`+channel of a currently-recording show could still hit this route directly — including its `transcode=` path — even though the feature looked fully hidden everywhere else, defeating the master flag's whole purpose. Now guarded by the same `activeVirtualTunerDeviceID != nil` check (checked on `MainActor`, inside the same `Task { @MainActor in ... }` hop the rest of the handler already uses) before matching against `state.shows`.

  **Join-offset race, fixed 2026-09-11** — `streamGrowingFile` used to re-stat the recording file independently of the stat this function had already taken to compute the FEED join offset (`joinOffset`, at the time computed as `max(0, currentSize - feedLiveEdgeCushionBytes)` — simplified to plain `currentSize` once the cushion below was removed entirely). The gap between the two stats (a `FileHandle` open plus several `glog` calls) gave the file room to keep growing, so `streamGrowingFile`'s own `hasBacklog` check could flip true even though `joinOffset` was computed to land exactly on the live edge "by construction" — reintroducing the large-chunk burst-delivery pattern a prior live-tested fix eliminated. `streamGrowingFile` now takes an optional `knownFileSizeAtOffsetComputation` parameter; this call site passes its own already-known `currentSize` instead of triggering a second stat. `handleWatchRecording`'s local Watch Now relay, whose `startOffset` isn't tied to a fresh stat of its own, is unaffected — it still re-stats as before.

  **Live-edge cushion — tried 2026-09-08, disabled 2026-09-09, removed entirely 2026-09-13.** A one-time idea for the VLC stall below: join a new FEED viewer a fixed distance behind the recording's true current size (instead of exactly at the live edge), to give every byte a moment to settle on disk before the relay touched it. Live-tested twice, found to make the stall worse both times (VLC stopped progressing entirely once any backlog formed between the live edge and the cushion boundary) — direct thread-level evidence showed VLC's demux pipeline going idle despite continuous byte delivery, ruling out the disk-read-latency theory this cushion was built to test. Removed once the real fix (below) was found to live somewhere else entirely, making the cushion concept itself a proven dead end. Full trail: `issues_resolved.md`'s "VLC-side FEED playback stalls" entry.

### Diagnostic request logging

Added 2026-09-03 while debugging a real third-party client (an iOS HDHomeRun-client app) that discovered the relay but couldn't load channels — needed visibility into exactly what a real client requests, not just what this app's own client-side code expects. Two layers, both to the main log (`~/Library/Logs/hdhrVCRplus.log`, prefixed `[VirtualTuner]`), gated to the virtual-tuner surface specifically (not every request — this would be noise on top of normal guide/API traffic):

- **UDP**: every discovery request logged in `VirtualTunerService.handleReadable()` with the requester's IP:port and the DeviceID/BaseURL replied with.
- **HTTP**: `WebServer.isVirtualTunerHTTPPath(_:)` gates a request-arrival log in `accumulate()` (method, path, remote endpoint) before routing, so a malformed/unexpected path still shows up even if it never reaches a matching `case`. Each of the four JSON routes and `/auto/v<channel>` also logs its own outcome (200 with entry/tuner counts, or 404 with the reason) from inside `routeOnMain`/`handleVirtualTunerStream` — e.g. `/lineup.json`'s log line includes the actual channel numbers returned, so an empty-but-200 response is distinguishable from a 404.

### A device visible but with no channels: the actual bug found this way

The diagnostic logging above led straight to a real, currently-live bug, not a protocol gap: **`AppState`'s web server could fail to bind at all after a relaunch while a show was already recording**, leaving `VirtualTunerService`'s UDP responder (an independent bind on port 65001) up and answering — so a client could discover the device — while the HTTP listener on port 1980 was completely down, so every route including `/lineup.json` was connection-refused. Reproduced live on two consecutive `deploy.sh` runs while a real recording was in progress at each relaunch.

**Root cause**: two independent triggers could each call `webServer.start()` directly, back-to-back, at launch — `reattachRecordings()`'s call to `updateVirtualTunerPresence()` (which claims the internal web server via `ensureWebServerRunning()` when a reattached show is already recording) immediately followed, in the same launch sequence, by `setupWebServer()`'s own unconditional start when Web LAN is on. Both guarded only on `webServerRunning`, which doesn't flip `true` until `NWListener`'s *async* `.ready` callback lands — so both calls saw `false` and both called `webServer.start()`, which itself calls `stop()` then creates a fresh `NWListener`: two real binds racing the same port produced `POSIXErrorCode(48)` ("Address already in use") and left the loser's listener cancelled, taking the whole web server down with it (not just the virtual-tuner routes).

**Fix**: consolidated every caller (`setupWebServer`, `ensureWebServerRunning`, `releaseInternalWebServer`) behind one arbiter, `AppState.reconcileWebServerState()` — the only function that ever calls `webServer.start()`/`stop()` — guarded by a `webServerStarting` flag that closes the exact window `webServerRunning` couldn't. See `docs/AppState.md`'s table for the full before/after and the infinite-retry-loop pitfall hit and reverted while building this fix (re-reconciling from inside the start completion handler itself, rather than only from the four trigger points).

`lanIPAddress(preferredInterface:)`, `buildVirtualTunerDiscoverJSON`/`LineupJSON`/`StatusJSON` are internal (not `private`), same testability pattern as `buildGuideJSON` — see `Tests/hdhr_VCRTests/WebServer/VirtualTunerWebRoutesTests.swift`, which calls them directly with a synthetic `AppState` rather than spinning up a live `NWListener`.

## Guardrails

Three behaviors that must never regress — hard backstops and consistent filtering, not just UI-level polish:

1. **This instance must never discover its own virtual tuner.** `AppState.excludingOwnVirtualTuner(_:)` filters any discovered device whose `DeviceID` matches `activeVirtualTunerDeviceID` out of the result *before* it reaches `state.devices` — both `discoverDevices(knownHosts:attempts:)` and `probeForNewDevices()` route their `hdhrManager.discoverDevices(...)` results through it. Another instance's relay (a different `DeviceID`) is deliberately *not* filtered here — only self-exclusion is required.
2. **A relay tuner — this instance's own (should self-exclusion ever be bypassed) or another instance's — is watch-only, never schedulable.** `HDHRDevice.isVirtualRelay` is checked in `AppState.addShow(_:)` and `AppState.updateShow(_:)` (the two universal show-creation/edit funnels every caller — native wizard, web guide, `hdhr_guide` TUI — eventually goes through), refusing with a `glog` warning and no-op. `WebServer.handleRecord` also checks it directly, right after the device/channel lookup, so the web guide's Record modal gets a clear JSON error (`"This tuner is a temporary recording FEED..."`) instead of a silent no-op from `addShowFromGuide`. `WebServer.handleToggleFavorite` carries the identical guard, right after its own device/channel lookup, for the same reason — a discovered relay's fabricated lineup entries must not be forwarded to `hdhrManager.setFavorite` against a device that isn't real.
3. **A relay device must never be treated as a real, functioning tuner by anything that lists, polls, or measures tuners.** This is the broadest and easiest guardrail to miss piecemeal — every call site below builds from `AppState.recordableDevices` instead of raw `devices` specifically because an earlier pass of this feature added the accessor but missed most of them, discovered only by two full audit passes after the fact:
   - **Device pickers/lists**: `WebServer.buildDevBarHTML`'s tuner boxes, `buildHTML`'s `defaultDev` selection (both the fallback chain and its `count > 1` mode gate), `buildGuideGridHTML`'s per-device row loop (a relay's synthetic lineup entry can carry the *same* `GuideNumber` as the real channel it's relaying — in practice `entriesInWindow`'s own empty-guide-window guard already keeps a row from rendering for a device with no real guide data, but the loop is filtered too, as defense in depth), `buildNowJSON`'s `/api/now.json` entries, and `buildGuideJSON`'s device list + default-device fallback (feeds `hdhr_guide`'s Tab/switchDevice()); `MenuContent.swift`'s top-of-menu device-header loop and its four `Recording`/`Up Next`/`Scheduled`/`Paused` per-device-section `count > 1` gates; `WatchNowView`'s tuner `Picker` and its `selectedDevice`/`onAppear` fallbacks; `AddShowView`'s default-device fallback (both its `onAppear` path and its lineup-load `.task`); `SettingsView`'s "Measure Signal" device list; `FirstRunWizardView`'s onboarding discovery-status/prefetch code (including falling back to `.notFound` if a brand-new install's only discovered "device" turns out to be someone else's relay, rather than falsely reporting a real tuner was found).
   - **Background polling that would otherwise fail forever or pollute shared state**: `AppState.performFetchAllGuides`/`refreshGuides` skip guide fetch for a relay device entirely — it has no `DeviceAuth`/cloud guide relationship, so the fetch can only ever fail, and an unfiltered retry loop (`ensureGuideLoaded`, called every idle tick for any device with an empty guide) would eventually fire a real "Guide Load Failed" user notification/Discord embed naming a device the user never configured. `AppState.probeForNewDevices()` was the one guide-fetch call site that missed this filter — a newly-*discovered* relay device (as opposed to one already known) flowed straight into `guideStore.loadAll(devices: newDevices, ...)` unfiltered, firing a real (if harmless-in-practice) request against the relay's fabricated `LocalIP`/no-`DeviceAuth` identity. Live-caught 2026-09-06, fixed 2026-09-07 by filtering to `newDevices.filter { !$0.isVirtualRelay }` before that one call — `devices.append(contentsOf: newDevices)` and `fetchAllLineups(for: newDevices)` stay unfiltered, since a relay still needs to appear in `devices` and still needs its own `/lineup.json` fetched (see `AppState.recordableDevices`'s own "Lineup fetch is the one deliberate exception" note above). Exactly the kind of call site this guardrail's own preamble warns can be missed piecemeal — see `TODO.md`'s matching entry for the fuller planned fix (a minimal, locally-sourced guide for FEED consumers, so a discovering instance has *something* to show instead of just skipping the fetch). `AppState.startSignalScan()` excludes relay devices for a sharper reason: `ChannelSignalStore.key(for:)` keys signal history purely by (trimmed/lowercased) `GuideName`, not by device — scanning a relay's synthetic lineup entry (whose `GuideName` is copied verbatim from the real channel it's relaying) polls a `/status.json` that never reports `SignalQualityPercent`, so every one of its channels falls into the "never locked" branch and would overwrite the *real* channel's signal history with a bogus 0% reading purely because a same-named channel happened to be relayed elsewhere on the LAN at scan time.
   - **The watching side**: `AppState.vlcOccupiesTuner(for:)` has the matching guard — a relay device must never register as tuner-occupied even while its stream is being watched via `watchRemoteRelay`, since `VLCBridge.play(url:)`'s relay-URL detection only recognizes the local `/api/watch-recording` shape, not a remote relay's `/auto/v<channel>` URL (which is intentionally the *same* shape a real tuner's own live stream uses, so it can't be used to distinguish the two). `AppState.releaseAssertionsIfIdle()` similarly excludes relay devices from its "any tuner active" check — a remote Mac's own relay occupancy must never keep this instance's sleep-prevention assertions held. `watchInApp`/`watchRecordingInApp`'s own `?? devices.first` fallbacks (used when an explicit device lookup fails) were also hardened to `recordableDevices.first`, so a defensive fallback can't silently pick a relay either.

Regression coverage: `Tests/hdhr_VCRTests/AppState/VirtualTunerGuardrailTests.swift` (self-exclusion, addShow/updateShow refusal, `vlcOccupiesTuner`'s relay guard) and `VirtualTunerWebRoutesTests.swift`/`VirtualTunerGuideGridTests.swift` (`handleRecord_refusesRecordingAgainstAVirtualRelayDevice`, `devBarHTML_excludesAVirtualRelayDevice`, the `lineup.json` device-disambiguation tests, the guide-grid row-exclusion test). The SwiftUI-only call sites (`WatchNowView`/`AddShowView`/`MenuContent`/`FirstRunWizardView`/`SettingsView`) and the background-polling exclusions (`performFetchAllGuides`/`refreshGuides`/`startSignalScan`) have no dedicated unit tests — verify manually per the Verification section below.

## Remote watch menu entry

`MenuContent.swift`'s menu builds a `remoteRelayEntries` list from `state.devices.filter { $0.isVirtualRelay }` (guaranteed to exclude self, per Guardrail 1 above) crossed with `state.lineups[deviceId]` entries carrying a non-nil `virtualRelayShowTitle` (the `LineupEntry` field decoded from `HdhrVCRplusShowTitle` — reuses the existing lineup-fetch pipeline, `HDHRManager.fetchLineup`, rather than a separate cache). Each becomes a "Recording on *\<title\>* — *\<hostname\>*" row (the hostname suffix from `LineupEntry.virtualRelaySourceHostname`, omitted if somehow absent) in a "Recording on Another Mac" section, alongside the existing "Recording Now" section. Clicking one calls `AppState.watchRemoteRelay(url:title:device:)`, which opens a native VLC window directly against the relay's stream URL via `VLCPlayerWindowManager.shared.open(url:title:device:appState:)`.

`watchRemoteRelay` is deliberately **not** `watchInApp` reused: `watchInApp`'s `tunerAvailable` gate protects a real device's limited physical tuner count, which doesn't apply to a relay stream (unlimited concurrent viewers is the whole point — see the Context section above), and its guide-entry-driven sleep-prevention has no local guide entry to key off for a remote device's synthetic channel.

**H.264 option, added 2026-09-04** — the menu offers a second `"Watch (H.264)"` item alongside the plain `"Watch"` one, whenever the source isn't already a modern codec (same `MPEGVideoStreamType.isAlreadyModernCodec(_:)` check `sourceIsAlreadyModernCodec` uses server-side). It calls the same `watchRemoteRelay`, just with `&transcode=auto` appended to the entry's `URL` — any non-empty, non-`"none"` string is enough to request transcoding at all (`WebServer.effectiveTranscodeProfile`'s `wantsTranscode`); the *level* is never up to the requester, it's always the remote Mac's own configured "Default transcode level" (Settings → Sharing → Recording FEED). This is the same shape every viewer of the relay already goes through — `docs/VirtualTunerService.md`'s "Real transcode (Phase 2)" section's sharing model applies identically whether the request came from this app's own menu or a real third-party client.

The row disappears the moment the remote show stops recording — the remote instance's `/lineup.json` naturally stops listing that channel, and the local lineup-fetch cache reflects that on its next refresh like any other lineup change.

**In-player raw/H.264 toggle and auto-play, added 2026-09-04** — this same raw-vs-H.264 choice, and the poster's Start click, no longer have to be decided at menu-click time: see `docs/VLCPlayerView.md`'s "Auto-play for a remote FEED session" and its Toolbar Layout's `[☑ H.264]` toggle. The toggle reconnects via `VLCBridge.play(url:)` with `&transcode=auto` added/removed from the same canonical entry `URL` the menu items above already use, so both entry points (menu click at open time, in-player toggle mid-session) end up requesting the exact same shape of URL and go through the identical server-side `wantsTranscode`/configured-default-level logic.

**Closed captions, checked 2026-09-04** — a **raw** FEED carries the source's embedded EIA-608/708 captions through untouched (byte-identical passthrough), and the in-app player's existing CC picker (`docs/VLCPlayerView.md`'s own CC picker section) needs no FEED-specific change to support it — confirmed live by pointing VLC directly at a running FEED URL and seeing it detect and add CC tracks the same way it would for a live channel. A **transcoded** FEED does not carry captions — VLC's own `x264` stream-out module (the one this app's transcode path uses) has no exposed option for A/53 caption passthrough, so they're silently dropped during the MPEG-2 decode → H.264 encode step (`mediainfo`-confirmed: 0 Text tracks in transcoded output vs. 6 in the untouched raw file for the same source). The player's CC picker already degrades correctly for this — `bridge.spuTracks` is genuinely empty for a transcoded session, so the picker just doesn't appear, rather than offering a control with nothing to switch.

**Estimated signal for FEED consumers, added 2026-09-04** — the "Recording on Another Mac" submenu also shows a "Signal: N%" line (`MenuContent.swift`, right below the existing "Transcoding: N viewers" line) reporting the *source* Mac's own real tuner signal for the show being relayed — deliberately built without any new HTTP route or new polling. The value already existed on the source side (`AppState.deviceTunerOccupancy`, continuously refreshed every idle tick against the real device for this instance's own tuner-occupancy math) and both existing routes above now surface it: `/status.json`'s new `SignalQualityPercent` field reuses the real HDHomeRun field name real client software already expects there, while `/lineup.json`'s new `HdhrVCRplusSignalQualityPercent` is what this app's own consumer actually reads — relay devices are deliberately excluded from the regular device-occupancy poll loop (Guardrail 3 below), so nothing already fetches a relay's own `/status.json`, and `/lineup.json` is the one endpoint already continuously fetched for a relay device (the deliberate `recordableDevices` exception, see `AppState.recordableDevices`'s own doc comment) — piggybacking there needed no new fetch on the consuming side either. `WebServer.liveSignalQualityPercent(for:state:)` is the one shared lookup (Resource-header-first, `VctNumber`-fallback match — the same precedent `AppState.fetchDeviceStatusUncached`'s own `vstatus` lookup and `teardownRecordingState`'s tuner-clear match already use) both routes' builders call, so the two never drift. Nil/omitted (not shown, not "0%") whenever the source device hasn't been polled yet or its tuner isn't currently locked — same "field present means known" convention `HdhrVCRplusTranscodeViewers` already uses.

## Client-side local relay (viewer-Mac side)

**Added 2026-09-12, simplified to an in-memory proxy the same day** once the fix was confirmed live (`issues_resolved.md`'s "VLC-side FEED playback stalls" entry has the full trail). `watchRemoteRelay` and the in-player raw/H.264 toggle (`VLCPlayerView.toggleFeedTranscode`) no longer hand VLC the remote Mac's `/auto/v<channel>` URL directly. libvlc's own PCR/clock-sync recovery logic only ever loses its reference clock (`ES_OUT_SET_(GROUP_)PCR is called too late` → `no reference clock` → full rebuffer) on a genuine cross-machine network read — the identical relay code has been repeatedly confirmed to play flawlessly forever over loopback, including in stock, unmodified VLC.app with zero app code involved. This inserts a relay on the viewer side to insulate libvlc from that network read entirely, and to smooth the remote source's own bursty delivery cadence before VLC ever sees it (the actual fix — see `FeedRelayProxyDelegate` below).

**First implementation (2026-09-12 morning) was disk-backed**: a puller curl wrote the remote Mac's FEED bytes to a local temp file, re-served to VLC over loopback via the same `streamGrowingFile`/`pumpGrowingFile` mechanism Watch Now uses. That confirmed the pacing fix worked, but turned out to be more machinery than needed — this file already has a proven pattern for "stream one HTTP source straight through to a viewer, in-process, no disk" (`pumpTranscodeProxy`/`TranscodeProxyDelegate`, used by the real-transcode relay below), so the same afternoon the disk round-trip was replaced with an in-memory version of that pattern, pacing added:

- **`WebServer`'s session registry** — `registerFeedRelaySession(id:remoteURL:)`/`unregisterFeedRelaySession(id:)`, an opaque-id-keyed `[String: String]` dictionary (session id → remote FEED URL, `NSLock`-protected, same pattern as `inFlightRequestTasks`). Never a raw client-supplied URL — same posture as `/api/watch-recording`'s `show=<id>` server-side lookup (no auth beyond LAN-subnet matching, CLAUDE.md).
- **`GET /api/feed-local-relay?session=<opaque-id>`** — `handleFeedLocalRelay` looks up the session's remote URL and calls `beginFeedRelayProxy`, which opens an in-process `URLSession` request to it and forwards bytes straight through to VLC's `NWConnection` via `FeedRelayProxyDelegate` — mirroring `beginTranscodeRelay`/`pumpTranscodeProxy`'s exact shape (retry-before-any-data for a transient "remote not answering yet," a periodic liveness probe for a viewer that vanishes without a clean TCP close). Special-cased in `accumulate()` alongside `/api/watch-recording`, for the same reason: it needs the raw `NWConnection`, not a `WebResponse`.
- **`FeedRelayProxyDelegate`** — the one piece `TranscodeProxyDelegate` didn't need: delivery pacing. libvlc's own sout httpd (`TranscodeProxyDelegate`'s source) is already correctly real-time-paced, so that delegate forwards `didReceive` chunks immediately; the remote FEED URL's delivery over a real network hop is *not* already smooth, so this delegate buffers incoming chunks in memory and drips them out via `drainIfNeeded()` — holding bytes back just long enough that cumulative delivery tracks a steady real-time pace (observed rate = a running average of real byte arrivals, no periodic file-stat sampling needed since every byte's arrival is already a direct event) plus 0.5s of lookahead slack, instead of forwarding whatever burst the network just delivered.
- **`AppState.startFeedLocalRelay(remoteURL:device:) -> String`** — the one place that wires the above together: unregisters any previous session on this player window, generates a fresh `<deviceId>-<uuid>` session id (the UUID so switching raw↔H.264 or re-watching never aliases two different sessions onto one id), registers it, and returns `http://127.0.0.1:<port>/api/feed-local-relay?session=<id>` for VLC to open. No pre-flight wait needed (unlike the disk-backed version) — a bad remote URL/host surfaces the same way `beginTranscodeRelay`'s own connect failures do, via the delegate's retry-then-give-up path, not a separate check here.
- **`VLCPlayerWindowManager.currentFeedRemoteURL`/`currentFeedSessionId`** — once `VLCBridge.play(url:)` is fed the local relay URL, `bridge.currentURL` no longer *is* the remote URL, which broke several places that used to match against it directly for a virtual-relay device: `VLCPlayerView.currentFeedEntry`/`feedIsTranscoding`/`inferredCodecs`/`syncChannel(to:)` all now substitute `currentFeedRemoteURL` in place of `bridge.currentURL` when `device.isVirtualRelay`. Set by `startFeedLocalRelay` right before it hands back the local URL; cleared in `playerWindowDidClose()` (just unregistering the session — the proxy delegate's own cleanup fires from the resulting `conn.cancel()`, no separate process or temp file to tear down).
- **`VLCBridge.play(url:)`'s `isRecordingRelay` check** broadened to `url.contains("/api/watch-recording") || url.contains("/api/feed-local-relay")` so a FEED session gets the same 300ms loopback network-caching value as Watch Now, instead of the 2000ms live-stream value it would otherwise fall into now that it's a loopback read too.
- **No disk involved at all** — no puller process, no temp files, no orphan sweep at startup. A `catchUpToLive` reconnect also no longer replays a growing backlog from byte zero (the old disk-backed design's own known quirk): each new proxy connection starts fresh at the remote's own live edge, since there's no local file accumulating history to seek into.

## Real transcode (Phase 2)

**Implemented and live-verified 2026-09-02** — `Tests/hdhr_VCRTests/WebServer/VirtualTunerLiveStreamTests.swift` passed against a real HDHomeRun device and a real over-the-air recording (`RUN_VIRTUAL_TUNER_LIVE_TESTS=1`): raw passthrough serves byte-identical content, and `?transcode=mobile` genuinely produces H.264 (confirmed via `mediainfo`, not just "some bytes came back"). Requesting a real `transcode` profile on `/auto/v<channel>` routes to a headless libvlc encode instead of raw passthrough — **the actual profile used comes from `config.Virtual_tuner_relay_default_transcode` (Settings → Sharing → Recording FEED → "Default transcode level," added 2026-09-03), not the viewer's own requested profile string.** A viewer's `?transcode=<anything-non-empty-non-"none">` only decides whether to transcode at all (`WebServer.handleVirtualTunerStream`'s `wantsTranscode`); once that's true, the admin-configured level always wins, per explicit user direction — a natural fit given the sharing model below already collapses differing per-viewer profile requests into whichever one happens to be running. The Settings picker offers all seven real, EXTEND-only profile names — `heavy`/`internet720`/`internet540`/`internet480`/`internet360`/`internet240`/`mobile` (sourced from the original AppleScript app's 2016+ production list plus SiliconDust's current `info.hdhomerun.com/info/http_api` docs, which dropped `internet720` in favor of `internet540` at some point — kept in the set since a live device still honors it directly) — defaulting to `"heavy"`.

- **Input**: a `VLCBridge.TranscodeSession`'s own independent `libvlc_media_player_t` (never the on-screen `mediaPlayer` singleton — no drawable/NSObject is ever set on it, so libvlc allocates no real vout) plays `http://127.0.0.1:<port>/api/watch-recording?show=<id>&start=0` — this app's own existing growing-file HTTP relay, **not** a `file://` path. `VLCBridge.play(url:)`'s own doc comment explains why: VLC's plain `file://` access module snapshots a file's length at open time and won't read past it on a growing file, which would stall a transcode input exactly the way it would on-screen playback.
- **Sout chain** (`libvlc_media_add_option`, the same call the on-screen player already uses for its own options): `sout=#transcode{vcodec=h264,vb=<kbps>,acodec=a52,ab=128,channels=2}:std{access=http,mux=ts,dst=127.0.0.1:<port>/relay}`, plus two separate media options `sout-x264-keyint=30`/`sout-x264-min-keyint=30` (x264's own global advanced config keys, not fields the `transcode{}` chain syntax itself recognizes — see the GOP note below for why they're separate) — output stays MPEG-TS-wrapped (`mux=ts`, matching this endpoint's `Content-Type: video/mp2t` and every other HDHomeRun-shaped consumer's expectation), only the *video* codec changes from MPEG-2 to H.264. **No `scale=`/`width=`/`height=`/`fps=` at all, deliberately** — per an explicit user request, every profile keeps the source's own frame rate and dimensions regardless of which one is requested; bitrate (`VLCBridge.transcodeBitrateKbps(for:)`, a first-pass guess for all seven recognized profiles — see that function's own doc comment for the full ladder — not a measured/tuned spec) is the *only* thing that varies by profile now. Real tradeoff, not an oversight: a `mobile` request at 400kbps against a full-resolution 1080i/720p source looks considerably blockier than the same bitrate would at a genuinely reduced resolution. Live-verified 2026-09-02 (`VirtualTunerLiveStreamTests.swift`'s `relayTranscodesToH264WhenAProfileIsRequested`): output width/height/frame rate probed via `mediainfo` and confirmed to match the source exactly. `channels=2` is a separate, earlier live-caught fix: a real over-the-air 5.1 source silently produced a video-only transcode with no audio at all — the audio encoder only supports up to 2 channels and drops the audio track entirely rather than erroring loudly when fed 5.1. Every relay profile is a low-bandwidth target anyway, so forcing stereo is the right call regardless, not just a workaround. **`acodec=a52` (AC-3), not `mpga` (MPEG Layer 2) — changed 2026-09-04, per explicit user request**: an AC-3 broadcast source stays AC-3 end to end instead of a second lossy re-encode to a different codec, and every real HDHomeRun-based client already decodes AC-3 natively as the standard ATSC audio codec, so there was no compatibility reason to change codec, only bitrate/channel-count. Live-verified 2026-09-04 against a real dual-language (5.1 English + stereo Spanish) recording: libvlc's `avcodec` encoder module reports "found encoder A52 Audio (aka AC3)" and both tracks downmix cleanly to 2-channel 128kbps AC-3 (mediainfo-confirmed) — same shape `mpga` produced before, just AC-3 instead of MP2. **`sout-x264-keyint=60`/`sout-x264-min-keyint=60`, added 2026-09-04** — found by comparing `mediainfo` output for this transcode against a real over-the-air H.264 channel's own broadcast encode side by side: the real broadcast keeps a keyframe every ~1s ("GOP M=4, N=30" at 29.97fps), while x264's own untouched default (`keyint=250`) left a 59.94fps source ~4.2s between keyframes — long enough that a viewer joining the FEED transcode mid-stream, or scrubbing, has to wait up to that long for the next IDR before anything decodes. **First attempt put `keyint=60,keyint_min=60` directly inside the `transcode{}` chain string — confirmed live not to work** (mediainfo still showed the untouched x264 default 250/25 afterward): those aren't fields the `transcode{}` module itself recognizes, they're x264's own global advanced config options (`vlc -p x264 --advanced --help-verbose` → `--sout-x264-keyint`/`--sout-x264-min-keyint`). **Second attempt — passing them as their own separate per-media `libvlc_media_add_option` calls (the same mechanism `soutOpt`/`sout-keep` above use) — also confirmed live not to work**, silently no-op'ing the same way: only the global-instance form, set once in `libvlc_new()`'s own argv (`VLCBridge.swift`'s init, not `startTranscodeSession`), actually changes the emitted GOP — re-verified live to actually change the output GOP this time. `startTranscodeSession` deliberately does not re-add these two keys as per-media options; doing so is dead weight at best, since only the global-argv form takes effect. The frame count isn't a per-source frame-rate lookup (the actual source fps isn't known before this sout chain is built, and probing it would need a real decode/SPS-parse this function doesn't otherwise do) — it's a fixed frame count picked to land close to real broadcast's own cadence across realistic frame rates. `min-keyint=N` is a request, not a guarantee — x264 still auto-clamps it down somewhat (`scenecut` stays enabled at its own default and wants room to insert an early scene-cut IDR), which only tightens the join-latency win further, never loosens it.

**Tightened 60 → 30, 2026-09-04, per explicit user request** — deliberately *tighter* than real broadcast's own ~1s cadence now (0.5s at 59.94fps, 1.0s at 29.97fps, down from 1.0s/2.0s), not just matching it. Rationale: a FEED transcode session is shared across every viewer of that show (`TranscodeSession` ref-counting, see "Sharing/lifecycle" below) — only the viewer whose request actually *creates* the session gets a guaranteed fresh IDR as frame one; every subsequent joiner connects mid-stream, at whatever GOP phase the already-running encode happens to be in, and VLC's `std{access=http}` output module has no per-client keyframe-alignment logic (checked directly — `vlc -p mux_ts --advanced --help-verbose` has no such option) — a joiner gets the live byte stream as-is and must wait for the next scheduled IDR regardless. So for most FEED viewers, the keyframe interval *is* the worst-case join latency, not just a nice-to-have. Cost is bitrate pressure, not size: `vb=<kbps>` targets a fixed average bitrate, so the rate controller absorbs the ~doubled I-frame frequency by very slightly raising QP (mostly on the P-frames between them) rather than growing the output — a small, likely-imperceptible quality dip at these already-modest relay bitrates, not a bigger stream. **Live-verified 2026-09-04** against a real HDHomeRun device (105404BE) and a real airing (5 Eyewitness News Midday, `heavy` profile): captured ~9s of the actual transcoded output via `curl .../auto/v5.1?dev=105404BE&transcode=heavy`, confirmed via `mediainfo --Full`'s x264 encoding-settings string — `keyint=30 / keyint_min=16 / ... rc=abr / bitrate=6000` — proving the new value actually took effect (not silently ignored the way the first `transcode{}`-inline attempt was) and giving the real auto-clamped `keyint_min` (16, not a guess — the equivalent clamp for the original 60/60 setting was only ever estimated at "~31"). Source was 59.94fps, so 30-frame keyint measures out to the predicted 0.5s. Measured actual video bitrate 5,586kb/s against the 6,000kb/s nominal target — confirms the "cost is quality, not size" reasoning above empirically, not just theoretically: the stream stayed near its target bitrate rather than growing.
- **Output serving**: libvlc's own `std{access=http}` sout module runs a tiny httpd bound to `127.0.0.1` only (never `0.0.0.0`) on one of a small fixed port range (`19810...19819` — ten concurrent distinct shows being transcoded at once, far beyond realistic use). `WebServer.pumpTranscodeProxy` connects to it as an HTTP client (`URLSession.bytes(for:)`-style streaming) and forwards every chunk straight out to the real external `NWConnection` as it arrives. `beginTranscodeRelay`'s own response to that external viewer sends `Connection: close`, not `keep-alive` (changed 2026-09-07, same rationale as `streamGrowingFile`'s identical fix, `docs/WebServer.md` — no `Content-Length` on an open-ended stream means "read until close" is the only valid framing per RFC 7230 §3.3.3).
- **Sharing/lifecycle**: one `VLCBridge.TranscodeSession` per **`showId` alone** — not per `(showId, profile)` pair, as it was originally built — reference-counted by concurrently-connected external viewers (`startTranscodeSession`/`stopTranscodeSession`) — mirrors Phase 1's "N viewers, one relay" model instead of spending a transcode per viewer. **Changed 2026-09-03, per explicit user direction**: since every profile already produces the source's own dimensions/frame rate and only bitrate differs (see the sout-chain bullet above), "transcode" itself doesn't mean anything more specific than "give me H.264" — there's no reason two viewers of the same show should pay for two separate decode+encodes just because they happened to pass different profile strings. Whichever profile actually started the running session wins for every later joiner, even one that requested a different profile — `TranscodeSession.profile` records which one that is, and `startTranscodeSession` logs clearly (`"requested profile=X differs from running profile=Y, which wins"`) whenever a join's requested profile doesn't match, rather than silently ignoring the mismatch. Live-verified 2026-09-03 (real deployed instance, real recording): a `mobile` request started a session; a concurrent `heavy` request for the same show joined it (`refs=2`) instead of starting its own. `AppState.teardownRecordingState`/`skipRecording` call `VLCBridge.shared.stopAllTranscodeSessions(showId:)` unconditionally on recording stop, regardless of ref count, so a session can never outlive its recording — now a direct dictionary removal by `showId` rather than a prefix scan over multiple profile-suffixed keys, since at most one session can exist per show.
- **Startup race**: libvlc's sout httpd only actually starts accepting connections once the input/decode/encode pipeline finishes initializing after `play()` returns, not immediately — `beginTranscodeRelay` waits out a fixed ~0.6s grace period after a *freshly-created* session (`TranscodeSession.startedAt`) before its first proxy connection attempt; an already-running (joined) session skips the wait. Confirmed sufficient in live testing, but still a fixed guess, not an event-driven readiness signal — a slower machine or heavier source content could in principle need longer.
  **Hardened 2026-09-06** — `pumpTranscodeProxy` no longer gives up after that single attempt: `TranscodeProxyDelegate` now distinguishes a dataTask that errors out having *never delivered a single byte* (the sout httpd almost certainly wasn't listening yet) from a genuine end/failure after real data was already flowing, and only the former retries — up to 4 more attempts, 0.5s apart, on the same session/delegate (so the liveness probe and `?duration=` deadline, both tied to that one delegate instance, aren't duplicated per attempt) — before actually tearing the connection down. Buys up to ~2s of extra headroom past the initial 0.6s guess for exactly the "slower machine/heavier content" case this note already flagged. Not yet live-confirmed against a real slow-start (the 0.6s grace period has never actually been observed to be insufficient) — this is a defensive hardening pass, not a fix for an observed failure.
  **Threading fix, 2026-09-07 code review** — `TranscodeProxyDelegate`'s normal-completion path (`urlSession(_:task:didCompleteWithError:)`'s `else { finishOnce() }` branch — a clean stream end, or a real error *after* data already flowed) called `cleanup()` directly from URLSession's own private delegate queue, unlike the "never delivered a byte" retry branch right above it, which explicitly hops onto `targetQueue` first (with a comment explaining exactly why: this delegate's callbacks don't run on `WebServer.queue`). No observed crash — everything `cleanup()` touches is independently thread-safe — but a real discipline inconsistency, now fixed to match its sibling.
- **Already-modern-codec skip**: some channels genuinely broadcast H.264 (or, in principle, HEVC) already, not MPEG-2 (`docs/HDHRFindings.md`'s `none` profile note: "Raw stream, no transcode (MPEG-2 or H.264 as broadcast)") — not a theoretical edge case: live-verified 2026-09-02, 15 of 112 channels on a real device reported `VideoCodec: "H264"`, not `"MPEG2"` (see `docs/HDHRFindings.md`'s "`/lineup.json` carries per-channel `VideoCodec`/`AudioCodec`" finding — an earlier pass of this doc incorrectly claimed no such field exists; it does). Re-encoding an already-modern source would spend CPU for a real quality loss with no format benefit, so `handleVirtualTunerStream` checks two ways, fast path first: `LineupEntry.VideoCodec` for the show's channel (an in-memory lookup against `state.lineups`, no disk I/O — string form, checked via `MPEGVideoStreamType.isAlreadyModernCodec(_ videoCodec: String)`) when present; when it's `nil` (older firmware, or this app's own synthetic virtual-relay lineup entries, which never set it), falls back to `mpegTSVideoStreamType(inFileAt:)` (`CompatibilityHelpers.swift`), which parses the on-disk recording's own PAT+PMT for the video elementary stream's `stream_type` byte (`0x02`/`0x01` = MPEG-1/2, `0x1b` = H.264, `0x24` = HEVC — the same byte values `docs/HDHRFindings.md`'s live-captured findings and `TranscodeStreamFormatTests.swift`'s fixtures already established, checked via the byte-taking overload of `isAlreadyModernCodec`). Either way, if the source is already modern, the request is relayed as-is (the same `streamGrowingFile` path a `transcode=none`/absent request takes) instead of spinning up a real `TranscodeSession`.

**Verified this session, live, against a real tuner** — `VirtualTunerLiveStreamTests.swift` has four tests, all passing against a real HDHomeRun device: raw passthrough (byte-identical relay of a real captured channel), real transcode (an MPEG2-reporting channel genuinely re-encoded to AVC via `mediainfo`, with a surviving stereo audio track), the already-modern-codec skip (a real H264-reporting channel — one of the confirmed channel-21 subchannels — requested with `?transcode=mobile` came back byte-identical to the raw capture, proving no re-encode happened, not just "the output still says AVC"), and (added 2026-09-05) a raw-socket consumer-stall regression test — see below. Cross-profile session sharing (two concurrent viewers of the same show requesting *different* profiles correctly joining one session, per the 2026-09-03 sharing-key change above) was also live-verified against the real deployed app, via the server's own request log.

**Sustained/long-running sessions — verified live 2026-09-05**, closing the "not yet verified" gap noted above until then. Two real, concurrently-recording channels were each relayed to a plain `curl` client for a full 30 minutes (1.16GB and 830MB delivered) while `growingFileSendTimeout`'s removal (see `docs/WebServer.md`'s `sendWithTimeout` entry) was live in place. Both full captures came back **byte-for-byte identical** to the source recording file over their entire length (verified by aligning each capture against the exact corresponding source offset and comparing every byte) — zero drops, corruption, or reordering — and the app log showed zero server-initiated forced disconnects the whole 30 minutes: one channel's relay connection closed itself gracefully only when the underlying recording legitimately ended (`"recording finished, drained 8654348256 bytes — closing stream"`, at the real broadcast's own scheduled end time), the other ran the complete, uninterrupted 30 minutes on its original connection until the test's own client closed it. This is what a "the relay doesn't work" report caught live the same day actually was: `growingFileSendTimeout` (originally 15s, then 60s) forcibly disconnecting a perfectly healthy connection every 15-30s because a real remote viewer's own player legitimately stops draining its socket for a stretch — see `docs/WebServer.md`'s `sendWithTimeout`/`growingFileNoTimeout` entry for the full fix.

**`?duration=` on the transcode path, added 2026-09-04**: `pumpTranscodeProxy` now takes the same `durationSeconds` `handleVirtualTunerStream` already threads to the raw-passthrough path, and schedules a single `queue.asyncAfter` timer at that offset that calls `TranscodeProxyDelegate.notifyFinished()` (the same once-only cleanup path a real send failure or the local httpd closing already triggers) once it fires — guarded by `!delegate.isFinished` so it's a no-op if the connection already ended on its own first. Unlike `pumpGrowingFile`'s own deadline (checked once per recursive chunk-read), this path is event-driven off `TranscodeProxyDelegate`'s `didReceive` callbacks with no per-chunk hook to piggyback on, hence the standalone timer instead of a threaded `deadline: Date?`. Unverified live (no `RUN_VIRTUAL_TUNER_LIVE_TESTS=1` run performed for this specific change) — logic-verified by mirroring the raw path's own already-live-verified deadline shape.

**Known gaps**: `libvlc_release` (releasing the whole `libvlc_instance_t`, not just a session's own media/player) is never bound in `VLCBridge.swift` at all — irrelevant here since the instance is process-lifetime shared with the on-screen player anyway, same as before this feature existed.

`Tests/hdhr_VCRTests/WebServer/VirtualTunerLiveStreamTests.swift` is the live proof of the above (real recording → raw stream connects and matches; real recording → transcoded stream's bytes probe as `AVC`/H.264 with a surviving stereo audio track, not `MPEG Video`/no-audio). Gated behind `RUN_VIRTUAL_TUNER_LIVE_TESTS=1`; needs a real, reachable (non-relay) HDHomeRun device on the LAN with a free tuner (briefly tunes one of its tuners, ~7s, to capture a genuine sample — deliberately not a synthetic test pattern, since a real codec-change assertion needs real decodable content) and `mediainfo` on `PATH` (test-only tool, `brew install media-info`, never shipped in the app). `relaySurvivesAConsumerThatStopsReadingForOverAMinute` (added 2026-09-05, regression guard for the `growingFileSendTimeout` removal above) needs no extra tool — a raw POSIX socket (same idiom `WebServerTests.swift`'s `rawRequest` already uses) deliberately stops calling `recv()` for 75s while a background loop keeps the source file growing fast enough to genuinely fill the kernel's TCP buffers, then asserts every byte received before and after the stall matches the known repeating pattern in order.

## Known limitation

The relay reads from the growing file on disk (same mechanism as Watch Now), so it's inherently a few seconds behind true live — not real-time. This applies to both the raw and transcoded paths (the transcode's own input is that same growing-file relay). The client-side local relay above adds a second, much smaller lag on top for a FEED viewer specifically — `FeedRelayProxyDelegate`'s own pacing lookahead (0.5s) — not a second growing-file relay's worth, since the in-memory version added 2026-09-12 has no disk hop of its own to add the same multi-second lag the source side has.

A discovered relay device never gets a real EPG on the discovering instance — `guideByDevice[relayId]` never populates, by design (see Guardrails above). This is invisible in normal use (the relay is never listed as a pickable tuner anywhere a guide would be shown), but worth remembering if a future feature ever wants to show more than the handful of per-show extras `/lineup.json` already carries (`HdhrVCRplusShowTitle`, `HdhrVCRplusTranscodeViewers`, `HdhrVCRplusSignalQualityPercent`, `HdhrVCRplusSourceHostname`, and — added 2026-09-12 — `HdhrVCRplusEpisodeTitle`/`HdhrVCRplusEpisodeNumber`/`HdhrVCRplusSynopsis`/`HdhrVCRplusImageURL`) — there's no program-grid data behind it to draw from, only the one current show's own snapshot each of these fields carries.
