# VirtualTunerService.swift — Recording-relay virtual tuner

While ≥1 show is actively recording, this app presents itself as an additional, temporary HDHomeRun-like tuner — discoverable via the real binary UDP protocol plus the standard `/discover.json`/`/lineup.json`/`/status.json` HTTP shape — whose channel(s) relay the in-progress recording(s) straight from disk. Any HDHomeRun-aware client on the LAN, and in particular **another instance of hdhrVCRplus**, can discover and watch what's currently being captured without opening a second real tuner session against the actual device. See `TODO.md`'s "Virtual tuner relay: real VLC-based H.264 transcode (Phase 2)" entry for the deferred follow-up work; this (Phase 1) shipped 2026-09-01.

This reuses the Watch Now relay's existing disk-tailing mechanism (`docs/WebServer.md`'s "Recording playback relay") rather than tapping the live tuner feed a second time, so viewer count for the relayed channel is not tied to any physical tuner slot — it's N HTTP readers of one growing file, not N tuner sessions.

**User-facing toggle**: `AppConfig.Virtual_tuner_relay_enabled` (default `true`) — Settings → Sharing → "Rebroadcast In-Progress Recordings", and explained on its own dedicated first-run wizard step (`FirstRunWizardView`'s Step 2 — see `docs/FirstRunWizardView.md`). `AppState.updateVirtualTunerPresence()` treats it as an equal condition alongside `isRecording` (`if isRecording && config.Virtual_tuner_relay_enabled`), and both `SettingsView.save()` and the wizard's `finish()` call `updateVirtualTunerPresence()` directly when the value changes, so toggling it off tears the relay down immediately if a recording happens to already be in progress, rather than waiting for that recording to end.

## Components

- **`VirtualTunerService.swift`** — owns only the UDP discovery socket lifecycle. `start(deviceID:baseURL:tunerCount:onBindResult:)` binds `INADDR_ANY:65001` (`SO_REUSEPORT`, so it coexists with a real device or another instance's own responder) and replies to any DISCOVER_REQUEST with a DISCOVER_REPLY carrying the given `deviceID`/`baseURL`/`tunerCount` (see "Wire protocol" below); `stop()` closes it. Deliberately dumb — it doesn't track the lineup, doesn't know about `Show`, and exposes no readable state back to callers; `AppState` remembers its own copy of the ID/baseURL/tunerCount it started the service with.
- **`AppState.virtualTuner`** — the one shared `VirtualTunerService` instance. **One shared virtual device, not one per recording** — if two shows are recording on two different real tuners, the same virtual device's lineup simply grows to two channels rather than standing up two fake devices.
- **`AppState.activeVirtualTunerDeviceID`** — `nil` when nothing is recording; otherwise the currently-advertised fake `DeviceID`. As of 2026-09-03, `"FEED" + the source tuner's own last 4 hex digits` (`VirtualTunerService.relayDeviceID(sourceDeviceID:)` — the real tuner actually being relayed; same `FEED` sentinel prefix `makeDeviceID()`'s own random scheme uses, for one consistent brand across every DeviceID this app ever mints), falling back to that random scheme (`VirtualTunerService.makeDeviceID()`, distinct from the project's own unrelated `FFFF0001` fake EXTEND test device) only when no source device can be resolved. Not private: `WebServer`'s JSON route handlers read it directly to know whether to answer or 404.
- **`AppState.updateVirtualTunerPresence()`** — internal, not private (both `SettingsView` and `FirstRunWizardView` call it directly on a settings-toggle change, see "User-facing toggle" above). Starts/stops the service and (re)generates the ID whenever `isRecording && config.Virtual_tuner_relay_enabled` flips. The ID is deterministic per source tuner (see `relayDeviceID`'s own doc comment below), not fresh-per-restart — so it's reused across sessions on purpose, deliberately reversing this doc's own previous "never reused across a stop/start cycle" claim (see `relayDeviceID`'s doc comment for why that's now safe). Called from `startRecording(index:)`, `teardownRecordingState(index:alsoRebuildGrid:)`, `skipRecording(showId:)` (the last doesn't route through `teardownRecordingState`, so it needs its own call), `reattachRecordings()` (a relaunch — deploy, or "Keep Recording & Quit" — while a show is recording reattaches its curl process without going through `startRecording`, so without this call the relay would never start for it until an unrelated recording elsewhere happened to start/stop), and the two settings-toggle save paths above. When already active, a repeat call re-derives `baseURL`/`tunerCount` (via `WebServer.virtualTunerBaseURL(preferredInterface:)` and `state.recordingShows.count`) and passes them to `virtualTuner.start(deviceID:baseURL:tunerCount:)` again — which updates the UDP responder's advertised TLVs in place without a rebind or a new ID — so TunerCount stays accurate as a second/third show starts or stops recording after the relay is already up. Passes an `onBindResult` closure only on the fresh-start path: if the UDP bind actually fails (port 65001 already in use — another instance, or a real libhdhomerun-based tool), it backs `activeVirtualTunerDeviceID` out to `nil` again (and releases the web-server claim below) rather than leaving the HTTP JSON routes advertising a "live" relay no UDP client can ever discover. Also holds an `ensureWebServerRunning()`/`releaseInternalWebServer()` claim (the same refcounted internal-use mechanism `watchRecordingInApp` uses for the Watch Now relay, tracked in its own `virtualTunerWebServerClaimActive` flag) for as long as the relay is active — without it, the relay's HTTP JSON routes and stream endpoint would be unreachable (the underlying `NWListener` simply isn't running) whenever `Web_server_enabled` (Sharing) is off and no other window happens to be using the internal server.
- **`AppState.recordableDevices`** — `devices.filter { !$0.isVirtualRelay }`. This is the one accessor essentially every device-facing list in the app builds from instead of raw `devices` — see the Guardrails section below for the (long, and still possibly incomplete — new call sites should default to this rather than raw `devices`) list of call sites. Single-device backstop checks on an already-known device (`addShow`/`updateShow`/`handleRecord`/`handleToggleFavorite`/`vlcOccupiesTuner`) check that device's own `isVirtualRelay` flag directly instead, and stay separate from this accessor — `addShow`/`updateShow`/`vlcOccupiesTuner` funnel through the shared `AppState.isVirtualRelayDevice(_:)` deviceId-keyed lookup rather than each re-deriving it; `handleRecord`/`handleToggleFavorite` already hold a resolved `HDHRDevice` from their own lookup and just read `.isVirtualRelay` off it directly. **Lineup fetch is the one deliberate exception** — `fetchAllLineups(for:)` and its callers (`refreshGuides`, the idle loop's Local-Network-confirm retry, `ensureLineupLoaded`) intentionally do NOT filter to `recordableDevices`: a relay device's own `/lineup.json` is exactly what feeds the "Recording on Another Mac" menu entry (see below), so fetching it is required, not a bug. Guide fetch is the opposite case — see Known limitation below.

## Wire protocol

UDP discovery request parsing mirrors `HDHRManager.swift`'s existing client-side `udpDiscoverSync` byte-for-byte, and matches `tools/mock_hdhr.py`'s own reference responder:

- Request (real client → this app, port 65001): `[0x00,0x02][len hi][len lo][TLV payload]` — validated as loosely as `mock_hdhr.py` itself (≥4 bytes, leading type `0x0002`), no TLV/CRC parsing required.
- Reply (this app → client, unicast): `[0x00,0x03][len hi][len lo][TLV payload][crc32 of everything before it, little-endian]`, TLVs in order: `0x01` DeviceType (`0x00000001` = tuner), `0x02` DeviceID (big-endian u32), `0x2A` BaseURL (ASCII, e.g. `http://10.0.2.100:1980`), `0x10` TunerCount (1 byte), `0x27` LineupURL (ASCII, `<BaseURL>/lineup.json`).

**Corrected 2026-09-02** — the reply used to carry *only* the DeviceID TLV (14 bytes total, no DeviceType/BaseURL/TunerCount), on the theory that "real device metadata lives in `/discover.json` instead, per the real protocol's own division of labor." That theory was never verified against a real device and turned out to be wrong: a live discovery probe sent directly to a real EXTEND (`105404BE`) shows its actual DISCOVER_REPLY carries DeviceType/DeviceID/DeviceAuth/BaseURL/TunerCount/LineupURL TLVs, not just DeviceID. This app's own client (`HDHRManager.udpDiscoverSync`) never needed BaseURL from the UDP reply because it always went straight to the HTTP JSON routes for everything else — but a genuine third-party HDHomeRun client (Plex, Channels DVR, TVHeadend, SiliconDust's own apps) reads BaseURL from the UDP reply itself to know where the device's HTTP API lives. Without it, such a client has no way to learn this relay runs on a non-standard port (`Web_server_port`, default 1980, not the real protocol's usual 80) and either assumes port 80 (connection refused) or discards the reply outright — this is why the relay was invisible to real third-party discovery even though this app's own instances, and a direct `curl` of `/discover.json`, always worked fine. Fixed by adding the DeviceType/BaseURL/TunerCount/LineupURL TLVs to match the real shape; DeviceAuth (`0x2B`) is deliberately omitted — this relay has no such secret to advertise, it isn't a real tuner with cloud-guide access.

`VirtualTunerService.isDiscoverRequest(_:)`/`buildDiscoverReply(deviceID:baseURL:tunerCount:)` are the pure, unit-tested halves of this (`Tests/hdhr_VCRTests/Network/VirtualTunerServiceTests.swift`) — `handleReadable()` is just socket plumbing around them. `start(deviceID:baseURL:tunerCount:onBindResult:)` updates all three advertised fields in place on a repeat call while already bound (no rebind) — `AppState.updateVirtualTunerPresence()` relies on this to keep TunerCount current as shows start/stop recording after the relay is already up, not just at the moment it first comes up.

`makeDeviceID()` mixes this Mac's hostname (crc32) with a fresh random value on *every* call — the fallback path only, used when `relayDeviceID(sourceDeviceID:)` (below) has no source device to derive a stable ID from.

**`relayDeviceID(sourceDeviceID:)`, added 2026-09-03, explicit user request** — the primary path: `"FEED" + the source's own last 4 hex digits`, e.g. `105404BE` → `FEED04BE`, when a real tuner is actually being relayed (`AppState.updateVirtualTunerPresence()` passes `recordingShows.first?.hdhr_record`). **Not `"<sourceDeviceID>_Relay"`** — a first version of this literally appended `_Relay` to the DeviceID, but `VirtualTunerService.start(deviceID:)` parses this string via `UInt32(deviceID, radix: 16)` to build the real UDP wire protocol's binary DeviceID TLV (see "Wire protocol" above) — a `u32` has exactly 8 hex digits of room, full stop, and `_Relay` isn't valid hex, so `start()` rejected it outright and the relay failed to bind at all, caught live within minutes via `"invalid deviceID ... — not starting"` in the log, mid-recording (an active MLB Baseball recording at the time). A middle version tried a leaner `"FE"` 2-digit marker (to show 6 of the source's 8 real digits instead of 4) but was reverted the same day in favor of keeping the *same* `FEED` sentinel `makeDeviceID()`'s own random scheme already uses — one consistent "known-fake" DeviceID brand across everything this app ever mints, rather than two slightly different reserved prefixes. `FEED` spends 4 of the 8 available digits on that marker, leaving room for the source's own last 4 — the human-readable "which tuner" connection still lives primarily in `FriendlyName` (`"<source>-Relay"`, no hex constraint), this is just a bonus. Deterministic on purpose, replacing the fully-random-every-restart scheme this doc previously described: a fresh random ID minted on every relay restart (a plain relaunch, or just normal daily recording start/stop) left yet another now-permanently-unavailable `FEED####` entry behind in every other instance's device list, with nothing to ever clean it up — reported live after a dev machine relaunched repeatedly during testing had accumulated 18 such stale rows, none with a show ever assigned to any of them. Reusing the same ID across sessions is safe here specifically *because* it's now tied to a real, stable source tuner (whose own DeviceID never changes between sessions either) instead of being an arbitrary session marker — the original concern the random scheme guarded against (a client confusing a later, unrelated recording session for one it already knew about) doesn't apply when the ID means "the relay for tuner X" and X is genuinely the same tuner both times. Two Macs relaying the exact same real tuner ID at once would collide on this ID — accepted as unlikely, since a tuner only allocates one connection per recording, so normally only one machine is ever actually recording from a given real tuner at a time. See `AppState.probeForNewDevices()`'s stale-device pruning (`deviceUnavailableSince`/`staleDeviceForgetAfter`, `docs/AppState.md`) for the other half of the same fix — forgetting an unavailable device with no show assigned to it after a grace period, for devices (relay or real) that still end up stale despite the now-stable ID.

## HTTP routes

No second HTTP listener — everything is added to the existing `WebServer` on its existing port (`Web_server_port`, default 1980). `BaseURL` in `/discover.json` (and, since the above fix, in the UDP reply itself) is `http://<lan-ip>:<port>`, built by the shared `WebServer.virtualTunerBaseURL(preferredInterface:)` helper; a compliant client resolves everything through it plus `/lineup.json`'s own per-channel `URL`, so there's no protocol requirement to match a real device's port-80/5004 split.

All four routes 404 the instant nothing is recording (`activeVirtualTunerDeviceID == nil`):

- **`GET /discover.json`** — `buildVirtualTunerDiscoverJSON(state:deviceID:)`: `DeviceID`, `FriendlyName`, `ModelNumber` ("HDVR-RELAY"), `BaseURL`, `LineupURL`, `TunerCount` (= number of currently-recording shows), `LocalIP`, plus the non-standard `HdhrVCRplusVirtualRelay: true` marker. A real client ignores an unknown field; this app's own `HDHRDevice` decodes it into `isVirtualRelay` (see that property's doc comment in `Models.swift`).

  **`FriendlyName` is `"<source device's own FriendlyName>-Relay"`, added 2026-09-03** — e.g. "HDHomeRun EXTEND-Relay" — so the relay reads as clearly related to the real unit it's relaying from in a third-party client's device list, per explicit request, rather than a generic, unrelated-looking label. Looked up via the currently-recording show's `hdhr_record` against `state.devices`; `HDHRDevice.FriendlyName` (`Models.swift`) is a new field added alongside this, decoded the same way `ModelNumber` already is — present from a real HTTP `/discover.json` fetch, absent (nil) from a UDP-only-discovered device with no FriendlyName TLV read. Falls back to the original generic `"hdhrVCRplus (Recording Relay)"` name when the source device's own name isn't known (a UDP-only source, or — rare, since a race is unlikely, but possible if nothing happens to be recording at the exact instant this is built) no show is currently recording at all.

  `FirmwareName`/`FirmwareVersion`/`DeviceAuth`, a second listener on the real tuning port (5004), and `ScanPossible:1`/`SourceList`/`/lineup.post` were all tried and reverted during the same 2026-09-03 Channels DVR investigation — see `FAILED_APPROACHES.md`'s "Channels DVR compatibility for the virtual-tuner relay" entry for the full trail and why each was backed out.
- **`GET /lineup.json`** — `buildVirtualTunerLineupJSON(state:)`: one entry per currently-recording show — `GuideNumber`, `GuideName` (looked up from the real lineup, falling back to the bare channel number if unavailable), `URL` (`.../auto/v<channel>?dev=<hdhr_record>`), plus the non-standard `HdhrVCRplusShowTitle` field carrying the real show title. This is what lets a discovering instance's menu bar say "Recording on *\<title\>*" instead of just a channel number — see "Remote watch menu entry" below. Returned as a top-level JSON *array*, matching the real protocol (not wrapped in an object). The `dev=` query param disambiguates two real devices that happen to share a channel number (e.g. two tuners fed from the same cable lineup) — without it, two simultaneous recordings on the same channel number would produce byte-for-byte identical URLs, and a remote viewer picking the second lineup entry would always resolve to the first show's video.
- **`GET /status.json`** — `buildVirtualTunerStatusJSON(state:)`: one `{"Resource", "VctNumber", "TargetIP"}` row per currently-recording channel, returned as a top-level JSON *array* — matching the real device's own `/status.json` shape (`docs/HDHRFindings.md`, and this app's own client-side `[DeviceTunerInfo]` decode of it in `AppState.swift`), not wrapped in an object, same as `/lineup.json` above.
- **`GET /lineup_status.json`** — static `{"ScanInProgress": 0, "ScanPossible": 0, "Source": "Cable"}`.
- **`GET /auto/v<channel>?dev=<deviceId>&duration=<seconds>&transcode=<profile>`** — `handleVirtualTunerStream(channel:deviceId:durationSeconds:transcode:conn:)`: finds the show currently recording on `channel` (and, when `dev` is present, on that specific device — the same disambiguation `/lineup.json`'s own `URL` field carries; falls back to a channel-only match when absent, e.g. a hand-typed URL). With no `transcode` (or `none`), relays `show_recording_path` via the same `streamGrowingFile`/`pumpGrowingFile`/`handleGrowingFileChunk` pipeline the Watch Now relay uses (`docs/WebServer.md`), generalized with an optional wall-clock `deadline` derived from `duration` — the connection is closed once the deadline passes, matching the real device's own `duration=` behavior (`RecordingManager.swift`'s `streamURL`). With a real profile, routes to the headless transcode pipeline — see "Real transcode (Phase 2)" below — *unless* the on-disk recording is already a modern codec (H.264/HEVC), in which case it's relayed as-is regardless of the requested profile (see that section's "Already-modern-codec skip"). `duration=` is not currently honored on the transcode path (only the raw-passthrough path derives a deadline from it) — a gap, not a deliberate choice; noted in Known Limitation below.

### Diagnostic request logging

Added 2026-09-03 while debugging a real third-party client (an iOS HDHomeRun-client app) that discovered the relay but couldn't load channels — needed visibility into exactly what a real client requests, not just what this app's own client-side code expects. Two layers, both to the main log (`~/Library/Logs/hdhrVCRplus.log`, prefixed `[VirtualTuner]`), gated to the virtual-tuner surface specifically (not every request — this would be noise on top of normal guide/API traffic):

- **UDP**: every discovery request logged in `VirtualTunerService.handleReadable()` with the requester's IP:port and the DeviceID/BaseURL replied with.
- **HTTP**: `WebServer.isVirtualTunerHTTPPath(_:)` gates a request-arrival log in `accumulate()` (method, path, remote endpoint) before routing, so a malformed/unexpected path still shows up even if it never reaches a matching `case`. Each of the four JSON routes and `/auto/v<channel>` also logs its own outcome (200 with entry/tuner counts, or 404 with the reason) from inside `routeOnMain`/`handleVirtualTunerStream` — e.g. `/lineup.json`'s log line includes the actual channel numbers returned, so an empty-but-200 response is distinguishable from a 404.

### A device visible but with no channels: the actual bug found this way

The diagnostic logging above led straight to a real, currently-live bug, not a protocol gap: **`AppState`'s web server could fail to bind at all after a relaunch while a show was already recording**, leaving `VirtualTunerService`'s UDP responder (an independent bind on port 65001) up and answering — so a client could discover the device — while the HTTP listener on port 1980 was completely down, so every route including `/lineup.json` was connection-refused. Reproduced live on two consecutive `deploy.sh` runs while a real recording was in progress at each relaunch.

**Root cause**: two independent triggers could each call `webServer.start()` directly, back-to-back, at launch — `reattachRecordings()`'s call to `updateVirtualTunerPresence()` (which claims the internal web server via `ensureWebServerRunning()` when a reattached show is already recording) immediately followed, in the same launch sequence, by `setupWebServer()`'s own unconditional start when Sharing is on. Both guarded only on `webServerRunning`, which doesn't flip `true` until `NWListener`'s *async* `.ready` callback lands — so both calls saw `false` and both called `webServer.start()`, which itself calls `stop()` then creates a fresh `NWListener`: two real binds racing the same port produced `POSIXErrorCode(48)` ("Address already in use") and left the loser's listener cancelled, taking the whole web server down with it (not just the virtual-tuner routes).

**Fix**: consolidated every caller (`setupWebServer`, `ensureWebServerRunning`, `releaseInternalWebServer`) behind one arbiter, `AppState.reconcileWebServerState()` — the only function that ever calls `webServer.start()`/`stop()` — guarded by a `webServerStarting` flag that closes the exact window `webServerRunning` couldn't. See `docs/AppState.md`'s table for the full before/after and the infinite-retry-loop pitfall hit and reverted while building this fix (re-reconciling from inside the start completion handler itself, rather than only from the four trigger points).

`lanIPAddress(preferredInterface:)`, `buildVirtualTunerDiscoverJSON`/`LineupJSON`/`StatusJSON` are internal (not `private`), same testability pattern as `buildGuideJSON` — see `Tests/hdhr_VCRTests/WebServer/VirtualTunerWebRoutesTests.swift`, which calls them directly with a synthetic `AppState` rather than spinning up a live `NWListener`.

## Guardrails

Three behaviors that must never regress — hard backstops and consistent filtering, not just UI-level polish:

1. **This instance must never discover its own virtual tuner.** `AppState.excludingOwnVirtualTuner(_:)` filters any discovered device whose `DeviceID` matches `activeVirtualTunerDeviceID` out of the result *before* it reaches `state.devices` — both `discoverDevices(knownHosts:attempts:)` and `probeForNewDevices()` route their `hdhrManager.discoverDevices(...)` results through it. Another instance's relay (a different `DeviceID`) is deliberately *not* filtered here — only self-exclusion is required.
2. **A relay tuner — this instance's own (should self-exclusion ever be bypassed) or another instance's — is watch-only, never schedulable.** `HDHRDevice.isVirtualRelay` is checked in `AppState.addShow(_:)` and `AppState.updateShow(_:)` (the two universal show-creation/edit funnels every caller — native wizard, web guide, `hdhr_guide` TUI — eventually goes through), refusing with a `glog` warning and no-op. `WebServer.handleRecord` also checks it directly, right after the device/channel lookup, so the web guide's Record modal gets a clear JSON error (`"This tuner is a temporary recording relay..."`) instead of a silent no-op from `addShowFromGuide`. `WebServer.handleToggleFavorite` carries the identical guard, right after its own device/channel lookup, for the same reason — a discovered relay's fabricated lineup entries must not be forwarded to `hdhrManager.setFavorite` against a device that isn't real.
3. **A relay device must never be treated as a real, functioning tuner by anything that lists, polls, or measures tuners.** This is the broadest and easiest guardrail to miss piecemeal — every call site below builds from `AppState.recordableDevices` instead of raw `devices` specifically because an earlier pass of this feature added the accessor but missed most of them, discovered only by two full audit passes after the fact:
   - **Device pickers/lists**: `WebServer.buildDevBarHTML`'s tuner boxes, `buildHTML`'s `defaultDev` selection (both the fallback chain and its `count > 1` mode gate), `buildGuideGridHTML`'s per-device row loop (a relay's synthetic lineup entry can carry the *same* `GuideNumber` as the real channel it's relaying — in practice `entriesInWindow`'s own empty-guide-window guard already keeps a row from rendering for a device with no real guide data, but the loop is filtered too, as defense in depth), `buildNowJSON`'s `/api/now.json` entries, and `buildGuideJSON`'s device list + default-device fallback (feeds `hdhr_guide`'s Tab/switchDevice()); `MenuContent.swift`'s top-of-menu device-header loop and its four `Recording`/`Up Next`/`Scheduled`/`Paused` per-device-section `count > 1` gates; `WatchNowView`'s tuner `Picker` and its `selectedDevice`/`onAppear` fallbacks; `AddShowView`'s default-device fallback (both its `onAppear` path and its lineup-load `.task`); `SettingsView`'s "Measure Signal" device list; `FirstRunWizardView`'s onboarding discovery-status/prefetch code (including falling back to `.notFound` if a brand-new install's only discovered "device" turns out to be someone else's relay, rather than falsely reporting a real tuner was found).
   - **Background polling that would otherwise fail forever or pollute shared state**: `AppState.performFetchAllGuides`/`refreshGuides` skip guide fetch for a relay device entirely — it has no `DeviceAuth`/cloud guide relationship, so the fetch can only ever fail, and an unfiltered retry loop (`ensureGuideLoaded`, called every idle tick for any device with an empty guide) would eventually fire a real "Guide Load Failed" user notification/Discord embed naming a device the user never configured. `AppState.startSignalScan()` excludes relay devices for a sharper reason: `ChannelSignalStore.key(for:)` keys signal history purely by (trimmed/lowercased) `GuideName`, not by device — scanning a relay's synthetic lineup entry (whose `GuideName` is copied verbatim from the real channel it's relaying) polls a `/status.json` that never reports `SignalQualityPercent`, so every one of its channels falls into the "never locked" branch and would overwrite the *real* channel's signal history with a bogus 0% reading purely because a same-named channel happened to be relayed elsewhere on the LAN at scan time.
   - **The watching side**: `AppState.vlcOccupiesTuner(for:)` has the matching guard — a relay device must never register as tuner-occupied even while its stream is being watched via `watchRemoteRelay`, since `VLCBridge.play(url:)`'s relay-URL detection only recognizes the local `/api/watch-recording` shape, not a remote relay's `/auto/v<channel>` URL (which is intentionally the *same* shape a real tuner's own live stream uses, so it can't be used to distinguish the two). `AppState.releaseAssertionsIfIdle()` similarly excludes relay devices from its "any tuner active" check — a remote Mac's own relay occupancy must never keep this instance's sleep-prevention assertions held. `watchInApp`/`watchRecordingInApp`'s own `?? devices.first` fallbacks (used when an explicit device lookup fails) were also hardened to `recordableDevices.first`, so a defensive fallback can't silently pick a relay either.

Regression coverage: `Tests/hdhr_VCRTests/AppState/VirtualTunerGuardrailTests.swift` (self-exclusion, addShow/updateShow refusal, `vlcOccupiesTuner`'s relay guard) and `VirtualTunerWebRoutesTests.swift`/`VirtualTunerGuideGridTests.swift` (`handleRecord_refusesRecordingAgainstAVirtualRelayDevice`, `devBarHTML_excludesAVirtualRelayDevice`, the `lineup.json` device-disambiguation tests, the guide-grid row-exclusion test). The SwiftUI-only call sites (`WatchNowView`/`AddShowView`/`MenuContent`/`FirstRunWizardView`/`SettingsView`) and the background-polling exclusions (`performFetchAllGuides`/`refreshGuides`/`startSignalScan`) have no dedicated unit tests — verify manually per the Verification section below.

## Remote watch menu entry

`MenuContent.swift`'s menu builds a `remoteRelayEntries` list from `state.devices.filter { $0.isVirtualRelay }` (guaranteed to exclude self, per Guardrail 1 above) crossed with `state.lineups[deviceId]` entries carrying a non-nil `virtualRelayShowTitle` (the `LineupEntry` field decoded from `HdhrVCRplusShowTitle` — reuses the existing lineup-fetch pipeline, `HDHRManager.fetchLineup`, rather than a separate cache). Each becomes a "Recording on *\<title\>*" row in a "Recording on Another Mac" section, alongside the existing "Recording Now" section. Clicking one calls `AppState.watchRemoteRelay(url:title:device:)`, which opens a native VLC window directly against the relay's stream URL via `VLCPlayerWindowManager.shared.open(url:title:device:appState:)`.

`watchRemoteRelay` is deliberately **not** `watchInApp` reused: `watchInApp`'s `tunerAvailable` gate protects a real device's limited physical tuner count, which doesn't apply to a relay stream (unlimited concurrent viewers is the whole point — see the Context section above), and its guide-entry-driven sleep-prevention has no local guide entry to key off for a remote device's synthetic channel.

The row disappears the moment the remote show stops recording — the remote instance's `/lineup.json` naturally stops listing that channel, and the local lineup-fetch cache reflects that on its next refresh like any other lineup change.

## Real transcode (Phase 2)

**Implemented and live-verified 2026-09-02** — `Tests/hdhr_VCRTests/WebServer/VirtualTunerLiveStreamTests.swift` passed against a real HDHomeRun device and a real over-the-air recording (`RUN_VIRTUAL_TUNER_LIVE_TESTS=1`): raw passthrough serves byte-identical content, and `?transcode=mobile` genuinely produces H.264 (confirmed via `mediainfo`, not just "some bytes came back"). Requesting a real `transcode` profile on `/auto/v<channel>` routes to a headless libvlc encode instead of raw passthrough — **the actual profile used comes from `config.Virtual_tuner_relay_default_transcode` (Settings → Sharing → Recording Relay → "Default transcode level," added 2026-09-03), not the viewer's own requested profile string.** A viewer's `?transcode=<anything-non-empty-non-"none">` only decides whether to transcode at all (`WebServer.handleVirtualTunerStream`'s `wantsTranscode`); once that's true, the admin-configured level always wins, per explicit user direction — a natural fit given the sharing model below already collapses differing per-viewer profile requests into whichever one happens to be running. The Settings picker offers all seven real, EXTEND-only profile names — `heavy`/`internet720`/`internet540`/`internet480`/`internet360`/`internet240`/`mobile` (sourced from the original AppleScript app's 2016+ production list plus SiliconDust's current `info.hdhomerun.com/info/http_api` docs, which dropped `internet720` in favor of `internet540` at some point — kept in the set since a live device still honors it directly) — defaulting to `"heavy"`.

- **Input**: a `VLCBridge.TranscodeSession`'s own independent `libvlc_media_player_t` (never the on-screen `mediaPlayer` singleton — no drawable/NSObject is ever set on it, so libvlc allocates no real vout) plays `http://127.0.0.1:<port>/api/watch-recording?show=<id>&start=0` — this app's own existing growing-file HTTP relay, **not** a `file://` path. `VLCBridge.play(url:)`'s own doc comment explains why: VLC's plain `file://` access module snapshots a file's length at open time and won't read past it on a growing file, which would stall a transcode input exactly the way it would on-screen playback.
- **Sout chain** (`libvlc_media_add_option`, the same call the on-screen player already uses for its own options): `sout=#transcode{vcodec=h264,vb=<kbps>,acodec=mpga,ab=128,channels=2}:std{access=http,mux=ts,dst=127.0.0.1:<port>/relay}` — output stays MPEG-TS-wrapped (`mux=ts`, matching this endpoint's `Content-Type: video/mp2t` and every other HDHomeRun-shaped consumer's expectation), only the *codec* changes from MPEG-2 to H.264. **No `scale=`/`width=`/`height=`/`fps=` at all, deliberately** — per an explicit user request, every profile keeps the source's own frame rate and dimensions regardless of which one is requested; bitrate (`VLCBridge.transcodeBitrateKbps(for:)`, a first-pass guess for all seven recognized profiles — see that function's own doc comment for the full ladder — not a measured/tuned spec) is the *only* thing that varies by profile now. Real tradeoff, not an oversight: a `mobile` request at 400kbps against a full-resolution 1080i/720p source looks considerably blockier than the same bitrate would at a genuinely reduced resolution. Live-verified 2026-09-02 (`VirtualTunerLiveStreamTests.swift`'s `relayTranscodesToH264WhenAProfileIsRequested`): output width/height/frame rate probed via `mediainfo` and confirmed to match the source exactly. `channels=2` is a separate, earlier live-caught fix: a real over-the-air 5.1 source silently produced a video-only transcode with no audio at all — `mpga`'s underlying twolame encoder only supports up to 2 channels and drops the audio track entirely rather than erroring loudly. Every relay profile is a low-bandwidth target anyway, so forcing stereo is the right call regardless, not just a workaround.
- **Output serving**: libvlc's own `std{access=http}` sout module runs a tiny httpd bound to `127.0.0.1` only (never `0.0.0.0`) on one of a small fixed port range (`19810...19819` — ten concurrent distinct shows being transcoded at once, far beyond realistic use). `WebServer.pumpTranscodeProxy` connects to it as an HTTP client (`URLSession.bytes(for:)`-style streaming) and forwards every chunk straight out to the real external `NWConnection` as it arrives.
- **Sharing/lifecycle**: one `VLCBridge.TranscodeSession` per **`showId` alone** — not per `(showId, profile)` pair, as it was originally built — reference-counted by concurrently-connected external viewers (`startTranscodeSession`/`stopTranscodeSession`) — mirrors Phase 1's "N viewers, one relay" model instead of spending a transcode per viewer. **Changed 2026-09-03, per explicit user direction**: since every profile already produces the source's own dimensions/frame rate and only bitrate differs (see the sout-chain bullet above), "transcode" itself doesn't mean anything more specific than "give me H.264" — there's no reason two viewers of the same show should pay for two separate decode+encodes just because they happened to pass different profile strings. Whichever profile actually started the running session wins for every later joiner, even one that requested a different profile — `TranscodeSession.profile` records which one that is, and `startTranscodeSession` logs clearly (`"requested profile=X differs from running profile=Y, which wins"`) whenever a join's requested profile doesn't match, rather than silently ignoring the mismatch. Live-verified 2026-09-03 (real deployed instance, real recording): a `mobile` request started a session; a concurrent `heavy` request for the same show joined it (`refs=2`) instead of starting its own. `AppState.teardownRecordingState`/`skipRecording` call `VLCBridge.shared.stopAllTranscodeSessions(showId:)` unconditionally on recording stop, regardless of ref count, so a session can never outlive its recording — now a direct dictionary removal by `showId` rather than a prefix scan over multiple profile-suffixed keys, since at most one session can exist per show.
- **Startup race**: libvlc's sout httpd only actually starts accepting connections once the input/decode/encode pipeline finishes initializing after `play()` returns, not immediately — `beginTranscodeRelay` waits out a fixed ~0.6s grace period after a *freshly-created* session (`TranscodeSession.startedAt`) before its first proxy connection attempt; an already-running (joined) session skips the wait. Confirmed sufficient in live testing, but still a fixed guess, not an event-driven readiness signal — a slower machine or heavier source content could in principle need longer.
- **Already-modern-codec skip**: some channels genuinely broadcast H.264 (or, in principle, HEVC) already, not MPEG-2 (`docs/HDHRFindings.md`'s `none` profile note: "Raw stream, no transcode (MPEG-2 or H.264 as broadcast)") — not a theoretical edge case: live-verified 2026-09-02, 15 of 112 channels on a real device reported `VideoCodec: "H264"`, not `"MPEG2"` (see `docs/HDHRFindings.md`'s "`/lineup.json` carries per-channel `VideoCodec`/`AudioCodec`" finding — an earlier pass of this doc incorrectly claimed no such field exists; it does). Re-encoding an already-modern source would spend CPU for a real quality loss with no format benefit, so `handleVirtualTunerStream` checks two ways, fast path first: `LineupEntry.VideoCodec` for the show's channel (an in-memory lookup against `state.lineups`, no disk I/O — string form, checked via `MPEGVideoStreamType.isAlreadyModernCodec(_ videoCodec: String)`) when present; when it's `nil` (older firmware, or this app's own synthetic virtual-relay lineup entries, which never set it), falls back to `mpegTSVideoStreamType(inFileAt:)` (`CompatibilityHelpers.swift`), which parses the on-disk recording's own PAT+PMT for the video elementary stream's `stream_type` byte (`0x02`/`0x01` = MPEG-1/2, `0x1b` = H.264, `0x24` = HEVC — the same byte values `docs/HDHRFindings.md`'s live-captured findings and `TranscodeStreamFormatTests.swift`'s fixtures already established, checked via the byte-taking overload of `isAlreadyModernCodec`). Either way, if the source is already modern, the request is relayed as-is (the same `streamGrowingFile` path a `transcode=none`/absent request takes) instead of spinning up a real `TranscodeSession`.

**Verified this session, live, against a real tuner** — `VirtualTunerLiveStreamTests.swift` has three tests, all passing against a real HDHomeRun device: raw passthrough (byte-identical relay of a real captured channel), real transcode (an MPEG2-reporting channel genuinely re-encoded to AVC via `mediainfo`, with a surviving stereo audio track), and the already-modern-codec skip (a real H264-reporting channel — one of the confirmed channel-21 subchannels — requested with `?transcode=mobile` came back byte-identical to the raw capture, proving no re-encode happened, not just "the output still says AVC"). Cross-profile session sharing (two concurrent viewers of the same show requesting *different* profiles correctly joining one session, per the 2026-09-03 sharing-key change above) was also live-verified against the real deployed app, via the server's own request log. Not yet verified: sustained/long-running sessions, and the `?duration=` gap noted below.

**Known gaps**: `?duration=` is accepted on the raw-passthrough path but not yet honored on the transcode path (`beginTranscodeRelay`/`pumpTranscodeProxy` have no deadline timer) — a real client requesting both together on a transcoded stream won't get the early-close behavior it would on a real tuner. `libvlc_release` (releasing the whole `libvlc_instance_t`, not just a session's own media/player) is never bound in `VLCBridge.swift` at all — irrelevant here since the instance is process-lifetime shared with the on-screen player anyway, same as before this feature existed.

`Tests/hdhr_VCRTests/WebServer/VirtualTunerLiveStreamTests.swift` is the live proof of the above (real recording → raw stream connects and matches; real recording → transcoded stream's bytes probe as `AVC`/H.264 with a surviving stereo audio track, not `MPEG Video`/no-audio). Gated behind `RUN_VIRTUAL_TUNER_LIVE_TESTS=1`; needs a real, reachable (non-relay) HDHomeRun device on the LAN (briefly tunes one of its tuners, ~7s, to capture a genuine sample — deliberately not a synthetic test pattern, since a real codec-change assertion needs real decodable content) and `mediainfo` on `PATH` (test-only tool, `brew install media-info`, never shipped in the app).

## Known limitation

The relay reads from the growing file on disk (same mechanism as Watch Now), so it's inherently a few seconds behind true live — not real-time. This applies to both the raw and transcoded paths (the transcode's own input is that same growing-file relay).

A discovered relay device never gets a real EPG on the discovering instance — `guideByDevice[relayId]` never populates, by design (see Guardrails above). This is invisible in normal use (the relay is never listed as a pickable tuner anywhere a guide would be shown), but worth remembering if a future feature ever wants to show more than just the current recording's title for a remote relay channel — there's no program-grid data behind it to draw from, only the one `HdhrVCRplusShowTitle` string `/lineup.json` carries.
