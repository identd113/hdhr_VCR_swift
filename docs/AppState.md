# AppState.swift — App Logic & Data Flow

`@MainActor ObservableObject`. All app state lives here. `hdhr_VCRApp` injects it as an `@EnvironmentObject`.

---

## Startup (`AppState.startup`)

1. `loadConfig()` — reads JSON, resets all `show_recording = false`. Auto-removes inactive Single shows (already recorded; no further scheduling needed).
2. `reattachRecordings()` — scans `ps -Axo pid,args` for lines containing `show_id:` + `/usr/bin/curl` + `hdhrVCRplus`. If the matching show's `show_end` is still future, sets `show_recording = true`, clears `show_tuner_resource` (will be re-captured by `captureResourceHeaders`), and calls `recordingManager.reattach(showId:pid:title:endDate:)` — recording continues uninterrupted and the sleep assertion is re-armed for the remaining duration. **Read pipe data before `waitUntilExit()`** to avoid deadlock when ps output exceeds the ~64 KB pipe buffer. After the PID scan, any show that has a non-empty `discord_start_msg_id` but was **not** reattached (i.e. its recording ended while the app was down) gets a recovery Discord embed: "✅ Recording Complete" if the output file has non-zero size, or "⚠️ Recording Interrupted" otherwise. The `discord_start_msg_id` is cleared to `""` in config **before** the network send — a crash during the PATCH won't re-trigger the recovery on the next launch.
3. `setupWebServer()` — binds the NWListener on `config.Web_server_port` immediately after config load, before device discovery. Port is available within ~1 s of launch; responses that require guide data are delayed by main-actor availability, not by the startup sequence itself.
4. Notification permission (background `Task` — non-blocking).
4b. GitHub release check (background `Task` — non-blocking) — `updateCheckLoop()` calls `checkForUpdateOnce()` then re-checks every 24h for the app's lifetime, gated per-tick on `config.Check_for_updates`. See `UpdateChecker.swift`.
5. `await ChannelSignalStore.shared.load()` — loads persisted per-channel signal history before the first guide fetch. Awaited (blocks the rest of startup), unlike the notification-permission step.
6. `discoverDevices(knownHosts:attempts:10)` — up to 10 retries with 1 s pauses; idle loop retries on each tick if devices remain empty.
7. `fetchAllGuides()` — parallel guide load for all devices; mirrors result into `guideByDevice`.
8. `startTimer()` — fires `idleLoop()` every `config.Idle_timer_interval` seconds (default 10, min 5).
9. `startStatusLightTimer()` — separate 1Hz `Timer` driving the menu bar icon's optional blink (Settings → General → "Blink menu bar icon", off by default); see `docs/MenuContent.md#menu-bar-icon-states`.
10. Sets `isStartingUp = false` (menu bar icon switches from dimmed to its normal lit mark).

## Idle Loop (`AppState.idleLoop`)

Runs every `config.Idle_timer_interval` seconds on MainActor:

- If `devices` is empty → retries discovery immediately.
- If guide channels missing for any device → calls `ensureGuideLoaded(for:)`.
- Refreshes lineup + guide at each clock-hour boundary (`lastRefreshHour` vs current hour; non-blocking `Task`) — aligned with the web UI's 30-minute window slide. On total API failure the next attempt is the next hour boundary; intra-hour retries are handled per-device by `ensureGuideLoaded` backoff.
- **Tuner-detection auto-pause/auto-resume** (2026-08-19) — any active show whose `hdhr_record` isn't in `usableDeviceIDs` (never discovered at all, or discovered but confirmed offline after 3 missed probes) gets auto-paused via `applyPause(index:reason: Self.autoPauseTunerMissingReason)` — marker string `"Tuner not detected"`, logged once instead of the unbounded "device not found" warning this replaced (see `issues_resolved.md`'s "Lyla in the Loop" entry). Symmetric auto-resume: any paused show carrying that exact marker gets `applyResume(index:)`'d the moment its own tuner is usable again — never a manually-paused or fail-threshold-paused show, since those carry a different `show_fail_reason`. Deliberately does **not** call `scheduleNextAir` on resume (unlike the Fail-Threshold auto-resume below) — for a `.single` show that unconditionally marks it `show_active = false` ("DONE — deactivated"), which would wrongly treat a mere resume as a completed recording. The Fail-Threshold auto-resume's own `endDate <= now`/`nextDate` branches explicitly skip any show carrying this marker (`guard show.show_fail_reason != Self.autoPauseTunerMissingReason else { continue }`) — without that exclusion the two mechanisms would fight: the window-expiry check un-pausing it, the tuner check re-pausing it again next tick, forever. See CLAUDE.md's "Auto-pause-on-missing-tuner marker" invariant.
- **Device probe** — calls `probeForNewDevices()` every 5 minutes to detect new and departing tuners. Guarded by `probeInFlight: Bool` (`guard !probeInFlight else { return }` / `defer { probeInFlight = false }`) — `idleLoop()` launches this as a detached, unawaited `Task`, so a slow probe (e.g. `discoverDevices` stalling under network stress) could otherwise overlap itself and double-append the same first-seen device, corrupting occupancy counts/menu/dev-bar for the session. When any device misses a probe (not seen in discovery response), a 60-second follow-up probe is scheduled (`nextQuickProbe`) so the 3-miss unavailability threshold is reached in ~2–7 minutes rather than 15. The condition `missedProbes <= 3` (inclusive) ensures a follow-up is also scheduled on the tick that crosses the unavailability threshold, keeping recovery detection at 60 s cadence immediately after a device goes offline. The normal 5-minute cycle is unaffected by quick probes. The merge for a still-present device re-applies `DeviceAuth`, `LocalIP`, **and `TunerCount`/`FirmwareVersion`** from the fresh probe — the last two matter because a UDP-only startup with the device's HTTP briefly down caches `TunerCount == nil` (no tuner badge, since `computeDevTuners` renders none when total is 0); a quick re-probe is also scheduled while any **reachable** (`isAvailable`) device has a nil `TunerCount`, so capacity is restored within ~60 s of the device's web server becoming reachable. Bounded by `tunerCountFallbackAt: [String: Date]`, which stores the deadline itself (stamped `now + 5 min` the first tick a device is seen in this state, matching `showRetryAfter`/`nextQuickProbe`'s deadline-based shape rather than a start-time) and is cleared once `TunerCount` is restored or the device stops being available: the quick-probe re-arm only fires while `now` is still before that deadline — i.e. **under 5 minutes** into the state. Past that, it falls back to the normal 5-minute cycle (which still retries the HTTP fetch, just less aggressively) rather than pinning the 60 s cadence for the rest of the session — needed for a real device whose HTTP server is permanently down (not just slow to start), since the plain `isAvailable` guard alone only excludes devices UDP itself stops seeing (e.g. the fake `FFFF0001` test device), not one that stays UDP-reachable with a dead HTTP server forever.
- Per active show:
  - Fires "Up Next" notification once at `Notify_upnext` minutes before; stamps `notify_upnext_time`.
  - Fires "Recording Soon" notification once at `Notify_recording` minutes before; stamps `notify_recording_time`.
  - Starts recording if `show_next <= now + 10s` AND `show_end > now` AND the show isn't in its post-failure retry cooldown (`showRetryAfter[show_id]`, see below).
  - Stops recording naturally if `show_end <= now`.
  - **Stranded show advance**: if `!show_recording && show_end <= now && show_next < now`, calls `scheduleNextAir` immediately. Handles the case where the app restarted after curl exited normally but before the idle loop fired the natural-stop handler (which requires `show_recording == true`). Logs `"stranded show_next in past — advancing"`.
  - Detects unexpected curl exit → reads `X-HDHomeRun-Error` from the curl header dump via `RecordingManager.readAndClearHDHRError` (precise device error code, e.g. "Tuner In Use (804)"); if no header was written, falls back to `RecordingManager.readAndClearExitStatus` (decodes curl's own process exit code from the `waitpid` status captured by `isRunning`, e.g. `"curl timeout (28)"`, `"curl couldn't connect (7)"`); only falls back further to the generic `"curl exited unexpectedly"` if neither yields a reason. Clears `show_tuner_resource`; calls `recordShowFailure(index:reason:)`, sends notification.
  - Fires Discord progress update (PATCH) once per 5-minute boundary for active recordings when `Discord_on_progress` is enabled and `discord_start_msg_id` is set.
- Conflict notifications: when a show can't start because all tuners are full, fires once per show+episode window (`conflictNotifiedEpochs: [String: TimeInterval]` — keyed by `show_id`, value is `show_next` epoch; clears on reschedule via `removeValue(forKey:)`).
- Calls `captureResourceHeaders()` then `fetchDeviceStatus(for:)` once per device (via `refreshTunerOccupancy`). `captureResourceHeaders` reads `X-HDHomeRun-Resource` from the curl header dump for any recording show whose `show_tuner_resource` is still empty — stores e.g. `"tuner0"` directly on the show. `fetchDeviceStatus` uses this value first when targeting `/tunerN/vstatus`; falls back to VctNumber channel match, then any locked tuner. Logs a warning if no locked tuner is found at all. Guards against concurrent status.json requests for the same device (`fetchStatusTasks: [String: Task<Void, Never>]` — a second caller awaits the already-in-flight Task rather than starting a redundant one) — the idle-loop tick, startup, and probe call sites can all target the same device within a short window, and a slow/stalled device could otherwise stack up several in-flight requests across ticks instead of each call effectively no-oping until the prior one finishes. The per-show `/tunerN/vstatus` fetches for a device recording several shows at once run **concurrently** (`withTaskGroup`, one child task per recording show on that device) rather than sequentially — a device with N simultaneous recordings used to pay N round-trips back-to-back here, which `tunerAvailable` (Watch Now/VLC) awaits synchronously before opening a stream. After each `vstatus` fetch's network `await` returns, its entry re-checks `shows.contains(where: { $0.show_id == show.show_id })` before writing to `tunerStatus` — a web-UI delete landing during that await window already ran `deleteShow`'s `tunerStatus` cleanup for that show_id, and writing here afterward would silently re-add a display-only leak nothing will ever clear again (the show is gone, so `deleteShow` never runs on it a second time).
- **Local Network permission fast-retry**: while `config.Local_network_confirmed` is still `false` (see "Dock icon" below), retries `fetchAllLineups(for: devices)` on every tick instead of waiting for the hour-boundary refresh above — guarded by `lineupConfirmRetryInFlight: Bool` so a slow/blocked fetch can't stack up across ticks. Self-limiting: `AppState.confirmLocalNetworkAccessIfNeeded()` flips the flag (and persists it) on the first successful fetch, after which this branch never fires again for the rest of the app's life. See `TODO.md`'s "Show Stoppers" entry.
- **Tuner audit**: after storing `deviceTunerOccupancy`, `fetchDeviceStatus` logs `[TunerAudit] DEVID: N/M active  rec=N vlc=N` — but only when the line differs from the previous tick's for that device (`lastTunerAudit: [String: String]`); an unchanged tick stays silent. `active` is the raw count of locked tuners from `status.json`, `rec` is `recordingShows.filter { hdhr_record == device.DeviceID }.count`, and `vlc` is 1 when `VLCPlayerWindowManager.shared.currentDeviceID` matches this device. Unexpected tuner usage (e.g. a leak after a delete) is immediately visible in the log the moment it changes.
- **NowAiring log**: gated to run at most once every 5 minutes (`lastNowAiringScan: Date`) rather than every tick — it's a full device×channel guide walk purely for diagnostic discovery, not something a program's actual air time depends on. When it runs, iterates all guide entries that are currently on-air (`StartTime <= now < EndTime`). For entries with no genre tag (`firstGenre == nil`) and a SeriesID not in the known paid-programming set (`C11809220ENAPZK`, `C459763EN3L6D`), logs `[NowAiring] {ch} {guideName} — {title} SeriesID={sid}`, once per (channelNum, StartTime) slot (tracked in `loggedNowAiring: Set<String>`). Used to discover new infomercial SeriesIDs for the web guide's hidden-by-default filter.

### Reentrancy & Mid-Tick Mutation Safety

`idleLoop()` guards itself with `idleLoopRunning: Bool` (`guard !idleLoopRunning else { return }` / `defer { idleLoopRunning = false }`) — `startTimer()`'s `Timer.scheduledTimer` fires a new `Task { await idleLoop() }` every `Idle_timer_interval` regardless of whether the previous run finished, and Pass 1/Pass 2 both `await` real network calls (`scheduleNextAir` → `guideStore.load`) that can exceed the tick interval under network stress. Without the guard, two overlapping `idleLoop()` runs could both act on `shows` at once.

Pass 1 and Pass 2 both iterate by `show_id`, not by a captured `Int` index (`for showId in shows.map({ $0.show_id })`, re-resolving `shows.firstIndex(where: { $0.show_id == showId })` at the top of each iteration, `continue`ing if not found). A plain `for i in shows.indices` would be unsafe here: `stopRecording`/`scheduleNextAir` await mid-loop, during which `shows` can be mutated by an interleaved event (a web-UI delete arriving on the same MainActor) — a stale `i` captured before the loop started could be out of range (fatal trap) or silently point at a different show after a deletion shifted the array. Pass 1 additionally re-checks the original stop condition (`show_active && show_recording && show_end <= now`) after re-resolving the index, in case the show changed state in the interleaving window.

The same class of fix applies to several other functions that hold an index across an `await`:
- **`scheduleNextAir(index:)`** uses a working `var idx = index` (not the immutable parameter directly). In the `.seriesChannel`/`.seriesAll` case, after `await guideStore.load(for:hours:useXML:)`, `idx` is re-resolved by `show.show_id` — the function returns early if the show was deleted while that fetch was in flight, rather than writing through a stale/reused index afterward.
- **`stopRecording(showId:)`** (the showId-taking convenience overload used by menu/web actions) re-derives its index *inside* the deferred `Task`, not before creating it — `shows` can mutate between the synchronous call and the Task actually running on the MainActor.
- **`stopRecording(index:natural:)`** itself re-resolves by `show.show_id` after `await scheduleNextAir(index:)` (its natural-completion path) before reading `shows[index]` again — the original `index` parameter isn't protected by `scheduleNextAir`'s own internal re-resolution, since that only guards `scheduleNextAir`'s own writes, not its caller's. Missing this was the one call site the initial round of this fix didn't cover, caught by a follow-up review.
- **`rescheduleAllSeries()`** (Settings → Rescan Series) iterates by `show_id`, re-checking the original filter (`show_active && !show_paused && !show_recording && show_use_seriesid`) after re-resolving each index — a snapshotted `Int` index list would let a later iteration's `scheduleNextAir(index:)` silently operate on an unrelated show that shifted into a stale slot if an earlier iteration's guide-fetch await let the array mutate.

### `scheduleNextAir`'s "no episode found" fallback keeps `show_end` in sync

When a fresh guide match *is* found, `applyMatch` sets `show_next` and `show_end` together from that one entry. When neither `currentEpisode`/`nextEpisode` nor the title-match fallback find anything — routine for a weekly show (SNL, `20/20`) whose next real airing is usually well outside the guide's ~29h window, so this fires on most hourly ticks between airings, not just on error — the two "no episode found" branches only ever touched `show_next` (bumping it to `now + Series_scan_retry_hours` if stranded, or leaving it as-is if already future). `show_end` was left untouched in both cases, so it could keep whatever a much earlier successful match had set it to — observed drifting to *months* stale for a weekly show that hasn't had a fresh match land in a while. A Discord card or menu display built from that pair before the next real match refreshes both fields together would show a nonsensical Time range (a correct future `show_next` paired with a `show_end` from a completely different, long-past airing). Both branches now also re-derive `show_end = show_next + show_length` minutes as a reasonable placeholder, keeping the pair internally consistent until a real match replaces both. Logs at `.info` when this actually changes something by more than 60s (not on every routine tick where `show_end` was already in sync) — the logged before/after gap doubles as a signal for how stale it had gotten.

**Guide-provider mistagging diagnostics**: `resolveSeriesAir`'s and `scheduleNextAir`'s `apply`/`applyMatch` helpers, and `guideEntryForShow(_:)`, all trust a matching `SeriesID` as authoritative (a differently-formatted display title across affiliates is normal for a genuinely correct match, so a title mismatch alone doesn't reject a SeriesID-confirmed entry) — but all three now log a `.warning` when the matched entry's title doesn't correspond to the show's own title anyway, since that's exactly the shape of a guide-provider crosswalk error (an unrelated program's guide entry mistagged with this show's SeriesID — observed in the wild: an H&I rerun of a *different* show carrying a Star Trek series' own SeriesID). `guideEntryForShow(_:)` additionally hard-rejects (returns `nil`) when SeriesID plainly disagrees, or — for entries without a usable SeriesID on either side — when the title-only fallback doesn't match; see its own doc comment above for that split (its callers already degrade gracefully to "no episode info" rather than a wrong one, so a full reject is safe there in a way it isn't for the scheduling functions, which need to pick *something* to record).

### Recording Failure Retry Backoff

Every `recordFailure` call site (curl exit, no stream URL, disk full, launch error, empty output file) is routed through the private `recordShowFailure(index:reason:)` helper instead of calling `Show.recordFailure(reason:)` directly. It increments `show_fail_count` as before, then starts a cooldown in `showRetryAfter: [String: Date]` (keyed by `show_id`, not persisted) so the idle loop's `readyIndices` filter skips the show until the cooldown expires — without this, a show would retry every `Idle_timer_interval` tick (default 10s) and burn through `Fail_count_setting` in well under a minute.

The cooldown length escalates with consecutive failures, expressed in idle-loop ticks rather than wall-clock time (`static let retryBackoffLoops: [Int] = [2, 3]`, indexed by `show_fail_count - 1`, clamped to the last entry): the 1st failure waits 2 ticks, the 2nd and any further consecutive failure waits 3 (capped) until `show_fail_count` reaches `Fail_count_setting` and `startRecording` pauses the show. Mirrors the shape of `APIBackoff` above, but tick-based rather than an exponential wall-clock delay.

`showRetryAfter` entries are cleared alongside `clearFailures()` at every call site (idle-loop auto-resume, `resumeShow`, `resetAllFailCounts`, `reactivatePausedShows`) and in `deleteShow`, so a manually-cleared or deleted show never carries a stale cooldown.

`reactivatePausedShows()` (Settings → Maintenance's bulk action) also clears `notify_upnext_time`/`notify_recording_time` on every show it un-pauses — same re-arm reasoning as `resumeShow`/`applyResume` below, added 2026-08-20 alongside the identical gap in `WebServer.handleEdit`'s pause-toggle branch (`docs/WebServer.md`'s `/api/edit` field table) after a review sweep found both had been missed by the original fix. Done inline rather than routed through `applyResume` itself, since that helper also fires a per-show `pushShowUpdate` broadcast this bulk loop never had before.

### Fail-Threshold Pause & Auto-Resume

When `show_fail_count` reaches `Fail_count_setting`, `startRecording` sets `show_paused = true` (or `show_active = false` for single-airing shows) and stops attempting to start it. The idle loop's paused-show handling (top of Pass 2) then decides when to un-pause, via `show_next`/`show_end` compared against `now`:

- `show_end <= now` — the airing's window has genuinely ended: un-pause, clear failures, and `scheduleNextAir` to the real next episode. This is the only path a threshold-paused show takes.
- `show_next > now && show_next <= now + 10` — the *next* airing is imminent and hasn't started yet: un-pause so it starts on the next tick. The `show_next > now` guard is required — right after a mid-recording pause, `show_next` still points at the airing that just failed (already in the past), so without the guard this branch was trivially true every tick for the rest of that window, causing an immediate resume → fail → pause loop for the remainder of the hour instead of waiting for `show_end`.

Both branches also clear `notify_upnext_time`/`notify_recording_time` (2026-08-19) — same re-arm reasoning as `resumeShow`/`applyResume` above, for a show that stayed paused through one or both pre-notification windows.

## Device Discovery (`HDHRManager.discoverDevices`)

Three paths run **concurrently**; results merged by DeviceID:

1. **Known hosts** — extracts IPs from `show_url` fields of saved shows → probes `/discover.json`. Sub-second on stable networks.
2. **mDNS** — `http://hdhomerun.local/discover.json`. Handles single-object or array response.
3. **UDP broadcast** — SiliconDust packet sent to each active network interface's subnet-directed broadcast address (e.g. `10.0.3.255:65001`, computed via `subnetBroadcastAddresses(interface:)`), plus the global `255.255.255.255:65001` as a best-effort fallback; waits 2 s, each reply followed up with `fetchDeviceInfo(ip:)`. The UDP reply's TLV payload is parsed for both DeviceID (tag `0x02`) and DeviceAuth (tag `0x2B`), so a device's cloud-guide token is available even when its HTTP server is asleep/unreachable. Global broadcast alone can silently miss devices on setups with a second default route (Thunderbolt Bridge, Internet Sharing) — the kernel routes it into the dead route (`errno 65`/`EHOSTUNREACH`) even though the device's subnet is reachable; only directed-broadcast `sendto` failures are logged as warnings, since the global-broadcast fallback failing in that scenario is expected.

Falls back to **SiliconDust cloud API** (`http://discover.hdhomerun.com/discover.json`) if all three yield nothing. After merging, devices missing `DeviceAuth` are supplemented from the cloud response (needed for EXTEND devices). Session timeouts: 2 s request / 6 s resource.

### EXTEND device (HDTC-2US)
- Has no local `/guide.json` — uses cloud guide API instead.
- `GuideStore.guideURL(for:hours:)` routes to `https://api.hdhomerun.com/api/guide.php?DeviceAuth=...&Duration=N` (hours) when `DeviceAuth != nil`; otherwise `http://{LocalIP}/guide.json?Duration=N`.
- When `Guide_use_xml = true`, `GuideStore.load(for:useXML:)` routes to `GuideStore.xmltvURL(for:)` → `https://api.hdhomerun.com/api/xmltv?DeviceAuth=...` instead. Local-only devices (no `DeviceAuth`) always use JSON even when the flag is on.
- mDNS response omits `LocalIP`; extracted from `BaseURL` host in `HDHRDevice.init(from:)`.
- Local `/discover.json` may omit `DeviceAuth` on some firmware; startup retry + mDNS/cloud discovery recovers.

| `unavailableDeviceShows` | Active shows (recording or scheduled) whose `hdhr_record` is in `unavailableDeviceIDs` |
| `usableDeviceIDs` | `Set<String>` of DeviceIDs that are discovered AND reachable (`isAvailable == true`). Used by the web guide to determine active vs. inactive tuner boxes. Inactive tuners are dimmed and non-selectable but still listed with their assigned shows. |
| `nextShowMinutes` | Minutes until nearest active show; drives the menu bar icon's amber-lit "show soon" state when ≤ 30 |
| `availableDeviceCount` | Excludes devices with missing lineup or guide; used in status message |
| `onAirNow(for:at:)` | Returns one `(channel: LineupEntry, entry: GuideEntry)` per unique on-air channel for a device at `date` (default `Date()`), sorted favorites-first then by channel number. Used by `WatchNowView` and `WebServer.buildNowJSON`. |
| `activeRecordingChannels(for: deviceId)` | Channels on this device with a show whose `show_recording == true`. Shared, channel-scoped source of truth for the "recording" ring/badge — used by both `WebServer.buildGuideGridHTML` and `WatchNowView` so the two surfaces can't drift apart. |
| `pendingRecordingChannels(for: deviceId)` | Channels whose managed show's recording window has opened (`show_next <= now < show_end`) but `show_recording` hasn't flipped true yet — the brief, normal startup lag between a show's scheduled time and `RecordingManager` actually flipping the flag. Excludes a show currently sitting out a missed-start retry backoff (`showRetryAfter` in the future) — that show isn't capturing anything, so it must not read as "recording." Also excludes a show whose current airing will be skipped as an already-recorded duplicate (`willSkipCurrentAiring(_:)`, mirroring `startRecording`'s own SKIP-branch check) — without this, a skip-eligible airing would sit in its `show_next...show_end` window reading as "recording" on the web guide/Watch Now for its entire air window instead of showing the skip badge, since `show_recording` deliberately never flips true for it. Same shared-source-of-truth role as `activeRecordingChannels` above; see `issues_resolved.md` for both fixes. |
| `tunersFull(for: deviceId)` | Returns `true` when every tuner on the device is occupied. Delegates to `activeTunerCount(for:)` — `max(status.json hw count, recordings + VLC)` — so it also honors tuners locked by another machine running this app against the same physical device, not just this instance's own recordings. Never count recordings alone — watching and recording occupy tuners equally, *except* watching a recording via the relay. Used by `startRecording`, `WatchNowView`, and `WebServer.handleRecord`. |
| `activeTunerCount(for: deviceId)` | Returns the current active-tuner count for a device as `max(status.json hw count, recordings + VLC)` (same `vlcOccupiesTuner(for:)` helper). Used by `broadcastRecordingEvent` and `pushFreshTunerCounts` to push accurate badge counts to the web guide via SSE. |
| `vlcOccupiesTuner(for: deviceId)` | `true` only when the in-app VLC window is open on this device **and** it isn't playing the recording relay (`VLCBridge.shared.recordingShowId == nil`). Without this distinction, `tunersFull`/`activeTunerCount` would count watching your own in-progress recording via Watch Now! as consuming a tuner it never touches — undermining the entire point of the relay (see `watchRecordingInApp(_:)` and `docs/WebServer.md`). |
| `vlcLiveChannel(for: deviceId)` | Returns the `GuideNumber` the in-app player is live-watching on this device (via `VLCPlayerWindowManager.currentChannelNumber`, set in `open()`), or `nil` when not applicable — including the relay case, since `vlcOccupiesTuner(for:)` gates it. Used by `WebServer.buildGuideGridHTML`/`recsByDevJS` and `WatchNowView`'s ring-state computation to exclude this instance's own live-watch channel from the "hardware tuner in use by something we don't control" set — without it, clicking Watch on a live (non-recording) channel would immediately flag that same channel as in-use-by-another-tuner for the person watching it. |

## Web Server

`webServer: WebServer` — `NWListener`-backed LAN HTTP server (see [WebServer.md](WebServer.md)).

| Property / Method | Description |
|---|---|
| `@Published webServerRunning: Bool` | `true` once NWListener reaches `.ready` state |
| `@Published webServerError: String?` | Non-nil when the listener fails (port in use, OS error, etc.) |
| `setupWebServer()` | Starts, restarts, or stops the server based on `config.Web_server_enabled` and `config.Web_server_port`. Called at step 4 of `startup()` and again whenever Settings saves a changed web server config. |
| `ensureWebServerRunning()` | Increments `internalWebServerUseCount`; starts the server if not already running. Called from `AddShowView` guide step's `onAppear`. |

## Discord Embed Flow

All recording lifecycle events (failure, start, progress, end) edit the **same Discord message** rather than posting new ones. The shared message ID (`show.discord_start_msg_id`) is the key:

1. **Recording starts** — `startRecording` inserts the show ID into `pendingDiscordStart: Set<String>`. The embed is **not sent immediately** — it is deferred to prevent a ping for recordings that fail in the first few seconds.
2. **First idle-loop confirmation** — on the first tick where `show_recording == true` and `recordingManager.isRunning()` confirms curl is alive, the show ID is removed from `pendingDiscordStart` and `discordRecordingCard` fires "🔴 Recording Started". If a failure card was posted earlier (e.g. a failed prior attempt for the same show), it edits that card; otherwise it creates a new one via `sendDiscordEmbedCapturing` (`?wait=true`), capturing the message ID into `show.discord_start_msg_id`. If curl has already exited before this tick, the start embed is suppressed and only the failure embed is sent. **Also captures `discordEpisodeSnapshots[show.show_id]`** — episode number/title, synopsis, genre tags, and new-episode flag from `guideEntryForShow(show)` at this exact moment, the last point `show.show_next` is guaranteed to still refer to the airing actually recording (see step 5 below for why this matters).
3. **Failure** (curl exits unexpectedly, no stream URL, disk full, launch error, or empty output file — all five routed through `recordShowFailure(index:reason:)`, see "Recording Failure Retry Backoff" above) — fires an event-specific embed ("❌ Recording Failed", "💾 Recording Skipped", etc), with the `"Reason"` field carrying the actual underlying cause (HDHR device error, decoded curl exit code, or disk/URL detail) rather than a generic string. The empty-output-file terminal failure in `stopRecording` prefers a fresh `readAndClearHDHRError` read taken *before* `teardownRecordingState` (which would otherwise delete the header file first), then falls back to `show.show_fail_reason` — but only when `failedThisAttempt: Set<String>` confirms a FAIL was actually recorded during *this* recording attempt (inserted by the idle-loop FAIL branch, cleared when `startRecording` launches a fresh attempt); `show_fail_count` alone can't distinguish "this attempt already failed" from "count hasn't fully decayed from an unrelated failure several episodes ago," since a success only decrements it without clearing the reason. The fold-in is also idempotent (skipped if the stored reason already ends with the same suffix), so repeated empty-file failures can't compound the message without bound. If `discord_start_msg_id` is already set (prior attempt card), the event edits that card; otherwise it creates a new one and captures the ID. The ID is **not** cleared on a mid-recording failure — a subsequent retry start will edit this failure card, keeping the entire lifecycle in one Discord message.
4. **Progress update** — the idle loop checks once per 5-minute boundary: if `show_recording && !discord_start_msg_id.isEmpty && Discord_on_progress`, it calls `editDiscordEmbed` with an "⏺ Recording In Progress" embed containing `"Xm elapsed · Ym remaining"`.
5. **Recording ends** — all three terminal outcomes (natural completion with data, the empty-output-file failure, and the fail-threshold "⏸ Recording Paused" event) go through `fireDiscordCard(..., clearIdAfter: true)`. The natural-completion path previously called `discordShow(editMessageId:)` directly, bypassing the per-show chain entirely — if a "Recording Started" CREATE was still in flight (slow webhook) when the recording finished, that direct call could read `discord_start_msg_id` as still empty and fire a second, ID-less "Recording Complete" POST via `discordShow`'s fire-and-forget path, orphaning it once the Started card's id landed afterward with nothing left to clear it. Routing through `fireDiscordCard` closes that gap the same way it does for the other two terminal events. In all cases `discord_start_msg_id` is cleared to `""` after the terminal event — `discordEpisodeSnapshots[show.show_id]` is cleared in the same `clearIdAfter` block, same lifecycle boundary. This ordering matters: the natural-completion path calls `scheduleNextAir(index:)` *before* firing the "Recording Complete" card, which advances `show.show_next` on to the *next* airing — a live `guideEntryForShow(show)` call inside `buildDiscordShowEmbed` at that point would resolve against the wrong (future) time and silently return nothing or the wrong episode. `buildDiscordShowEmbed` prefers the snapshot captured in step 2 for exactly this reason; confirmed via a real Discord screenshot (2026-08-12) where a "Recording Complete" card was missing its episode number and synopsis lines that an earlier "Tuner Conflict" card for the same show had shown correctly.

6. **App restart recovery** — `reattachRecordings()` (step 2 of startup) scans for shows with a non-empty `discord_start_msg_id` that were not reattached as actively recording. For each, it sends a recovery embed: "✅ Recording Complete" if `show_recording_path` file has non-zero size, or "⚠️ Recording Interrupted" otherwise. The ID is cleared before the send so a crash during the PATCH doesn't re-trigger on the next launch.

**Helper split**: `discordEffectiveURL(enabled:webhookURL:)` is the shared gate — returns the URL to post to, or `nil` when `enabled` is false, the URL is empty, or `Discord_enabled` is false (for default-webhook calls). `buildDiscordShowEmbed(event:show:color:extra:)` builds the `[String: Any]` embed dict — description (bold title + "🆕 NEW" suffix when applicable + episode number/title line + synopsis, truncated to 200 chars), `Channel`/`Type`/`Time` fields plus any event-specific `extra` fields, and a `Tags` field from the guide's genre `Filter` (falling back to the show's own stored `show_genre` when no live guide entry is available). Episode number/title/synopsis/tags/new-flag come from `discordEpisodeSnapshot(entry:show:)` — either the snapshot captured at "Recording Started" (`discordEpisodeSnapshots[show.show_id]`, see step 2/5 above) when one exists, or a fresh `guideEntryForShow(show)` lookup otherwise (correct for pre-recording events like Show Added/Up Next/Recording Soon/Tuner Conflict, where `show_next` hasn't moved yet). `discordRecordingCard(showId:event:color:enabled:extra:)` is the `@MainActor async` primitive used by all lifecycle paths — it checks `discord_start_msg_id`: if set, calls `editDiscordEmbed`; otherwise calls `sendDiscordEmbedCapturing` and stores the returned message ID.

Every call site fires `discordRecordingCard` through `fireDiscordCard(showId:event:color:enabled:extra:clearIdAfter:)` rather than calling it directly. Each call chains behind whatever call is already running for that same `show_id` via `discordCardTasks: [String: Task<Void, Never>]` — the new call captures the previous entry's `Task` (if any), awaits it first inside its own detached `Task { @MainActor in ... }`, then does its own send, so at most one `discordRecordingCard` is ever actually in flight per show at a time, with no busy-polling and no latency floor. (This replaced an earlier `discordCardInFlight: Set<String>` design that polled with `Task.sleep` every 150ms — same guarantee, but chaining mirrors `ensureLineupLoaded`'s existing `loadingLineupTasks` idiom instead of reinventing a weaker one, and makes clearing a stale dict entry in `deleteShow` always safe: removing the entry doesn't affect an already-started `Task`, it only stops a future call from chaining behind it.) Without this serialization, two lifecycle events racing for the same show — e.g. a "Recording Started" confirmation firing while a fail-threshold "Paused" card from the previous attempt is still awaiting a slow CREATE round trip — could both observe `discord_start_msg_id` empty and each capture their own message id, silently orphaning one of the two cards (or, worse, a delayed `clearIdAfter` from the older send stomping the id the newer send just captured). Because the chain guarantees only one send per show_id is ever touching `discord_start_msg_id` at a time, `clearIdAfter: true` can unconditionally clear the field after its own `await` returns.

`discordShow` routes to either `sendDiscordEmbed` (fire-and-forget POST, never captures an ID) or `editDiscordEmbed` based on `editMessageId`, and is now used only by `discordWebDelete` (web-delete) and non-terminal notifications like "Up Next"/"Recording Soon" that don't participate in the shared-card lifecycle at all — every event that's part of a recording's card lifecycle (including natural completion, as of the fix above) goes through `fireDiscordCard`/`discordRecordingCard` instead, so the chain covers the entire lifecycle with no gap. `sendDiscordEmbedCapturing` and `editDiscordEmbed` are free functions in `DiscordNotifier.swift`.

**SIGTERM race**: `discordCardTasks`'s async `discord_start_msg_id` clear happens only after its Discord network round trip returns, but `idleLoop`'s `saveConfig()` persists a show's terminal state to disk immediately — a `pkill`/SIGTERM (routine during `deploy.sh`'s stop-before-rebuild step) landing in between could previously persist a stale, uncleared `discord_start_msg_id`, which `reattachRecordings()` would then mistake for an unfinished recording on next launch and post a bogus recovery embed for. The SIGTERM handler (`startup()`) now waits for any pending `discordCardTasks` (capped at 2s via a `withTaskGroup` race against a timeout, skipped entirely when nothing is pending) before its final `saveConfig()` and re-raise.

## @Published Safety Rule

In a SwiftUI `.menu`-style `MenuBarExtra`, the menu body re-evaluates on every `@Published` change.

**Never assign `guideByDevice = ...` unconditionally after a failed/empty response.** A failed load that assigns `guideByDevice` triggers `didSet → rebuildMenuEntries → @Published changes → re-eval → ...` at ~35ms/loop, freezing the menu. Guards: `ensureGuideLoaded` only assigns when `guideStore.channels(deviceId:)` is non-empty; `guideApiBackoff: [String: APIBackoff]` enforces exponential backoff (1 → 5 → 15 → 30 → 60 min) on failed devices.

`rebuildMenuEntries()` is called from `guideByDevice.didSet` (after every guide load) and from the idle loop (guarded by `menuIsOpen`). It rebuilds: `menuScheduledEntry`/`menuUpcomingSlots` (pre-computed guide matches for scheduled/paused menus), and `conflictingShowIDs`/`conflictBeatenByFavorite` (one conflict pass instead of one per open). It previously also rebuilt `managedShowBySeriesID`/`managedShowByTitle`, a device-agnostic (not channel-scoped) O(1) show lookup — removed 2026-08-15 once its one real consumer, `WebServer.buildNowJSON`'s `/api/now.json`, was switched to the same channel-scoped `ManagedGuideMatcher` the guide grid uses (see `issues_resolved.md`); nothing else read it (`WatchNowRow` had already moved off it earlier — see `docs/WatchNowView.md`'s `managedShow` note). `channelImageURLs` (logo URL map for WatchNow) is **not** part of `rebuildMenuEntries()` — it only depends on `guideByDevice`, which changes on guide load (~hourly), not per tick, so it lives in its own `rebuildChannelImageURLs()`, called from `guideByDevice.didSet` and once after `fetchAllGuides()` (guarded by `menuIsOpen`, same as `rebuildMenuEntries()`) but deliberately not from the per-tick idle-loop call — folding it into `rebuildMenuEntries()` used to mean every idle tick re-scanned every channel's `ImageURL` even though guide data hadn't changed since the last tick.

`guideByDevice.didSet` also increments `guideGeneration: Int`, unconditionally on every actual assignment (regardless of the `menuIsOpen` guard around the two rebuilds above — since a failed/empty load is never assigned in the first place per the guard described above, this only fires on real guide reloads) — a cheap monotonic counter other views can key a `.task(id:)`-cached computation on to force a recompute after any guide reload, without needing to inspect `guideByDevice`'s actual contents themselves (e.g. `AddShowView`'s `otherAiringsCache`, see `docs/AddShowView.md`).

`fetchDeviceStatus(for:)` has two independent `menuIsOpen`-related behaviors, refined 2026-08-09: `deviceTunerOccupancy` (the menu header's "X/Y" live tuner count — reflects real hardware occupancy from *any* consumer, not just this app's own recordings; verified live against a real device, showing "1/2 ⚠ app expects 0" while the menu was open, correctly tracking an external TV using a tuner this app didn't initiate) is now written whenever the freshly-polled **active-tuner count** (`tuners.filter { $0.VctNumber != nil }.count`) differs from the currently-stored value's own count, **even while `menuIsOpen`** — a real occupancy change is worth the occasional submenu-dismiss risk, since showing a stale "X/Y" for as long as the menu happens to be open would otherwise mask another consumer grabbing a tuner. Deliberately compares just the count, not the full `tuners` array/struct — per-tuner fields like `SignalQualityPercent` fluctuate on essentially every poll even when occupancy hasn't changed, so a full-struct comparison would defeat the point (every tick would look "changed"). Tradeoff, found during the v2.0.2 pre-release review: per-tuner identity (`Resource`/`VctNumber`/`TargetIP`) in the stored value can now go stale whenever the count doesn't move, **even with the menu closed** — a real widening vs. the pre-fix behavior, where staleness was bounded to "while the menu happens to be open." Two known readers of that per-tuner detail (not just the count) — `stopRecording`'s optimistic tuner-clear (`AppState.swift`) and the web UI's per-tuner dev-bar dropdown (`WebServer.swift`'s `recsByDevJS`, see `docs/WebServer.md`) — both just display/copy through whatever's stored, so a stale entry there self-heals on the next count-changing poll rather than needing anything more.

**Cooldown, not unconditional, while the menu is open**: a count-changed check alone doesn't bound how *often* it fires — an external consumer channel-surfing can flip the locked/unlocked count on consecutive idle-loop ticks, which would otherwise re-glitch the open menu every ~10s for as long as the surfing continues (found by `invariants-reviewer` during the v2.0.2 pre-release pass). `lastMenuOpenTunerWrite: [String: Date]` + `menuOpenTunerWriteCooldown` (30s) caps a real change to disrupting an open menu **at most once per 30 seconds** per device; closed-menu writes to `deviceTunerOccupancy` itself are never throttled (no glitch risk there — `!menuIsOpen || cooldownElapsed`). The separate `/tunerN/vstatus` fetch (which updates the per-tuner signal-quality `tunerStatus`, not `deviceTunerOccupancy`) still skips entirely while `menuIsOpen`, unchanged — signal display isn't as safety-relevant as tuner availability, so the older skip-outright behavior stays for that one. Signal alerting (Discord notifications, `signalDropoutTicks`, `ChannelSignalStore` recording) still runs unconditionally either way because it is not display-only.

**Web-guide push on a real count change**: inside that same `countChanged` block, `fetchDeviceStatusUncached` also calls `webServer.broadcastGuideChangeEvent(type: "tuner_occupancy_changed", ...)` (added 2026-08-11, found live-verifying the tuner-popover title fix) so the web guide's tuner popover (`recsByDevJS`) and `.g-st-inuse` ring stay in sync with a hardware-only occupancy change — previously that data could sit stale for up to the hourly `guide_refreshed` broadcast despite `deviceTunerOccupancy` itself updating within one idle tick. Unlike the `deviceTunerOccupancy` write above, this push has its **own** dedicated per-device cooldown (`lastGuideOccupancyBroadcast` + `guideOccupancyBroadcastCooldown`, 15s) that applies regardless of `menuIsOpen` — a channel-surfing external consumer flipping the count on every idle-loop tick would otherwise re-trigger a full grid rebuild + gzip (`buildGuideGridHTML`/`prebuildPageHTML`) every ~10s indefinitely, menu open or not. See `docs/WebServer.md`'s "Events pushed" table (`tuner_occupancy_changed`).

**Conflict detection** uses `candidateShows = shows.filter { show_active && !show_paused }` — this includes currently-recording shows (`show_recording == true`), unlike `activeShows` which excludes them. A scheduled show that overlaps an already-recording show is therefore correctly flagged. Detection is a **per-device greedy tuner-slot simulation**, not an all-pairs overlap count: `candidateShows` is grouped by `hdhr_record`, and within each device the shows are sorted by `(show_next, favorite-first tiebreak)` — mirroring the real recording-start priority — then walked in order, assigning each to the first tuner slot that's free by its `show_next` (`slotFreeAt: [Date]`, one entry per `TunerCount`). A show that finds no free slot is the one flagged into `conflictingShowIDs` — only the actual loser(s), not every member of an overlapping cluster. If a flagged non-favorite show lost specifically to a favorited competitor (one whose window covers its `show_next`), its `show_id` is also added to `conflictBeatenByFavorite: Set<String>`, which feeds more specific menu/web tooltip text than a generic conflict warning. `conflictingShows(for:)` returns the actual contending `Show`s for a given show (same overlap definition as `hasConflict`, sorted by channel) so the menu's conflict submenu can list channel/title/episode instead of a bare warning. `conflictNotifiedEpochs: [String: TimeInterval]` (keyed by `show_id`, value = `show_next` epoch) is cleared per show on each `scheduleNextAir`, fail-threshold pause, and manual stop — so stale entries don't accumulate across airings.

## Show Delete / Skip (`deleteShow`, `skipRecording`)

`skipRecording` calls `recordingManager.stop(showId:)` directly (sends SIGKILL to curl and releases the show's sleep assertion — see `docs/RecordingManager.md` for why SIGTERM isn't used). `deleteShow` instead routes through the full `teardownRecordingState(index:)` when the show being deleted is actively recording (`show_recording == true`) — a bare `recordingManager.stop()` alone skipped the tuner-occupancy optimistic clear, the `recording_stopped` broadcast, and `tunerStatus`/`signalDropoutTicks` cleanup, leaving the web UI showing a recording tuner for up to one idle-tick until the next hardware poll self-corrected. When the show isn't recording, `deleteShow` falls back to the same bare `recordingManager.stop()` (harmless no-op). Both functions then call `VLCPlayerWindowManager.shared.closeIfPlaying(showId:url:)` — if the in-app VLC player is currently streaming the deleted/skipped show (matched by relay showId or stream URL) the player window is closed, freeing the tuner.

`deleteShow` removes the show from `shows`, then purges every show_id-keyed side table before saving — not just `showRetryAfter`, but also `conflictNotifiedEpochs`, `missedStartNotifiedEpochs`, `pendingDiscordStart`, `failedThisAttempt`, `suppressStartDiscord`, `discordCardTasks`, `duplicateOverrideUsedThisAttempt`, `tunerStatus`, `signalDropoutTicks`, and `discordEpisodeSnapshots` (see step 5 of the Discord lifecycle above). Since `show_id` is never reused, skipping any of these would leak an entry for the life of the app session; a long-running install that adds/deletes shows over weeks would otherwise grow these dictionaries/sets without bound. `skipRecording` additionally marks `show_paused = true`, sets `show_fail_reason = "Skipped"`, and calls `scheduleNextAir` to advance to the next airing.

This cleanup list has a regression test (`Tests/hdhr_VCRTests/AppState/AppStateDeleteShowCleanupTests.swift`) that populates the original ten tables for a show, calls `deleteShow`, and asserts every one is empty — which is why these are `internal` (no `private`) rather than truly private: `@testable import` doesn't reach `private`, and testing the real properties directly avoids a hand-duplicated shadow list in the test that could itself drift out of sync with this cleanup. `discordEpisodeSnapshots` was added later and is correctly cleared by the code above, but isn't yet exercised by this test — tracked in `TODO.md`. See also `docs/Config.md`'s "Test seam" note — this test is exactly why `ConfigManager` needed one (`deleteShow` calls `saveConfig()`).

## Quit (`quit()`)

All three exit branches call `VLCBridge.shared.releasePlayer()` before terminating so the in-app player starts releasing its HDHR tuner immediately. As of 2026-08-15, `releasePlayer()`'s actual libvlc stop/release calls run on a background queue (`docs/VLCBridge.md`'s `libvlcQueue` — moved off the MainActor to avoid a real deadlock risk), so `NSApplication.terminate(nil)` on the very next line can fire before that native teardown has actually completed. This is an accepted tradeoff, not a bug: process exit force-closes the underlying socket either way, and waiting here would reintroduce the exact blocking-on-libvlc risk this change exists to avoid — quitting while stuck would be worse than quitting slightly before libvlc's own handshake finishes.

- **No recordings** — `releasePlayer()` → `recordingManager.stopAll()` → `NSApplication.terminate(nil)`
- **Keep Recording & Quit** — `releasePlayer()` → `NSApplication.terminate(nil)` (curl orphaned to launchd; reattach on relaunch via `reattachRecordings()`)
- **Stop Recordings & Quit** — `releasePlayer()` → `recordingManager.stopAll()` → `NSApplication.terminate(nil)`
