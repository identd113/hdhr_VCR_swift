# Failed Approaches

Not an issue tracker — this is a record of things that were tried repeatedly, failed, and eventually either abandoned or solved a different way. Kept separate from `ISSUES.md`/`issues_resolved.md` (which track specific bugs against current code) because these entries are about *technique*, often against code that no longer exists — the lesson is the point, not the bug.

---

## Channels DVR compatibility for the virtual-tuner relay

**Context**: `VirtualTunerService`/`WebServer`'s virtual-tuner relay (`docs/VirtualTunerService.md`) — while a show records, this app advertises a temporary HDHomeRun-like tuner so another instance can watch the in-progress recording. 2026-09-02's UDP protocol fix (adding DeviceType/BaseURL/TunerCount/LineupURL TLVs, matching a real EXTEND byte-for-byte) got the relay showing up for the first time in a real third-party client — the iOS "Channels" app, used in its standalone server-less mode (no separate Channels DVR Server involved). But Channels would only ever discover the device (repeatedly, correctly, over UDP) and — at most — fetch `/discover.json` once over HTTP; it never once requested `/lineup.json`, no matter what was tried in its UI, so the source always showed with no channels ("(null)" name, empty lineup).

**What was tried, in order, and why each failed to change Channels' behavior at all:**

1. **`FirmwareName`/`FirmwareVersion`/`DeviceAuth` added to `/discover.json`** — a live `curl` of a real EXTEND's own `/discover.json` showed it always carries these three fields, and researching known-working fake-tuner projects (Threadfin, the xTeVe fork) confirmed their own `Discover` struct carries the same three — strong circumstantial evidence, but adding them didn't change Channels' behavior at all: still exactly one `/discover.json` GET, then nothing.
2. **The same synthetic `DeviceAuth` added to the raw UDP `DISCOVER_REPLY` TLV set too** (tag `0x2B`, matching the real device's own UDP reply, which also carries it) — on the theory that Channels validates the UDP reply itself before ever bothering with HTTP. No change.
3. **`ScanPossible: 1` + `SourceList: ["Antenna","Cable"]` in `/lineup_status.json`** (a real device reports `ScanPossible:1`; this relay had been reporting `0`) — this was the only change that visibly did something: Channels' UI then showed "Scan For Channels — Error: Unable to scan Antenna". So `/discover.json` was reachable, but no scan or lineup fetch ever actually followed.
4. **Implemented `POST /lineup.post?scan=start`/`?scan=abort`** (previously a bare 404) to make that scan attempt succeed immediately, since this relay's lineup is always already current and there's nothing to actually scan. Verified live via `curl` — clean `200 OK`. Channels' behavior didn't change: no new `/lineup.post` request was ever observed in the server's own request log on a repeat attempt, with or without first force-quitting the app, removing/re-adding the source, or toggling the source's "Enabled" switch back on (a red herring — the "Unable to scan Antenna" message on screen was a stale error left over from *before* this fix, never actually cleared by a fresh attempt).
5. **A second listener on port 5004** (the real HDHomeRun protocol's fixed tuning port, separate from the JSON API's port 80/1980) — live-comparing against the real EXTEND showed it accepts a direct `GET /auto/vX.X` on 5004 with `Server: HDHomeRun/1.0`, while this relay had nothing listening there (connection refused). Theory: Channels does a pre-flight reachability check on 5004 before ever trying `/lineup.json`. Added the listener, verified live it served the stream correctly on 5004 — no change in Channels' behavior; the manual "Add Tuner" flow still stalled after one `/discover.json` GET.
6. **Auto-discovery scan instead of manual "Add Tuner"** — tried once the UDP+HTTP shape was as close to the real device as achievable. Result was *worse*, not better: zero HTTP requests at all, not even the one `/discover.json` GET the manual flow always got. Auto-scan appears to filter the device out purely from the UDP reply, before ever trying HTTP.

**Root cause: never identified.** Every change that was independently verifiable against real hardware (byte-for-byte UDP diffing, live `curl` comparison of every JSON endpoint) was applied, and none of them moved Channels' observed behavior even slightly, except step 3 which made things *worse* in a way step 4 then quietly fixed without changing the overall outcome. That consistency across six independently-plausible, verified-correct changes is itself the signal: whatever's actually blocking Channels almost certainly isn't discoverable by further server-side protocol tweaking from this side of the wire. Likely candidates, untested: an allowlist/vendor check unrelated to protocol correctness, a client-side bug specific to non-genuine devices, or something only visible via an actual packet capture of Channels' own traffic (not just this server's request log) — none of which were pursued given the investigation's time cost relative to the underlying feature (hdhrVCRplus-to-hdhrVCRplus relaying, unaffected throughout and separately verified working end-to-end) already working correctly.

**What was kept** (independently justified, not reverted): the original 2026-09-02 UDP TLV fix (DeviceType/BaseURL/TunerCount/LineupURL) — this is what made the relay discoverable via real UDP broadcast at all, confirmed via a real client actually seeing the device for the first time; the `FriendlyName` "`<source>-Relay`" naming (a separate, explicit feature request, unrelated to this investigation); and the diagnostic request logging added along the way (`docs/VirtualTunerService.md`'s "Diagnostic request logging" section) — generically useful for debugging *any* future client's discovery behavior, not just this one.

## Pinning a scroll-synced header/column over a bidirectional SwiftUI ScrollView (macOS, pre-15)

**Context**: `CableGuideView.swift`, the native cable-guide grid (now fully removed — replaced by the WKWebView-embedded web guide). The grid needed a time-axis header and a channel-label column that both stayed fixed while the grid itself scrolled horizontally and vertically.

**What was tried, in order, and why each failed:**

1. **Time header inside the ScrollView with `LazyVStack(pinnedViews: [.sectionHeaders])`** — works for vertical-only scroll, but the header scrolls away horizontally along with the grid content, since pinning only holds a section header in place along the scroll axis it's pinned for.
2. **Nested ScrollViews with offsets synced via `PreferenceKey` + `GeometryReader`** — the offset `PreferenceKey` doesn't fire during AppKit-driven scroll *momentum*. It updates fine for a slow manual drag, then visibly lags or snaps on momentum release, because SwiftUI's preference propagation only runs on SwiftUI layout passes, not on every AppKit scroll frame.
3. **10 further documented layout permutations** (combinations of the above, plus various offset-clamping and animation-suppression attempts) — all inherited variants of the same root problem: nothing in pure SwiftUI observes AppKit's own scroll-frame cadence.

**What actually worked**: Don't try to keep the header/column inside the scrolling content at all.
- Channel label column: pinned **outside** the `ScrollView` entirely as a fixed left column (`HStack { channelColumnFixed | ScrollView }`).
- Time header: also external, shifted via `.offset(x: -timeHeaderOffset)` to track horizontal scroll position.
- Scroll position itself: captured via `NSViewRepresentable` wrapping the scroll view's `NSClipView`, observing `NSView.boundsDidChangeNotification` directly — this fires on every AppKit scroll frame, including momentum, unlike the SwiftUI `PreferenceKey` path.
- A 1-pt change threshold plus `Transaction.disablesAnimations` around the offset write killed residual jitter.
- Noted at the time: `LazyVStack(pinnedViews:)` inside a bidirectional `ScrollView` only behaves correctly on macOS 15+ — a real deployment-target constraint discovered in the course of this, independent of which approach was used.

**The generalizable lesson** (this is the part worth remembering even though `CableGuideView` itself is gone): if you need to react to AppKit scroll state — position, momentum, velocity — on macOS, go straight to `NSViewRepresentable` + `NSView.boundsDidChangeNotification` (or the equivalent `NSScrollView` notification) rather than trying to make SwiftUI's own layout/preference system track it. SwiftUI's tools only fire on SwiftUI's own layout cadence, which does not include AppKit-driven momentum scrolling. macOS 15's native `onScrollGeometryChange` closes this gap when the deployment target allows it.
