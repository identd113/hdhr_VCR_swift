# Issue Log

Historical record of bugs encountered during development. Used as a "don't repeat this" reference during code reviews. Unrelated bugs found during work go here rather than fixed inline — note the resolving commit when done. Deferred features go in `TODO.md`.

**This file holds only what's still open, or accepted as-is (won't-fix / by-design / too marginal to schedule).** Once something is actually fixed, its entry moves to [`issues_resolved.md`](issues_resolved.md) rather than staying here — that file is the "how was X fixed" archive, this one is "what still needs attention." Findings about *technique* (things tried repeatedly and abandoned, independent of any specific still-open bug) live in [`FAILED_APPROACHES.md`](FAILED_APPROACHES.md) instead of either issue file.

**Format**: each issue has a status (`OPEN` or `ACCEPTED`), a brief description, root cause, and a fix note if one's been scoped but not done.

*(Found 2026-09-07, confirmed still open and reproducible 2026-09-09 — this now gets its own entry rather than staying a footnote inside the unrelated "cadence fix" RESOLVED entry in `issues_resolved.md`.)*

- **VLC-side FEED playback stalls for tens of seconds at a time — client demux/decode freezes while the relay keeps delivering data normally.** Signature, confirmed identical across every reproduction: `windowVisible=true` (rules out a backgrounded window), server-side bytes flowing continuously and at a normal rate throughout, but the client's own `pos`/`displayed` tick counters frozen at `+0ms`/`+0` for the whole duration. Not a delivery problem — the relay-cadence fix (`issues_resolved.md`) genuinely fixed the *original* burst/silence bug; this is a separate, still-unfixed VLC 3.0.23 client-side issue.
  **Reproduced live 2026-09-09** against a real, currently-recording show ("Late Night With Seth Meyers"), post-cushion-revert (i.e. with only the already-shipped cadence fix active, no experimental changes): two stalls in one session, one lasting **~36s** (self-recovered), one lasting **90s+** (still ongoing when last checked) — both longer than the originally-documented 66-81s range, so if anything this is getting *worse* under some condition not yet identified, not better.

  **Reproduced live again, 2026-09-09, later the same day, this time with `feedLiveEdgeCushionBytes` still active (git never actually reverted it despite the entry above's "post-cushion-revert" framing — see `docs/VirtualTunerService.md`'s doc-drift flag, filed earlier this same session before this retest)**: real single-episode recording ("Today," device `105404BE`, channel 11.1), watched cross-machine from the laptop. `displayed` pinned at `+0` from the very start of playback for ~90+ seconds, then a second stall shortly after recovery. Matches the signature above exactly.

  **First real thread-level evidence, 2026-09-09 — the debugger/sampler step this entry's own "next step, not yet tried" line called for.** Two clean `sample <pid> 5` captures taken on the laptop squarely mid-stall (confirmed via `[VLC] tick` showing `displayed=+0` immediately before and after each capture) both show the same pattern: the network-read thread (`vlc_stream_ReadPartial` → `vlc_tls_Read` → `poll`) and the "prefetch" plugin's own consumer thread (`_pthread_cond_wait`) both >99% blocked/idle for the *entire* 5-second window (4068-4072 of ~4077 samples each), while the `libts_plugin.dylib` TS-demux frames account for only 1-2 samples total. This is despite the source relay's own log confirming continuous, gap-free byte delivery throughout the same window (hundreds of KB/tick, "caught up to live edge" repeating normally, no send timeouts/errors). So during a stall, VLC's own demux pipeline goes essentially idle — not backed up processing a burst, not blocked *trying* to read — while bytes keep arriving on the wire. Doesn't yet pin an exact root cause (a real trailing question: was `poll()`'s wait genuinely against an empty socket buffer, or did it fail to wake for data that had already arrived? — the sample alone can't distinguish those), but rules out "the demuxer is just slow/backed up" as the explanation.

  **Cushion disabled 2026-09-09 as a result — `WebServer.swift`'s `feedLiveEdgeCushionBytes` set to `0`** (see that constant's own updated doc comment, and `docs/VirtualTunerService.md`'s live-edge cushion entry): two independent live-tested rounds (2026-09-08 and this session) both found the cushion made this same stall worse, not better, so it's disabled — mechanism left in place, gated on `> 0`, in case a future investigation wants to revisit it rather than reinvent it. **Retested immediately after, same show/channel/machines**: 4m39s of continuous, clean playback (`rate=1.000`, `lost=0` every tick, `displayed` tracking real-time throughout, zero stall events) — a marked improvement over both cushion-active sessions above, which each hit a stall within the first ~90 seconds. **Not enough to call this fixed** — a single clean run doesn't rule out the same intermittent behavior the 2026-09-09-early entry above already showed getting *worse* under some still-unidentified condition even without the cushion; needs a longer, repeated retest (ideally the same 7+ minute standard this investigation has used before) before this issue can be downgraded or closed. The underlying VLC demux/decode-side root cause remains unconfirmed either way — disabling the cushion removed a likely-aggravating factor, not a proven fix.
  **Diagnostic attempt, dead end**: added a real `libvlc_log_set` callback (`VLCBridge.swift`, now permanent infrastructure — see `docs/VLCBridge.md`) to route every libvlc-internal log message directly into `glog()`, specifically to catch what the "prefetch" stream_filter module (the prior investigation's own named suspect) is doing during a live stall. The callback mechanism itself works (confirmed — real startup/module-load messages flow through), but even combined with a temporary `--verbose=2`, it never emitted a single demux/stream_filter/decoder-level message during either reproduced stall — only the same startup-only output `--file-logging` alone had already hit a ceiling on. Best guess: this VLC.app build's demux/decode modules have debug-level `msg_Dbg()` tracing compiled out entirely, in which case no amount of verbosity tuning will ever surface it.

  **Chunk-size experiment, 2026-09-09 — reverted `watchRecordingChunkSize` from the 2026-09-07 small-chunk "cadence match" (1504 bytes) back to a generous single size (37.6KB, matching `watchRecordingBacklogChunkSize`), after comparing against Jellyfin's own HDHomeRun relay** (`jellyfin/jellyfin`'s `ProgressiveFileStream.cs`/`SharedHttpStream.cs` — a mature, widely-deployed project solving this exact problem, using one ~80KB buffer everywhere with no small-chunk cadence-matching at all). Kept the already-proven 20ms live-edge poll interval unchanged, isolating the one variable the 2026-09-07 fix never tested alone. **Live-tested result: no improvement — user-observed live** ("it plays longer, like 10 seconds, but then pauses for like 20") **and log-confirmed**: `displayed` pinned at `+0` for 66s straight (12:32:15–12:33:21), then a huge catch-up burst (`displayed=+869` in one tick), then healthy for ~24s, then stalled again. The source relay's own log for that exact window shows a single, continuous, uninterrupted connection the whole time (steady ~125KB/s via `sent NN MB so far` milestones, no OPEN/disconnect/timeout lines) — ruling out both chunk size *and* a network-layer reconnect as the cause. Wi-Fi signal checked directly at the same time: -36dBm/-92dBm noise, 802.11ax 6GHz/160MHz, ruling out weak signal too. **New detail this run**: a negative playback-clock delta right before recovery (`[VLC] tick pos=+-6857ms/3000ms` — `get_time()` regressing, not just advancing slowly), while `bytes=`/`i_demux_read_bytes` kept climbing normally (~300-400KB/tick) throughout the whole stall — the demuxer was actively consuming bytes the entire time, so this isn't a starved/blocked demuxer either; it's specifically the stream-clock mapping that goes wrong. **Superseded same session, see below**: chunk size was re-reverted back to the small (1504-byte) value after tracing this large-chunk test as an untested *second* change layered on top of a working state (the cushion fix alone), and a same-session re-test with the small chunk size *also* stalled (54s) — meaning chunk size was never actually the deciding factor either way. See the network-hop-isolation entry below for what the deciding factor turned out to be.

  **ts-trust-pcr experiment, 2026-09-09 — tried and reverted the same session.** The negative-clock-delta finding above pointed directly at VLC 3.0.23's TS demux module's `ts-trust-pcr` option (`modules/demux/mpeg/ts.c`, default `true` — trust the broadcast's own embedded PCR clock vs. generate one from packet arrival timing); a real broadcast can legitimately carry PCR discontinuities (ad breaks, program boundaries) that this module is supposed to smooth over (`ts-pcr-offsetfix`/`PCRFixHandle`) but plausibly doesn't fully handle for this relay's specific shape (open-ended HTTP stream, joined mid-file at an arbitrary offset). Set `--no-ts-trust-pcr` in `VLCBridge.swift`'s per-media options. **Live-tested result: much worse, not better** — a fresh FEED connection never produced a single displayed frame in 6+ minutes, stuck in an ever-climbing "Buffering NN%" the whole time (normally reaches 100%/first frame within a few seconds). Reverted immediately; see `VLCBridge.swift`'s own doc comment on the (now-removed) option for the full note.

  **stream-filter experiment, 2026-09-09 — tried and reverted immediately after, same session.** Targeted the "prefetch" module directly (rather than tuning it — `prefetchBufferKiB`, see below, already tried that once) since two independent `sample <pid> 5` captures this session both showed prefetch's own consumer thread >99% blocked in `_pthread_cond_wait` mid-stall (see the thread-level-evidence entry above). Set `--stream-filter=record` (excludes prefetch from VLC's auto-probed stream-filter chain entirely, keeping only "record," the chain's other real member per the teardown log's `removing module` lines). **Live-tested result: the same failure mode as ts-trust-pcr** — "Buffering NN%" crept to 57% over 50+ seconds with zero displayed frames, instead of the normal few-second ramp. Reverted immediately. Two different levers (PCR trust, prefetch presence) both broke the same "Buffering %"/rate-ramp startup logic instead of fixing the mid-session stall — suggests that startup logic depends on the prefetch module's own internal fill-state more directly than its outward tunable behavior (buffer-size sizing) implied, and this investigation doesn't have enough visibility into that dependency to keep guessing at it safely. Both reverted options' full reasoning is preserved as comments in `VLCBridge.swift` even though the flags themselves are gone, so this isn't rediscovered from scratch.

  **Local-vs-network isolation test, 2026-09-09 — the actual deciding factor, found after four inconclusive server-side experiments.** All four prior experiments this session (cushion, chunk size, ts-trust-pcr, stream-filter) implicitly assumed the growing-file relay/disk-read/demux path itself was the problem. None of them had isolated the one variable every FEED test that session actually shared: the real cross-machine Wi-Fi hop. Direct test: played the *same* actively-recording show via VLC's CLI (`/Applications/VLC.app/Contents/MacOS/VLC -I dummy --extraintf=rc --rc-host=127.0.0.1:9998 --vout=dummy --aout=dummy ...`) against `http://127.0.0.1:1980/api/watch-recording?show=<id>&start=0` **on the source Mac itself** — identical `streamGrowingFile`/`pumpGrowingFile` code path, zero network hop, matching options to the app's own (`network-caching=300`, `prefetch-buffer-size=1024`, `no-audio-time-stretch`). Polled `get_time` via VLC's RC interface. **Result: perfectly clean for 12+ minutes straight** — six manual checkpoints (36s, 125s, 152s, 167s, 214s, 737s of playback position) every one matching real elapsed wall-clock time almost exactly, CPU actively decoding (40.8%) throughout, zero stalls. (An automated polling *script* wrapped around the same RC interface produced persistent false "stuck at 3s" readings the whole time due to an unresolved bug in how repeated short-lived `nc` connections interact with VLC's single-client RC session — a testing-harness artifact, not real player state; only individually-issued manual checks proved reliable. Flagged here so a future session doesn't waste time re-debugging the same harness issue.)
  **Conclusion**: the growing-file relay mechanism itself — disk reads, chunk sizing, the "prefetch" module, PCR content in the recording — is not the cause. VLC handles it flawlessly over loopback. Every cross-machine FEED test this session (cushion on/off, both chunk sizes, PCR-trust on/off, prefetch present/absent) stalled within 90 seconds to a few minutes; this local test never stalled once in 12+ minutes. **The differentiating factor is the real network hop itself** — not weak signal (independently verified excellent: -36dBm, 6GHz/160MHz, 2.4Gbps PHY) and not a reconnect (the source relay log shows one continuous connection throughout every cross-machine test). This reorients the investigation: future work should focus on what's different about the real Wi-Fi hop's TCP/timing behavior (vs. instant loopback) rather than continuing to tune the relay's disk-read/chunking logic, which this test shows is already sound.
  **Concurrent confirmation, same session, immediately after** — the laptop's own FEED viewer window had been left open the whole time the local loopback test above was running, watching the exact same recording over the real network hop. Its log for that identical window shows real, ongoing distress: an 81s stall (resolved 13:22:17), another stall with a negative clock delta seconds later (13:22:23, `pos=+-5726ms`), then a sustained freeze from 13:22:35 that was still going over a minute later. At 13:23:54, captured live: `ES_OUT_SET_(GROUP_)PCR is called too late (jitter of 62085 ms ignored)` → `Timestamp conversion failed for 56622507123: no reference clock` → `Could not convert timestamp 0 for FFmpeg` → `early picture skipped`/`buffer too late: dropped` — VLC's PCR-derived clock reference is being lost *entirely* on the real network path, cascading into dropped frames and a fully stalled display. Nothing resembling this ever appeared once during the 12-minute clean local run. This is a genuine simultaneous A/B, not just sequential tests at different times: same recording, same source, only the network path differs, and the outcomes diverged completely and continuously.
  **`tcpdump` packet-capture analysis, 2026-09-09, same session — done, with a correction along the way.** Captured simultaneously on both machines (`sudo tcpdump -i en0 -w ... host <peer> and port 1980`) across a real ~30-minute session spanning multiple real stalls (a 117s stall resolved 13:55:23 UTC, a 93s stall resolved 13:57:26 UTC, among others). Analyzed with `tshark` (installed via `brew install wireshark` — CLI tools only, no GUI/cask). **First pass overclaimed a finding that didn't hold up**: raw counts across the whole capture showed ~90K `tcp.analysis.out_of_order`/45K `tcp.analysis.duplicate_ack` events — alarming-looking in isolation, but a proper controlled comparison (a 118s stall window vs. the 97s healthy window immediately following it, same connection) showed **statistically identical rates in both** (~28% of frames flagged either way) — too high to be real loss on a link otherwise sustaining normal throughput, and clearly uncorrelated with when the stall actually happened. Concluded this is very likely a NIC-offload capture artifact (TSO/GRO), not a genuine network signal, and retracted the "massive reordering" framing.
  **What held up**: per-second byte throughput in the 118s stall window never dropped below ~28KB and never showed a true gap — continuous delivery the entire time, matching the app's own logs exactly. Packet-arrival jitter, though, *was* measurably different: stdev 19.1ms vs. 13.2ms (stall vs. healthy), 33 vs. 13 gaps over 100ms in matched ~2-minute windows, no single gap over 330ms either way. Real, but small in absolute terms next to a 60-120+ second freeze — the refined read is that ordinary real-world network jitter (present on any real path, absent on loopback) is *triggering* something in VLC's PCR/clock-sync logic that then gets stuck far longer than the trigger justifies, rather than the jitter itself being severe enough to explain the outage directly.

*(Found 2026-08-19 by a time-boxed parallel-agent review sweep — not yet independently re-verified by a human, flagged with agent-reported confidence. Four of the original five were fixed 2026-08-22 — see `issues_resolved.md`; only the deadlock-hardening entry below remains.)*

- **`AppState.seekRecording`/`VLCPlayerView`'s recording-relay seek path — live deadlock scenario not force-reproduced; hardening fix shipped 2026-08-15, root live report not yet re-confirmed fixed.** Original finding: the main thread could block synchronously inside a VLC `input_Close` → `pthread_join` → `__ulock_wait` call, hanging the whole app (unresponsive UI, no crash) until something external kills it — caught live via a crash report, ~11 minutes hung (stack: `VLCPlayerView.seekRelative(_:)` → `AppState.seekRecording(showId:toSeconds:)` → `input_Close`, `queue: com.apple.main-thread`).
  **Root cause, identified by code reading (not a forced live reproduction)**: `VLCBridge.play(url:)` called `libvlc_media_player_stop` — a synchronous, blocking libvlc call (superseded by the async `libvlc_media_player_stop_async` in VLC 4+) — directly on the MainActor. `WebServer.pumpGrowingFile` (the recording-relay's data pump), once caught up to the live edge, needs a `Task { @MainActor in ... }` hop just to check `show_recording` before it can send the next chunk. If `_mpStop` runs on the MainActor at the exact instant VLC's own input thread is blocked reading that next chunk, neither side can unblock the other: the MainActor is frozen inside `pthread_join` waiting for VLC's input thread to close, and VLC's input thread is waiting for bytes gated behind that same frozen MainActor. A genuine mutual deadlock, not just a slow operation — matches the observed indefinite hang. Both halves of this dependency (the relay's `@MainActor` poll-hop, and the scrub bar calling into `play()`) predate this discovery by six weeks (2026-07-03, `b783629`/`4714b0d`); this is the first time it was actually caught.
  **Fix shipped**: `_mpStop` (and `_mpRelease`) now run on a private serial background queue (`VLCBridge.libvlcQueue`) instead of synchronously on the MainActor, across `play()`/`stop()`/`releasePlayer()`/`stopAndClearState()` — the MainActor is now always free to service other work (including the relay's poll-hop) while VLC's teardown runs, breaking the circular wait at its root. Kept every external call site's signature unchanged (no `async` propagation needed) by deferring only the native-object work; `currentURL` still updates synchronously so `beginRecordingSeek`'s staleness guard keeps working. A `currentMedia`-claim-on-capture pattern prevents a double-release if two calls overlap before the first's background work lands; a `currentURL`-staleness check in the background commit avoids a superseded call clobbering newer state (and releases its own stale media object instead of leaking it). Full test suite (262 tests) passes; deployed and confirmed the running app still serves the guide/API correctly against a real in-progress recording.
  **Stress-tested live 2026-08-24** (still not a forced reproduction of the exact original race, see below): scheduled a real recording (`[MOCK] DW News`, single-show, self-cleaned after), opened it in the native Watch Now window, and used Accessibility UI scripting (`osascript`/System Events) to send ~500 rapid arrow-key seeks (keyCode 123/124) against the player window while a background probe hit `/api/now.json` (a MainActor-touching route) every second to watch for a hang. The app log confirms this actually drove the vulnerable state repeatedly and hard — dozens of `beginRecordingSeek`/`play url=`/relay OPEN/disconnect events landing within the same wall-clock second, several while the relay pump was in exactly the "caught up to live edge — waiting for more data" state the original bug depended on. Result: **no deadlock** — the app never became unresponsive. Two brief blips (one ~3s, one an outright 5s probe timeout) occurred during the heaviest burst and both self-recovered within a couple seconds; the log kept advancing throughout, the relay resumed normal live-edge polling right after, and the app (same PID) was back to ~5ms `/api/now.json` responses afterward. `VLCBridge.swift` confirms every `libvlcQueue` handoff is `.async` (no `.sync` anywhere), so those blips are read as ordinary scheduler contention from the burst, not a residual circular wait. **Still not done**: this didn't force the *exact* original timing window (VLC's input thread blocked mid-read at the precise instant `_mpStop` fires) — it was volume/frequency stress, not a surgical repro — so it raises confidence without being definitive proof.

- **Web guide feels laggy while the app is doing something "heavy."** Reported live 2026-08-24 — no specific action pinned down yet, just a general "the web UI slows down when the app is busy" observation.
  **Prime suspect (not yet confirmed as root cause)**: `TODO.md`'s existing "Watch for UI hitches from `broadcastGuideChangeEvent`'s wider call-site fan-out" entry — 9+ show-lifecycle events (add/edit/delete/pause/resume/favorite-toggle/duplicate-override-clear, plus recording start/stop) each trigger a full `@MainActor` rebuild (`buildGuideGridHTML` + `buildDevBarHTML` + gzip'd `prebuildPageHTML`), which blocks the actor every other web request funnels through. That TODO entry was written as a "watch for it" note with no confirmed live hitch; this is the first actual report matching its predicted symptom.
  **Regression test added 2026-08-24**: `Tests/hdhr_VCRTests/WebServer/WebServerPerfTests.swift` → `apiLatency_staysResponsive_duringGuideChangeBurst()`. Deliberately reuses the existing "post-deploy, requires running app on :1980" pattern rather than adding new mocking infrastructure — POSTs `/api/toggle-favorite` on a real channel 10 times (even count, so the channel's favorite state ends up exactly as found), interleaved with a `/api/ping` latency probe right after each toggle, and asserts the median stays under a generous 500ms. Chosen over scheduling a real recording (would tie up a tuner and write a file) as the cheapest *safe*, repeatable trigger of the same `broadcastGuideChangeEvent` path. **Passed** on first run and 3 repeats (3.9s–7.1s total for the 10-iteration burst, comfortably under threshold each time) — even under an elevated system load average (~3.6) that was concurrently failing the pre-existing `guideRefreshLatency_underThreshold` test.
  **Follow-up same day — user narrowed the cause**: not a CPU-bound "intensive app task," but *disk I/O* specifically — CrashPlan backing up plus a large file copy were both running at the time. This redirects the suspect list: `AppState.saveConfig()` → `ConfigManager.save(_:)` does three **synchronous, blocking filesystem calls directly on the `@MainActor`** (remove the old `.bak`, copy the current config to it, then an atomic write of the new one) — called from **26 sites** in `AppState.swift` covering essentially every show mutation (add/edit/delete/pause/resume/idle-loop reschedule). Since `WebServer` hops onto that same actor for nearly every request touching `AppState`, a slow disk write here would stall every web request queued behind it — architecturally the exact same shape as two bugs this codebase already found and fixed the same way: `issues_resolved.md`'s "Blocking `waitpid` on the main actor can freeze the menu-bar UI", and `writeMetadataSidecar`/`recordedEpisodeTags` (`AppState.swift`, ~line 2826) being deliberately marked `nonisolated` specifically so a slow-to-wake NAS/external recording drive "could stall the whole app" no longer does. **`ConfigManager.save` never got the same treatment** — it's the one remaining synchronous-disk-write-on-MainActor call site of this shape, and by far the most frequently hit (26 sites vs. 1-2 for the already-fixed ones).
  **Second regression test added 2026-08-24**: `Tests/hdhr_VCRTests/AppState/AppStateDiskIOLatencyTests.swift` → `saveConfig_staysResponsive_underConcurrentDiskWrites()`. - **`ConfigManager.swift:35`** — `FileManager.default.urls(for: .documentDirectory, in: .userDomainMask)[0]` force-subscripts instead of using the defensive `.first ?? ...` pattern its own Application Support lookup uses 22 lines earlier. - **`ChannelSignalStore.swift:113-143`** — `flush()`'s `savePending?.cancel()` doesn't actually stop the debounced `scheduleSave()` task, because that task swallows the resulting `CancellationError` via `try? await Task.sleep(...)` and continues on to perform its own write. Net effect is a wasted duplicate disk write of a near-identical snapshot, not data loss or corruption — the two writes race but produce materially the same content. Accept as a minor inefficiency; not worth the added complexity of real cooperative cancellation for a debounced local cache write.
- **`WebServer.swift`** — refines the existing SSE dead-connection entry above: the 25 s keepalive prune only covers connections still in the pre-registration `accumulate()` phase.
