# Issue Log

Historical record of bugs encountered during development. Used as a "don't repeat this" reference during code reviews. Unrelated bugs found during work go here rather than fixed inline — note the resolving commit when done. Deferred features go in `TODO.md`.

**This file holds only what's still open, or accepted as-is (won't-fix / by-design / too marginal to schedule).** Once something is actually fixed, its entry moves to [`issues_resolved.md`](issues_resolved.md) rather than staying here — that file is the "how was X fixed" archive, this one is "what still needs attention." Findings about *technique* (things tried repeatedly and abandoned, independent of any specific still-open bug) live in [`FAILED_APPROACHES.md`](FAILED_APPROACHES.md) instead of either issue file.

**Format**: each issue has a status (`OPEN` or `ACCEPTED`), a brief description, root cause, and a fix note if one's been scoped but not done.

*(Found 2026-08-19 by a time-boxed parallel-agent review sweep — not yet independently re-verified by a human, flagged with agent-reported confidence. Four of the original five were fixed 2026-08-22 — see `issues_resolved.md`; only the deadlock-hardening entry below remains.)*

- **`AppState.seekRecording`/`VLCPlayerView`'s recording-relay seek path — live deadlock scenario not force-reproduced; hardening fix shipped 2026-08-15, root live report not yet re-confirmed fixed.** Original finding: the main thread could block synchronously inside a VLC `input_Close` → `pthread_join` → `__ulock_wait` call, hanging the whole app (unresponsive UI, no crash) until something external kills it — caught live via a crash report, ~11 minutes hung (stack: `VLCPlayerView.seekRelative(_:)` → `AppState.seekRecording(showId:toSeconds:)` → `input_Close`, `queue: com.apple.main-thread`).
  **Root cause, identified by code reading (not a forced live reproduction)**: `VLCBridge.play(url:)` called `libvlc_media_player_stop` — a synchronous, blocking libvlc call (superseded by the async `libvlc_media_player_stop_async` in VLC 4+) — directly on the MainActor. `WebServer.pumpGrowingFile` (the recording-relay's data pump), once caught up to the live edge, needs a `Task { @MainActor in ... }` hop just to check `show_recording` before it can send the next chunk. If `_mpStop` runs on the MainActor at the exact instant VLC's own input thread is blocked reading that next chunk, neither side can unblock the other: the MainActor is frozen inside `pthread_join` waiting for VLC's input thread to close, and VLC's input thread is waiting for bytes gated behind that same frozen MainActor. A genuine mutual deadlock, not just a slow operation — matches the observed indefinite hang. Both halves of this dependency (the relay's `@MainActor` poll-hop, and the scrub bar calling into `play()`) predate this discovery by six weeks (2026-07-03, `b783629`/`4714b0d`); this is the first time it was actually caught.
  **Fix shipped**: `_mpStop` (and `_mpRelease`) now run on a private serial background queue (`VLCBridge.libvlcQueue`) instead of synchronously on the MainActor, across `play()`/`stop()`/`releasePlayer()`/`stopAndClearState()` — the MainActor is now always free to service other work (including the relay's poll-hop) while VLC's teardown runs, breaking the circular wait at its root. Kept every external call site's signature unchanged (no `async` propagation needed) by deferring only the native-object work; `currentURL` still updates synchronously so `beginRecordingSeek`'s staleness guard keeps working. A `currentMedia`-claim-on-capture pattern prevents a double-release if two calls overlap before the first's background work lands; a `currentURL`-staleness check in the background commit avoids a superseded call clobbering newer state (and releases its own stale media object instead of leaking it). Full test suite (262 tests) passes; deployed and confirmed the running app still serves the guide/API correctly against a real in-progress recording.
  **Stress-tested live 2026-08-24** (still not a forced reproduction of the exact original race, see below): scheduled a real recording (`[MOCK] DW News`, single-show, self-cleaned after), opened it in the native Watch Now window, and used Accessibility UI scripting (`osascript`/System Events) to send ~500 rapid arrow-key seeks (keyCode 123/124) against the player window while a background probe hit `/api/now.json` (a MainActor-touching route) every second to watch for a hang. The app log confirms this actually drove the vulnerable state repeatedly and hard — dozens of `beginRecordingSeek`/`play url=`/relay OPEN/disconnect events landing within the same wall-clock second, several while the relay pump was in exactly the "caught up to live edge — waiting for more data" state the original bug depended on. Result: **no deadlock** — the app never became unresponsive. Two brief blips (one ~3s, one an outright 5s probe timeout) occurred during the heaviest burst and both self-recovered within a couple seconds; the log kept advancing throughout, the relay resumed normal live-edge polling right after, and the app (same PID) was back to ~5ms `/api/now.json` responses afterward. `VLCBridge.swift` confirms every `libvlcQueue` handoff is `.async` (no `.sync` anywhere), so those blips are read as ordinary scheduler contention from the burst, not a residual circular wait. **Still not done**: this didn't force the *exact* original timing window (VLC's input thread blocked mid-read at the precise instant `_mpStop` fires) — it was volume/frequency stress, not a surgical repro — so it raises confidence without being definitive proof.
  **Visual smoke test done 2026-08-24** (`screencapture` region-capture of the player window's on-screen bounds + Read, since no dedicated native-window screenshot tool exists here): opened a second real test recording in the native Watch Now window and screenshotted through the normal (non-adversarial) flow — poster overlay with Start button, live video after Start (MPEG-2 decoding correctly, no error/ended overlay), a single ordinary left-arrow seek (one clean reconnect in the log, not a burst — `OPEN ... startOffset=29371240` → old connection `stopping` → resumed live-edge polling), video still playing smoothly post-seek, and the hover-triggered recording scrub overlay (`5:30PM ... 5:36PM ... 5:36PM` with position near live edge) rendering exactly as `docs/VLCPlayerView.md` describes. No visual defects found. Both outstanding verification items from the 2026-08-19 sweep are now addressed (stress-tested + visually smoke-tested); only the surgical exact-timing repro remains undone, which is why this entry stays open rather than moving to `issues_resolved.md`.

- **Web guide feels laggy while the app is doing something "heavy."** Reported live 2026-08-24 — no specific action pinned down yet, just a general "the web UI slows down when the app is busy" observation.
  **Prime suspect (not yet confirmed as root cause)**: `TODO.md`'s existing "Watch for UI hitches from `broadcastGuideChangeEvent`'s wider call-site fan-out" entry — 9+ show-lifecycle events (add/edit/delete/pause/resume/favorite-toggle/duplicate-override-clear, plus recording start/stop) each trigger a full `@MainActor` rebuild (`buildGuideGridHTML` + `buildDevBarHTML` + gzip'd `prebuildPageHTML`), which blocks the actor every other web request funnels through. That TODO entry was written as a "watch for it" note with no confirmed live hitch; this is the first actual report matching its predicted symptom.
  **Regression test added 2026-08-24**: `Tests/hdhr_VCRTests/WebServer/WebServerPerfTests.swift` → `apiLatency_staysResponsive_duringGuideChangeBurst()`. Deliberately reuses the existing "post-deploy, requires running app on :1980" pattern rather than adding new mocking infrastructure — POSTs `/api/toggle-favorite` on a real channel 10 times (even count, so the channel's favorite state ends up exactly as found), interleaved with a `/api/ping` latency probe right after each toggle, and asserts the median stays under a generous 500ms. Chosen over scheduling a real recording (would tie up a tuner and write a file) as the cheapest *safe*, repeatable trigger of the same `broadcastGuideChangeEvent` path. **Passed** on first run and 3 repeats (3.9s–7.1s total for the 10-iteration burst, comfortably under threshold each time) — even under an elevated system load average (~3.6) that was concurrently failing the pre-existing `guideRefreshLatency_underThreshold` test.
  **Follow-up same day — user narrowed the cause**: not a CPU-bound "intensive app task," but *disk I/O* specifically — CrashPlan backing up plus a large file copy were both running at the time. This redirects the suspect list: `AppState.saveConfig()` → `ConfigManager.save(_:)` does three **synchronous, blocking filesystem calls directly on the `@MainActor`** (remove the old `.bak`, copy the current config to it, then an atomic write of the new one) — called from **26 sites** in `AppState.swift` covering essentially every show mutation (add/edit/delete/pause/resume/idle-loop reschedule). Since `WebServer` hops onto that same actor for nearly every request touching `AppState`, a slow disk write here would stall every web request queued behind it — architecturally the exact same shape as two bugs this codebase already found and fixed the same way: `issues_resolved.md`'s "Blocking `waitpid` on the main actor can freeze the menu-bar UI", and `writeMetadataSidecar`/`recordedEpisodeTags` (`AppState.swift`, ~line 2826) being deliberately marked `nonisolated` specifically so a slow-to-wake NAS/external recording drive "could stall the whole app" no longer does. **`ConfigManager.save` never got the same treatment** — it's the one remaining synchronous-disk-write-on-MainActor call site of this shape, and by far the most frequently hit (26 sites vs. 1-2 for the already-fixed ones).
  **Second regression test added 2026-08-24**: `Tests/hdhr_VCRTests/AppState/AppStateDiskIOLatencyTests.swift` → `saveConfig_staysResponsive_underConcurrentDiskWrites()`. Measures `saveConfig()`'s own wall-clock latency directly (no web server needed — the suspected mechanism lives in `AppState`/`ConfigManager`, not anything web-specific) while 3 background `Task`s repeatedly write+fsync 20MB blobs to the same scratch volume, asserting the median stays under 500ms. **Passed**, but with an honest caveat: on this dev machine's SSD, the synthetic pressure barely moved the needle (~0.8-1.1ms median with or without it) — nowhere near enough to reproduce a felt slowdown, meaning this test is a real regression baseline but was **not** able to synthetically reproduce the reported symptom. Modern NVMe write-back caching absorbs synthetic bursts like this far more easily than it would absorb CrashPlan's real (likely fsync-heavy, possibly sustained-minutes-long) backup pattern.
  **Not done**: actually fixing `ConfigManager.save`'s MainActor-blocking write (mirroring the `nonisolated` + detached-`Task` pattern already used twice in this file) — 26 call sites is real scope to review (a few may rely on the save completing before a web response is sent), so this wasn't done as a drive-by part of adding a test. Scoped and ready to pick up; see `TODO.md`.
  **Root-caused 2026-08-24, second follow-up — user clarified further**: "it seems a lot of the slowdown is time just connecting, before the app has time to respond." Measured directly against the live app with `curl -w '%{time_connect} %{time_starttransfer}'`: **TCP connect stays ~0.2-0.4ms even under heavy synthetic load — it's the time-to-first-byte that balloons**, so the *feeling* of "stuck connecting" is real but the mechanism isn't the TCP handshake. Isolated by testing combinations directly against the live server:
  - Disk pressure alone (3 background `Task`s fsync-writing 20MB blobs, no SSE, no broadcasts): **no effect** — `/api/ping` ttfb stayed ~1-2ms. This rules out the disk-I/O/`ConfigManager.save` theory above as the *primary* mechanism (still worth fixing on its own merits, just not this).
  - **8 held-open SSE connections + a 20-toggle `/api/toggle-favorite` burst, zero disk pressure: reproduced the full symptom** — `/api/ping` ttfb jumped to 650-950ms, consistently across 15 samples. This is the real mechanism.
  - Root cause: `broadcastGuideChangeEvent` embeds the **entire guide grid HTML, uncompressed, in the SSE event's JSON payload** — captured directly off a real broadcast on this app's own guide: **~2.2MB for one event**. That gets sent to *every* connected SSE client (every open web guide tab/window) via `conn.send()`. `WebServer.swift`'s `NWListener` and every single `NWConnection` share one serial `DispatchQueue` (`queue` — see its own doc comment, which already documents this exact risk for the Watch Now relay's disk reads, but not for this) — accepting a *brand-new* connection, and reading the first bytes off it, has to wait its turn behind whatever's already queued there. With even a modest number of open guide tabs, a burst of large SSE sends can back up that one queue badly enough that a totally unrelated new request sits waiting before the app ever gets to look at it — which is exactly what "feels like slow connecting" from a browser's point of view, even though the raw TCP accept was instant.
  - **Test corrected 2026-08-24**: the original `apiLatency_staysResponsive_duringGuideChangeBurst()` had **zero SSE connections open** and so completely missed this — it measured only the CPU-rebuild cost, not the SSE-fanout cost, and passed comfortably because of it. Now opens 4 real SSE connections (`URLSession.bytes(for:)`, held open via an uncancelled streaming read) before running the same toggle burst. Real measured baseline: **~350-460ms median** with 4 connections (vs. 650-950ms at 8) — threshold widened from 500ms to 750ms for headroom. The whole suite is now `.serialized`: running this test's real background load concurrently with a sibling test (Swift Testing's default) actually timed out that sibling's own request once, live — itself further confirmation of how easily this backs up.
  - **Option (b) done 2026-08-31 — gzip the SSE payload.** `broadcastGuideChangeEvent` now gzip+base64's grid/sumph/tdrop via a new `WebServer.gzipBase64(_:)` helper before embedding them in the SSE JSON, under new `gridZ`/`sumphZ`/`tdropZ` keys (falls back per-field to the plain key when `gzipBase64` declines, e.g. too small to shrink — same as every other optional-gzip call site in this file). Not a stream-level `Content-Encoding: gzip` as originally scoped — SSE frames are plain UTF-8 text (`"data: {...}\n\n"`), so raw gzip bytes go through base64 inside the JSON field instead, which claws back some of the ratio but needed no changes to the connection/response framing (`registerSSE`/`sseKeepalive`/the shared serial queue are all untouched). `guide.js`'s new `decodeGzipB64(_:)` (using the browser's native `DecompressionStream('gzip')`, broadly supported since ~2023) decodes async before handing a plain `{grid,sumph,tdrop}` object to the existing `applyGuidePayload` — falls back to a full `refreshGuide()` fetch if `DecompressionStream` is missing rather than silently doing nothing. **Measured live 2026-08-31**: one real guide-change broadcast dropped from 2,252,437 bytes to 211,466 bytes (10.65x). New regression test `WebServerPerfTests.guideChangeBroadcast_isGzipCompressed` captures a real SSE frame, confirms `gridZ` (not `grid`) is used, and round-trips it through `/usr/bin/gunzip` to confirm the decompressed content is real grid HTML — catches both "compression silently turned off" and "compression produces garbage." Options (a) (lightweight notify-and-pull, the bigger structural fix, changes the SSE contract) and (c) (give the accept path its own queue) remain undone — this alone doesn't touch the shared-serial-queue mechanism itself, only how many bytes have to move through it per broadcast.

- **`AppStateRecordingEngineTests.startRecording_metadataSidecarEnabled_writesNfoFileAlongsideRecording` is flakes under load — missing a wait for the sidecar write.** Found 2026-08-28 while adding an unrelated test to the same file (`startRecording_unsupportedDevice_forcesTranscodeNone_supportedDeviceKeepsChoice`, transcode-capability gating) — 1 failure in ~15 full-suite runs, always this same test, never the new one.
  **Root cause (read, not yet instrumented/confirmed)**: the test asserts `FileManager.default.fileExists(atPath: nfoPath)` immediately after `await state.startRecording(index: 0)` returns, with no polling — every other test in this file that waits on filesystem/process side effects from `startRecording` uses the shared `waitUntil(...)` helper (`TestFixtures.swift`) specifically because those effects (real subprocess spawn, real file writes) aren't synchronous with `startRecording` returning. If the `.nfo` sidecar write (`writeMetadataSidecar`) is dispatched off the calling task the same way the disk-scan half of `duplicateEpisodeTag` is (`docs/ShowFormSection.md`'s "Duplicate Episodes Toggle" section documents that pattern elsewhere in `AppState.swift`), this assertion can legitimately race ahead of the write completing under system load.
  **Fix (scoped, not applied — out of scope for the change that found it)**: wrap the existing assertion in `await waitUntil { FileManager.default.fileExists(atPath: nfoPath) }` before reading the file, matching every other real-I/O assertion in this file.

*(Found 2026-09-03 by a code review of the full `v2.2.0..HEAD` range — virtual tuner relay, VLCBridge, VLC gating, Sharing settings reorg. See `.claude/CODE_NOTES.md`'s matching dated entry for what else the same review found that turned out to already be documented/intentional, or was already fixed same-day. Verified against live code by re-reading each site directly, not just agent-reported.)*

- **`AppState.applyWebServerState()` stamps `boundWebServerPort` from the live `config` value, not the port the listener actually bound — a race if the port is changed again while a bind is in flight.** `reconcileWebServerState()` (`AppState.swift:657`) starts a bind by calling `webServer.start(port: config.Web_server_port, ...)`, capturing that port value at call time. If the user changes Settings → Sharing → Port and saves again while `webServerStarting == true`, the reconcile guard (`guard !webServerRunning, !webServerStarting else { return }`) skips starting a second time — correctly avoiding a racing bind — but the *first* bind's completion handler, `applyWebServerState(_:)` (`AppState.swift:686`), sets `boundWebServerPort = config.Web_server_port` reading the *current* (now-changed) config value, not the port that bind actually succeeded on. `boundWebServerPort` and `config.Web_server_port` end up falsely agreeing, so the stale-port check at `reconcileWebServerState`'s line 662 (`if webServerRunning, boundWebServerPort != config.Web_server_port`) never fires to correct it — the server silently keeps serving on the old port, believing itself correctly bound to the new one, until an unrelated Web_server_enabled toggle forces a real restart. Narrow window (needs a Settings save to land in the middle of an in-flight bind, which is normally fast), but a real, confirmed bug — same general class as the port-rebind race `58c2682` already fixed once for two racing *start* calls; this is a racing *port-change-during-start* instead.
  **Fix, not yet applied**: capture the port passed to `webServer.start(port:...)` in the closure so `applyWebServerState` stamps `boundWebServerPort` with the port that was actually requested for *this* bind, not whatever `config.Web_server_port` happens to read at completion time.

- **The virtual tuner relay's `TunerCount`/lineup/discover JSON all re-derive "which shows are recording" via a bare `shows.filter { $0.show_recording }` instead of the canonical `recordingShows` property, which also excludes a show whose `show_end` has already passed.** `AppState.recordingShows` (`AppState.swift:160`) is `shows.filter { $0.show_recording && ($0.show_end ?? .distantPast) > Date() }` — deliberately excluding the brief window after a show's guide end time passes but before the idle loop actually flips `show_recording` to `false`. Four call sites duplicate the plain, unguarded filter instead of using that property: `AppState.updateVirtualTunerPresence()` (`AppState.swift:848`, drives the relay's advertised `TunerCount`) and `WebServer.swift`'s `buildVirtualTunerDiscoverJSON`/`buildVirtualTunerLineupJSON`/`buildVirtualTunerStatusJSON` (lines ~2654/2686/2723). In that end-of-recording window, the relay can advertise/report a tuner as still busy relaying a show the rest of the app (menu bar's "Recording Now" section, `recordingShows`-based UI everywhere else) already considers finished — an inconsistency between what the relay says and what the app itself believes, not a crash, but a real state-mismatch bug.
  **Fix, not yet applied**: swap all four bare `shows.filter { $0.show_recording }` call sites for `recordingShows`.

- **`WebServer.sourceIsAlreadyModernCodec`'s on-disk PAT/PMT fallback re-reads and re-scans the recording file (~2MB) on every viewer connection, with no per-show cache.** When a channel's lineup doesn't carry a `VideoCodec` field (older firmware, or this app's own synthetic virtual-relay lineup entries), `handleVirtualTunerStream` (`WebServer.swift:640`) falls back to `mpegTSVideoStreamType(inFileAt:)`, a real file read + PAT/PMT parse, on *every* `/auto/v<channel>` request for that show — not cached per-show. Two viewers of the same in-progress recording, or one viewer reconnecting/seeking, each pay the same redundant disk I/O and parse for a value that can't change for the life of that recording (the codec is fixed once capture starts). Efficiency only, no correctness impact.
  **Fix, not yet applied**: cache the probed result keyed by `showId` (or recording path) for the life of the recording, cleared alongside the rest of that show's runtime state.

- **`WebServer.lanIPAddress()`/`virtualTunerBaseURL()` re-runs a full `getifaddrs()` interface enumeration on every `/discover.json` and `/lineup.json` request instead of caching the resolved LAN IP.** (`WebServer.swift:2618`.) A real HDHomeRun-aware client (Channels DVR, Plex, etc.) polls these endpoints periodically while the relay is up — each poll pays a fresh syscall-based interface enumeration for a value that's stable for the life of the relay (until the network interface itself changes). Efficiency only.
  **Fix, not yet applied**: cache the resolved IP, invalidated the same way `boundWebServerPort`/other network-derived state already gets invalidated on a real network change.

- **`MenuContent.remoteRelayEntries` (the "Recording on Another Mac" list) is recomputed via `filter`+`flatMap` over `state.devices`/`state.lineups` on every menu body render, landing directly in the "Menu rebuild churn" hot path CLAUDE.md already warns about.** (`MenuContent.swift:155`.) CLAUDE.md's own Invariants & Gotchas: "frequent `@Published` mutations while the NSMenu is open cause rebuild glitches; batch/coalesce assignments." Every other per-render list in this same file (`recordingShows`, `nextUpGroups`, etc.) is a `let` computed once at the top of `body` from already-published state, same as this one — so it's consistent with the surrounding code's own pattern, just not yet proven to actually glitch in practice with realistic list sizes (typically 0-2 remote relays). Flagging as a known-shape risk in a documented-sensitive area, not a confirmed live glitch.
  **Fix, if ever picked up**: no different from how the file already handles this class of risk elsewhere — would need the same batching/coalescing approach already used for other `@Published`-driven menu content, not a new mechanism.

- **`AppState.usableDeviceIDs` is derived from raw `devices`, not `recordableDevices`, so it can include a virtual relay's own `DeviceID`.** (`AppState.swift:227`.) Every current caller happens to be safe only because it separately intersects against an already-`recordableDevices`-filtered list first — this property itself doesn't structurally exclude a relay. Matches the exact regression class CLAUDE.md's own Virtual Tuner Relay guardrails section warns about generally ("a picker doesn't inherit backstop... for free"): a future new call site that checks `usableDeviceIDs.contains(id)` directly, without itself first filtering through `recordableDevices`, would silently treat a relay device as a legitimately usable real tuner. Currently harmless; a latent trap for the next person (or agent) touching this property, not an active bug.
  **Fix, if ever picked up**: `usableDeviceIDs` could filter through `recordableDevices` itself at its own definition, so every current and future caller inherits the exclusion for free instead of each needing to remember it separately.

## Accepted — flagged, not scheduled (marginal / by-design)

First four re-verified against current code 2026-08-10 — all still accurate. Fifth added 2026-08-11. Following three added 2026-08-16 (full-codebase audit).

- **`ConfigManager.swift:35`** — `FileManager.default.urls(for: .documentDirectory, in: .userDomainMask)[0]` force-subscripts instead of using the defensive `.first ?? ...` pattern its own Application Support lookup uses 22 lines earlier. Crashes only if the array is ever empty — not a realistic risk for today's direct-distribution, unsandboxed build, but exactly the failure mode a future App Sandbox entitlement gap (see `docs/MAS_COMPLIANCE.md`) could trigger. Accept until the MAS track is actually picked up; fix trivially alongside that work.
- **`ChannelSignalStore.swift:113-143`** — `flush()`'s `savePending?.cancel()` doesn't actually stop the debounced `scheduleSave()` task, because that task swallows the resulting `CancellationError` via `try? await Task.sleep(...)` and continues on to perform its own write. Net effect is a wasted duplicate disk write of a near-identical snapshot, not data loss or corruption — the two writes race but produce materially the same content. Accept as a minor inefficiency; not worth the added complexity of real cooperative cancellation for a debounced local cache write.
- **`WebServer.swift`** — refines the existing SSE dead-connection entry above: the 25 s keepalive prune only covers connections still in the pre-registration `accumulate()` phase. Once `registerSSE()` runs, an abandoned client (sleep/Wi-Fi-drop/force-quit without a clean FIN) isn't pruned until the OS's own TCP retransmission timeout eventually fails a `send()` — which can take much longer than 25 s. Same accepted risk profile as the existing entry (self-heals eventually, bounded by realistic LAN client counts), just a correction to the recovery-time estimate.

- **`RecordingManager.swift:161`** — orphaned-recording liveness uses `kill(pid,0)`, which tests PID existence not identity; PID reuse could report a dead recording as running. Astronomically low probability (slow PID cycling); accept.
- **`Models.swift`** (`GuideEntry`) — `==`/`hash`/`id` are StartTime-only, unsafe for cross-channel `Set`/`ForEach(id:)`. Already documented (`WatchNowView.swift`) and every call site deliberately uses `\.GuideNumber` — latent trap, no live bug.
- **`WebServer.swift`** — `stateCallback`/`activePort`/`listener` are unsynchronized under `@unchecked Sendable` (benign word writes); a dropped SSE conn lingers in `sseConns` up to 25 s until the keepalive prunes it (self-heals). Neither observed to misbehave.
- **`VLCBridge.swift`** (~line 55-60 at time of writing) — a CoreAudio device-change callback already in flight during `stopDeviceChangeMonitoring()` teardown could read a freed context. Very edge; related listener-lifecycle issue (double-registration) is fixed — see `issues_resolved.md` — this is a narrower residual case that wasn't.
- **`WebServer.swift` — LAN-trust hardening notes (2026-08-11 security pass)** — three related accepts, all requiring a hostile or misbehaving device *already on the trusted network*: (1) the subnet check matches any local interface's subnet, **including VPN tunnels** (utun) — a connected VPN with a wide netmask admits all VPN-side peers as "local"; inherent to the subnet-trust design, worth knowing when running a VPN on the host Mac. (2) **No cap on concurrent SSE connections** — `sseConns` grows per open `/api/events` connection with no limit; dead ones prune via the 25 s keepalive but a client holding thousands open exhausts file descriptors (degradation, not crash). (3) **`handleEdit`/`handleRecord` accept unbounded `title` strings** — bounded only by the 128 KB request cap; a ~100 KB title bloats config/page builds, and embedded newlines pass into `glog` lines (log-line injection). All three accepted as marginal on a home LAN; revisit if the trust model ever widens.
- **`src/HDHomeRunKit/`** — ~1,000 lines of dead player code (`HDHomeRunPlayerView`, `HDHomeRunPlayerViewModel`, `DVRBufferManager`, etc.) sitting in the working directory from an earlier player exploration. Gitignored (`/src` in `.gitignore`) and not referenced by `Package.swift`, so it can't affect the build or the repo — but it *does* show up in filesystem-wide searches (`find`/`grep` over the checkout without a `.build`-style exclusion), where its similarly-named types can mislead a code search or an automated audit into reading it as live code. Local-only clutter, zero runtime risk; accept unless/until it confuses something, in which case just delete the directory (it exists nowhere else — confirm nothing in it is worth salvaging first). Found during 2026-08-11 lean code audit.
- **Strict-concurrency build (`swift build -Xswiftc -strict-concurrency=complete`) — 2026-08-11 follow-up audit** — remarkably little noise (8 warnings, 5 distinct causes), none a real live race:
  - **`ConfigManager.swift:77` (`iso8601Formatter`), `Models.swift:69/71` (`logDateFormatter`/`logFile`), `DiscordNotifier.swift:9/14` (`discordLogDateFormatter`/`discordLogFile`)** — "not concurrency-safe, may have shared mutable state" on module-level `ISO8601DateFormatter`/`RotatingLogFile` globals. All three are compiler-pedantry, not real races: `ISO8601DateFormatter` is thread-safe per Apple docs (same reasoning as the `ConfigManager` hoist, see `issues_resolved.md`'s guide-detail-adjacent commit `a6d67de`); `logFile`/`discordLogFile` are only ever touched from inside their own serial `logQueue`/`discordLogQueue` `.async` closures (already commented as such at both call sites) — safe by construction, just not statically provable to the Sendable checker without `nonisolated(unsafe)` annotations this audit deliberately isn't adding (audit, not a Swift 6 migration).
  - **`VLCBridge.swift:57`** — `capture of 'ctx' with non-Sendable type 'AudioDeviceChangeContext'` + `sending 'ctx' risks causing data races`, both on the CoreAudio `audioDeviceChangeProc` C callback dispatching `ctx.callback()` onto `DispatchQueue.main.async`.
