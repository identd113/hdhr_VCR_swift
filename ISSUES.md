# Issue Log

Historical record of bugs encountered during development. Used as a "don't repeat this" reference during code reviews. Unrelated bugs found during work go here rather than fixed inline — note the resolving commit when done. Deferred features go in `TODO.md`.

**This file holds only what's still open, or accepted as-is (won't-fix / by-design / too marginal to schedule).** Once something is actually fixed, its entry moves to [`issues_resolved.md`](issues_resolved.md) rather than staying here — that file is the "how was X fixed" archive, this one is "what still needs attention." Findings about *technique* (things tried repeatedly and abandoned, independent of any specific still-open bug) live in [`FAILED_APPROACHES.md`](FAILED_APPROACHES.md) instead of either issue file.

**Format**: each issue has a status (`OPEN` or `ACCEPTED`), a brief description, root cause, and a fix note if one's been scoped but not done.

## Open

*(Found 2026-08-19 by a time-boxed parallel-agent review sweep — not yet independently re-verified by a human, flagged with agent-reported confidence. Four of the original five were fixed 2026-08-22 — see `issues_resolved.md`; only the deadlock-hardening entry below remains.)*

- **`AppState.seekRecording`/`VLCPlayerView`'s recording-relay seek path — live deadlock scenario not force-reproduced; hardening fix shipped 2026-08-15, root live report not yet re-confirmed fixed.** Original finding: the main thread could block synchronously inside a VLC `input_Close` → `pthread_join` → `__ulock_wait` call, hanging the whole app (unresponsive UI, no crash) until something external kills it — caught live via a crash report, ~11 minutes hung (stack: `VLCPlayerView.seekRelative(_:)` → `AppState.seekRecording(showId:toSeconds:)` → `input_Close`, `queue: com.apple.main-thread`).
  **Root cause, identified by code reading (not a forced live reproduction)**: `VLCBridge.play(url:)` called `libvlc_media_player_stop` — a synchronous, blocking libvlc call (superseded by the async `libvlc_media_player_stop_async` in VLC 4+) — directly on the MainActor. `WebServer.pumpGrowingFile` (the recording-relay's data pump), once caught up to the live edge, needs a `Task { @MainActor in ... }` hop just to check `show_recording` before it can send the next chunk. If `_mpStop` runs on the MainActor at the exact instant VLC's own input thread is blocked reading that next chunk, neither side can unblock the other: the MainActor is frozen inside `pthread_join` waiting for VLC's input thread to close, and VLC's input thread is waiting for bytes gated behind that same frozen MainActor. A genuine mutual deadlock, not just a slow operation — matches the observed indefinite hang. Both halves of this dependency (the relay's `@MainActor` poll-hop, and the scrub bar calling into `play()`) predate this discovery by six weeks (2026-07-03, `b783629`/`4714b0d`); this is the first time it was actually caught.
  **Fix shipped**: `_mpStop` (and `_mpRelease`) now run on a private serial background queue (`VLCBridge.libvlcQueue`) instead of synchronously on the MainActor, across `play()`/`stop()`/`releasePlayer()`/`stopAndClearState()` — the MainActor is now always free to service other work (including the relay's poll-hop) while VLC's teardown runs, breaking the circular wait at its root. Kept every external call site's signature unchanged (no `async` propagation needed) by deferring only the native-object work; `currentURL` still updates synchronously so `beginRecordingSeek`'s staleness guard keeps working. A `currentMedia`-claim-on-capture pattern prevents a double-release if two calls overlap before the first's background work lands; a `currentURL`-staleness check in the background commit avoids a superseded call clobbering newer state (and releases its own stale media object instead of leaking it). Full test suite (262 tests) passes; deployed and confirmed the running app still serves the guide/API correctly against a real in-progress recording. **Not yet done**: an actual live repro of the original deadlock (forcing VLC's input thread to stall at the relay's live edge at the exact moment a seek fires) — deliberately not attempted against the one real running instance available (a live recording was in progress at the time). The fix is reasoned from code, not proven against a forced reproduction of the failure; also not yet manually smoke-tested for ordinary playback/seek behavior in the native Watch Now window (no native-window screenshot tool available in this environment — needs a human check).

## Accepted — flagged, not scheduled (marginal / by-design)

First four re-verified against current code 2026-08-10 — all still accurate. Fifth added 2026-08-11. Following three added 2026-08-16 (full-codebase audit).

- **`ConfigManager.swift:35`** — `FileManager.default.urls(for: .documentDirectory, in: .userDomainMask)[0]` force-subscripts instead of using the defensive `.first ?? ...` pattern its own Application Support lookup uses 22 lines earlier. Crashes only if the array is ever empty — not a realistic risk for today's direct-distribution, unsandboxed build, but exactly the failure mode a future App Sandbox entitlement gap (see `docs/MAS_COMPLIANCE.md`) could trigger. Accept until the MAS track is actually picked up; fix trivially alongside that work.
- **`ChannelSignalStore.swift:113-143`** — `flush()`'s `savePending?.cancel()` doesn't actually stop the debounced `scheduleSave()` task, because that task swallows the resulting `CancellationError` via `try? await Task.sleep(...)` and continues on to perform its own write. Net effect is a wasted duplicate disk write of a near-identical snapshot, not data loss or corruption — the two writes race but produce materially the same content. Accept as a minor inefficiency; not worth the added complexity of real cooperative cancellation for a debounced local cache write.
- **`WebServer.swift`** — refines the existing SSE dead-connection entry above: the 25 s keepalive prune only covers connections still in the pre-registration `accumulate()` phase. Once `registerSSE()` runs, an abandoned client (sleep/Wi-Fi-drop/force-quit without a clean FIN) isn't pruned until the OS's own TCP retransmission timeout eventually fails a `send()` — which can take much longer than 25 s. Same accepted risk profile as the existing entry (self-heals eventually, bounded by realistic LAN client counts), just a correction to the recovery-time estimate.

- **`RecordingManager.swift:161`** — orphaned-recording liveness uses `kill(pid,0)`, which tests PID existence not identity; PID reuse could report a dead recording as running. Astronomically low probability (slow PID cycling); accept.
- **`Models.swift`** (`GuideEntry`) — `==`/`hash`/`id` are StartTime-only, unsafe for cross-channel `Set`/`ForEach(id:)`. Already documented (`WatchNowView.swift`) and every call site deliberately uses `\.GuideNumber` — latent trap, no live bug.
- **`WebServer.swift`** — `stateCallback`/`activePort`/`listener` are unsynchronized under `@unchecked Sendable` (benign word writes); a dropped SSE conn lingers in `sseConns` up to 25 s until the keepalive prunes it (self-heals). Neither observed to misbehave.
- **`VLCBridge.swift`** (~line 55-60 at time of writing) — a CoreAudio device-change callback already in flight during `stopDeviceChangeMonitoring()` teardown could read a freed context. Very edge; related listener-lifecycle issue (double-registration) is fixed — see `issues_resolved.md` — this is a narrower residual case that wasn't.
- **`WebServer.swift` — LAN-trust hardening notes (2026-08-11 security pass)** — three related accepts, all requiring a hostile or misbehaving device *already on the trusted network*: (1) the subnet check matches any local interface's subnet, **including VPN tunnels** (utun) — a connected VPN with a wide netmask admits all VPN-side peers as "local"; inherent to the subnet-trust design, worth knowing when running a VPN on the host Mac. (2) **No cap on concurrent SSE connections** — `sseConns` grows per open `/api/events` connection with no limit; dead ones prune via the 25 s keepalive but a client holding thousands open exhausts file descriptors (degradation, not crash). (3) **`handleEdit`/`handleRecord` accept unbounded `title` strings** — bounded only by the 128 KB request cap; a ~100 KB title bloats config/page builds, and embedded newlines pass into `glog` lines (log-line injection). All three accepted as marginal on a home LAN; revisit if the trust model ever widens.
- **`src/HDHomeRunKit/`** — ~1,000 lines of dead player code (`HDHomeRunPlayerView`, `HDHomeRunPlayerViewModel`, `DVRBufferManager`, etc.) sitting in the working directory from an earlier player exploration. Gitignored (`/src` in `.gitignore`) and not referenced by `Package.swift`, so it can't affect the build or the repo — but it *does* show up in filesystem-wide searches (`find`/`grep` over the checkout without a `.build`-style exclusion), where its similarly-named types can mislead a code search or an automated audit into reading it as live code. Local-only clutter, zero runtime risk; accept unless/until it confuses something, in which case just delete the directory (it exists nowhere else — confirm nothing in it is worth salvaging first). Found during 2026-08-11 lean code audit.
- **Strict-concurrency build (`swift build -Xswiftc -strict-concurrency=complete`) — 2026-08-11 follow-up audit** — remarkably little noise (8 warnings, 5 distinct causes), none a real live race:
  - **`ConfigManager.swift:77` (`iso8601Formatter`), `Models.swift:69/71` (`logDateFormatter`/`logFile`), `DiscordNotifier.swift:9/14` (`discordLogDateFormatter`/`discordLogFile`)** — "not concurrency-safe, may have shared mutable state" on module-level `ISO8601DateFormatter`/`RotatingLogFile` globals. All three are compiler-pedantry, not real races: `ISO8601DateFormatter` is thread-safe per Apple docs (same reasoning as the `ConfigManager` hoist, see `issues_resolved.md`'s guide-detail-adjacent commit `a6d67de`); `logFile`/`discordLogFile` are only ever touched from inside their own serial `logQueue`/`discordLogQueue` `.async` closures (already commented as such at both call sites) — safe by construction, just not statically provable to the Sendable checker without `nonisolated(unsafe)` annotations this audit deliberately isn't adding (audit, not a Swift 6 migration).
  - **`VLCBridge.swift:57`** — `capture of 'ctx' with non-Sendable type 'AudioDeviceChangeContext'` + `sending 'ctx' risks causing data races`, both on the CoreAudio `audioDeviceChangeProc` C callback dispatching `ctx.callback()` onto `DispatchQueue.main.async`. This is the same code region as the CoreAudio teardown-race entry two bullets up — the compiler is (correctly) flagging that `AudioDeviceChangeContext` isn't `Sendable`; in practice it's immutable after `init` (`let callback`), so the cross-thread hand-off is safe, but the pointer stays freeable by `stopDeviceChangeMonitoring()` while a hop is in flight (the actual, narrower accepted risk). Confirms rather than adds to the existing accepted item.
  - **`AddShowView.swift:470`** — `webView(_:decidePolicyFor:decisionHandler:)` "nearly matches optional requirement" of `WKNavigationDelegate`. Not a race — WebKit's headers now declare the protocol's `decisionHandler` as `@escaping @MainActor @Sendable (WKNavigationActionPolicy) -> Void`, but this override's closure type omits `@MainActor @Sendable`, so Swift's strict-concurrency-aware overload matching no longer considers it an exact witness (only surfaces under this flag; a normal build has zero warning here). Since `WKNavigationDelegate` is an `@objc` protocol, conformance is resolved via Objective-C selector dispatch, not the Swift witness table, so this method almost certainly still fires normally — a widely-seen, largely cosmetic warning as WebKit's SDK headers pick up Sendable annotations ahead of app code. Not verified at runtime as part of this audit (out of scope); low priority, trivial fix (add `@MainActor @Sendable` to the closure param) if ever revisited.
  - **Re-audited and cleared 2026-08-17 (full site-by-site pass, not a spot-check).** The "111 warning sites" figure quoted below by the 2026-08-15 pre-release pass was a measurement artifact, not real growth: `grep -c warning:` on a plain build log counts each diagnostic once per frontend job that re-typechecks the file as same-module context (this project's debug build is per-file incremental, not whole-module — a file with many in-module dependents gets its diagnostics re-emitted once per dependent's compile job). Deduplicating on `file:line:col:message` (clean build via `swift build --build-path <tmp> -Xswiftc -strict-concurrency=complete`, all 28 source files freshly compiled) drops the true count to **28 distinct sites** — `WebServer.swift` (8), `AppState.swift` (7), `HDHRManager.swift` (5), `VLCBridge.swift`/`Models.swift`/`DiscordNotifier.swift` (2 each), `ConfigManager.swift`/`AddShowView.swift` (1 each). Every one of the 28 was individually read in context (not pattern-matched) and traces to one of these already-accepted shapes, none a real live race:
    - **`HDHRManager` sent across a concurrency boundary** — ~10 sites (`AppState.swift:628/651/756/2272`, `HDHRManager.swift:38/39/40/75/98`) as `self`/`self.hdhrManager` inside `async let`, `withTaskGroup { group.addTask { ... } }`, or a direct `await hdhrManager.foo(...)` call from `@MainActor` code. Root cause confirmed by reading `HDHRManager`'s full property list (`HDHRManager.swift:4-13`): `final class HDHRManager` has exactly three stored properties, all `let` — `session`/`dataSession` (`URLSession`, thread-safe per Apple docs) and `cloudDiscoveryURL` (`URL`, a value type). No mutable state exists to race on; the compiler can't prove this because the class itself isn't declared `Sendable`. (Not fixed here — an audit, not a migration — but `final class HDHRManager: Sendable {}` would be a correct, one-line fix that silences this entire cluster if ever revisited.)
    - **`AppState.swift:2829`** (`sending 'embed'`) and **`:3576`** (`NotificationActionDelegate` `self` capture crossing into `MainActor.run`) — a locally-built `DiscordEmbed` value type sent to a nonisolated function, and a delegate forwarder (`weak var appState` only) crossing an actor hop. Same shape: non-`Sendable`-declared type, no actual shared mutable state.
    - **`WebServer.swift:212/223`** (`onState` callback captured across `DispatchQueue.main.async`), **`:594`** (`idle: DispatchWorkItem` captured in a receive-completion closure), **`:483/1958`** (`initialBytes`/`keepAlive` — local `var`s read-only inside a single connection's completion closure, never touched after that closure fires) — all single-owner captures scoped to one request/connection's lifetime, not shared fields. **`:1`** is a compiler *suggestion* (`add '@preconcurrency' to suppress Sendable-related warnings from module 'Dispatch'`), not a warning about this codebase's own code at all.
    - The three previously-catalogued causes (`ConfigManager`/`Models`/`DiscordNotifier` formatter/log-file globals; `VLCBridge.swift:57`'s `ctx` capture; `AddShowView.swift:494`'s `WKNavigationDelegate` near-miss) are unchanged from the 2026-08-11 audit above.
    - **Conclusion: fully cleared, not just re-confirmed-by-pattern.** No code changes made (nothing here rises above "accepted, by-design" per this project's own bar). Future growth in this count should be re-measured with the dedup method above, not raw `grep -c`, or it will again look alarming without being so.
- **Long-session resource audit — 2026-08-11 follow-up** — traced every creation/cleanup path for the resources most likely to leak across a months-long session. Two unbounded (but low-severity) growth points found; everything else checked out:
  - **`ChannelIconCache.failedURLs`** (`Set<String>`, actor-private) — every icon URL that ever fails to download is inserted and never removed/pruned, unlike the actor's `mem` cache (capped at 600, full-flush eviction) and its disk cache (capped at 150 MB, oldest-by-mtime eviction via `pruneDiskCacheIfNeeded`). Bounded in practice by the total number of distinct icon URLs the guide ever presents across the session (order of hundreds to low thousands even over months, per the disk-cache comment's own real-world estimate), so not a practical concern, but structurally the one uncapped collection in that actor.
  - **`AppState.channelIconImages`** (`[ImageURL: NSImage]`, `@Published`) — populated via `.merging(fetched) { _, new in new }` in `prefetchChannelIcons`, which only ever adds keys, never removes one for a URL that's stopped appearing in the guide (e.g. a station's CDN logo URL rotating). Its sibling `channelImageURLs` (`"device:channel" → URL`) is fully rebuilt from scratch on every `rebuildChannelImageURLs()` call and has no such issue. In practice logo URLs churn rarely, so growth is slow and bounded by the same "total distinct URLs ever seen" ceiling as the item above — holds decoded `NSImage` bitmaps though, so the per-entry cost is higher than a string set.
  - **IOKit sleep assertions** (`RecordingManager.assertionIds`) — traced clean. Every creation path (`start`, `reattach`, the VLC "vlc"-keyed watch assertion) either has an explicit release on the corresponding teardown path (`stop`/`skipRecording`/`deleteShow` all route through `teardownRecordingState` → `recordingManager.stop()` → `releaseAssertion`) or is caught by the self-healing `releaseAssertionsIfIdle()` (called after every `refreshTunerOccupancy()`, itself invoked by the idle loop and by every watch/recording state change) — plus IOKit's own `kIOPMAssertionTimeoutActionRelease` duration-based auto-release as a final backstop. Live-verified via `pmset -g assertions` with the app idle (no active recording/watch) — zero stray hdhrVCRplus-owned assertions.
  - **Task-caching dicts** (`loadingLineupTasks`, `fetchStatusTasks`) — both use `defer { removeValue(forKey:) }` immediately after registering the coalescing `Task`, safe on every exit path (the wrapped work is `Task<Void, Never>`, so there's no throwing path to miss). `discordCardTasks` uses a genuinely different pattern — intentionally *not* removed on completion (each new call chains behind and replaces the previous entry, by design, so the next lifecycle event for that show has something to await) — but is explicitly cleared in `deleteShow` per the project's own show_id-keyed-table rule, so it's bounded by live show count, not session length. All three check out; no fix needed.
  - **SSE connection list** (`sseConns`) — already tracked as part of the 2026-08-11 security-pass entry above (dead connections self-heal via the 25 s keepalive prune; no cap on concurrent connections). Nothing new found here.
