#### Slice 1 — Engine & state (AppState, RecordingManager, Models, Config, Guide, HDHR, Discord)


##### [SEV low-med] AppState.swift:4420-4421 — organizeSeriesRecordings prefix match mis-files other series sharing a title prefix
Files are selected with `hasPrefix("\(safeFolderTitle)_") || hasPrefix("\(safeFolderTitle) ")`. The `" "` branch (meant for the legacy "Title SxxExx guests" format) also matches any longer title that starts with the same words, e.g. show "Law & Order" claims "Law & Order SVU_S01E02_5.1_date.ts" (new-format name) or "Star Trek" claims "Star Trek Voyager_..."; they are moved into "Law & Order/Season 01/". Maintenance action is user-triggered but irreversible-ish (recordedEpisodeTags dedup then reads wrong series dir). Fix: for the " " branch require the remainder to start with an episode tag (`S\d+E\d+`) via episodeTag(inFilename:) at the exact position, or only match the " " form when the next token matches `^S\d+`. CONFIRMED by reading.

##### [SEV low-med] GuideStore.swift:101-104 + AppState.swift:1915-1920/1752 — "already loading — skipped" is reported as a load FAILURE
`load()` returns false when `loadingDevices` already contains the device. `loadAll` -> `refreshGuides`/`probeForNewDevices`/`performFetchAllGuides` treat false as a failed fetch: refreshGuides calls handleGuideLoadFailure (recordFailure => 60 s backoff, plus a "Guide Load Failed" user notification + Discord embed once per streak). A second loader is easy to get: scheduleNextAir (AppState.swift:3871, on any series show whose guide is >1 h old) and the periodic `Task { await refreshGuides() }` launched in the same idleLoop tick both call guideStore.load for the same device. The loser gets `false` even though the guide loaded fine. Fix: return a tri-state (loaded / skipped-already-loading / failed) or have load() await the in-flight task (coalesce like fetchAllGuidesTask) instead of returning false. CONFIRMED by reading (scenario plausible, not reproduced).

##### [SEV low] HDHRManager.swift:15/509-514 — fetchLineup (and setFavorite) use URLSession.shared (60 s timeout), contradicting LANFetch's stated intent; stalls hourly guide refresh
LANFetch's doc says lineup polls should use the 10 s LAN session, but `fetchLineup` uses `dataSession` (= `.shared`, 60 s request timeout). `refreshGuides()` does `await fetchAllLineups(for: devices)` over ALL known devices (incl. unavailable ones kept because a show references them, and virtual relays) in a task group and only then calls `guideStore.loadAll`, so a single unreachable tuner delays the whole periodic guide refresh (and rescheduleAllSeries) by up to 60 s each cycle; the idle-loop `lineupConfirmRetry` has the same exposure. Fix: give dataSession a 10 s timeout for lineup/favorite calls (or route fetchLineup through LANFetch) and/or skip `!isAvailable` devices in the refresh pass. CONFIRMED by reading.

##### [SEV low] ConfigManager.swift:11-14 — config (and its .bak fallback) is keyed by ProcessInfo.hostName, which is volatile and can block
`hdhr_VCR-\(ProcessInfo.processInfo.hostName).json` is the only lookup key for both the main file and the `.bak`. `ProcessInfo.hostName` is derived (reverse DNS / DHCP / Bonjour name) and can change between launches (VPN, different SSID/DNS suffix, ".local" vs ".lan", "-2" Bonjour collision suffix); on change load() finds neither file and logs "No config found — fresh install", and the next saveConfig() creates an empty config under the new name (all shows appear lost; old file orphaned). The call also runs synchronously on the main thread in ConfigManager.init and again in `updateVirtualTunerPresence`, and can stall for seconds when DNS is slow. Fix: key on a stable id (e.g. `Host.current().localizedName`/IOPlatformUUID or a fixed filename), and migrate by globbing `hdhr_VCR-*.json` when the expected name is missing. PLAUSIBLE (not reproduced; code path CONFIRMED).

##### [SEV low] DiscordNotifier.swift:41-44/156 — no 429/backoff handling; webhook URL scheme and trailing path not validated
All three senders treat any non-2xx (incl. Discord's 429 rate limit, easily hit when several shows start/stop in one idle tick) as a one-shot failure with no retry or Retry-After wait; a failed CREATE (capturing) leaves `discord_start_msg_id` empty so the card is simply lost. `isDiscordHost` checks the host only, so `http://discord.com/...` (token in clear) is accepted, and `editDiscordEmbed` builds `"\(webhookURL)/messages/\(id)"` by string concat, which breaks for a webhook URL with a query string (?thread_id=) or trailing slash. Fix: require https, build edit URL via URLComponents (append path, keep query), and retry once on 429 after Retry-After. CONFIRMED by reading.

##### [SEV low-med] AppState.swift:1592-1599 — discoverDevices replaces a known device record outright, losing TunerCount/ModelNumber/DeviceAuth when this round was a degraded (UDP-only) hit
`merged[i] = fresh` overwrites the whole HDHRDevice, whereas probeForNewDevices (1636-1652) carefully copies only non-nil fields. A UDP-only reply (HTTP /discover.json briefly failed -> udpDiscoverAndFetch returns the bare UDP device with TunerCount/ModelNumber/FriendlyName nil, possibly DeviceAuth nil) via Settings "Rediscover" or the idle loop's `devices.isEmpty` retry wipes those fields on a device that was fully known. Effects until the next successful probe (~60 s quick-probe at best): `tunersFull`/`hasConflict` return false (they `guard let tunerCount`), so the Tuner Conflict gate is bypassed; `supportsTranscode` flips false so a recording starting in that window is forced to transcode=none (violating the user's saved choice); a lost DeviceAuth makes GuideStore fall back to the device's local /guide.json. Fix: reuse one field-merging helper (non-nil wins) for both discoverDevices and probeForNewDevices. CONFIRMED by reading.

##### [SEV low] Models.swift:174-181 — posixRecordDir treats a volume ROOT as "mounted" when it is not
`posixRecordDir` uses `show_dir` only if `deletingLastPathComponent(show_dir)` exists. For a show_dir that is a mount root (e.g. "/Volumes/Raid6", a very natural pick in the folder chooser) the parent "/Volumes" always exists, so when the NAS/external disk is unmounted startRecording's `createDirectory(withIntermediateDirectories:)` happily creates "/Volumes/Raid6/..." on the startup disk (admin users can write /Volumes) and records there; diskOK reads the boot volume's free space; the later real mount becomes "Raid6 1". The fallback to show_temp_dir never triggers. Fix: check the volume is actually mounted (e.g. `URL.resourceValues(.volumeIsLocalKey)`/compare st_dev of path vs "/Volumes"... or require the first path component under /Volumes to be a mount point via getmntinfo). PLAUSIBLE (logic CONFIRMED, depends on user picking a volume root).

##### [SEV low] AppState.swift:6121-6157 — tuner-occupancy data that gates recording starts is throttled by the UI-only menuIsOpen flag
fetchDeviceStatusUncached only writes `deviceTunerOccupancy` when the active count changed AND (!menuIsOpen || 30 s cooldown elapsed). `tunersFull`/`activeTunerCount` (the Tuner-occupancy invariant's hw half) read that dictionary from startRecording. With the menu open (or `menuIsOpen` stuck true, which tickStatusLight's own comment says can happen after SwiftUI's eager startup build) an externally-started stream is invisible for up to 30 s per change, so a scheduled start can launch curl into an HTTP 805 and burn a fail-count/retry cycle; conversely a stale high count blocks a start. Fix: always keep a non-@Published shadow copy (plain dictionary) for decisions and only gate the @Published mirror used by views. CONFIRMED by reading; impact PLAUSIBLE.

##### [SEV low] AppState.swift:3871-3925 — scheduleNextAir can overwrite a show that started recording while it was suspended on the guide reload
Callers (updateShow's Task, rescheduleAllSeries, Pass 2) only check `!show_recording` BEFORE calling. After `await guideStore.load(...)` the function re-reads `show = shows[idx]` but never re-checks `show_recording`, then `applyMatch` writes show_next/show_end/show_channel/hdhr_record/show_url. If the idle loop started the recording during that network await (window only exists when the device guide is >1 h old), a currently-airing match resets `show_end` to the guide end (dropping Bonus Time padding -> recording cut off early by Pass 1) and a next-airing match moves channel/device/end under a live recording (activeRecordingChannels/tuner bookkeeping then describe the wrong channel). Fix: after the await, `guard !shows[idx].show_recording else { return }` (and also skip the stale-bump branch). CONFIRMED by reading; narrow window.

##### [SEV low] RecordingManager.swift:139-141 — stop() SIGKILLs a stored pid without verifying it is still our curl
isRunning() has the pid-recycle guard (isCurlProcess) but only runs when polled (idle tick, 10 s). stop(showId:)/stopAll()/teardown call `kill(pid, SIGKILL)` on `pids[showId]` directly. If curl exited and its pid was recycled to an unrelated user process before the next poll (long-uptime Mac, manual stop/delete/skip in between), that process is killed. Same for a reattached orphan pid. Fix: reuse `isCurlProcess(pid:)` (or `kill(pid,0)`+proc_pidpath) before SIGKILL. CONFIRMED by reading; probability very low.

##### [SEV low] AppState.swift:1299-1308 — loadConfig silently drops every inactive show, including ones deactivated with a "fix me" reason
`shows = allShows.filter { $0.show_active }` and re-saves. A .dateTime show deactivated by scheduleNextAir's no-air-days branch (show_fail_reason = noAirDaysReason, notification says "edit show to fix") is therefore deleted on the next launch, which also makes updateShow's reactivate-on-edit logic and `reactivatePausedShows`'s `!show_active` branch unreachable across restarts. Fix: only auto-clean `.single` shows that completed (state == .single && !show_active); keep others. CONFIRMED by reading.

##### [SEV nit] RecordingManager.swift:357-372 — respawn appends at an arbitrary byte, shifting the 188-byte packet alignment of everything after
A dropped curl usually leaves a partial trailing TS packet; the `>>` append then makes every later packet start at (size % 188) offset. AppState.byteOffset aligns scrub offsets to 188 from byte 0, so seeks past the splice land mid-packet (VLC resyncs on 0x47, so cosmetic). Fix: before respawn, truncate the cache file to `size - size % 188` (reader already past that point is unaffected only if it has not consumed the tail; safest is to pad the tail to a full packet with 0xFF null-packet bytes). PLAUSIBLE.

##### [SEV nit] AppState.swift:1592,1631,1821,2098 — four `Dictionary(uniqueKeysWithValues:)` over device lists trap on a duplicate DeviceID
`HDHRManager.discoverDevices` returns the cloud list verbatim in its no-local-device fallback (HDHRManager.swift:53-57) with no DeviceID dedup (local paths dedup via mergeDevice/knownHostsDiscover). A duplicate there would reach `devices` via probeForNewDevices' append and then crash on EVERY idle tick (rebuildMenuEntries/updateShowURLsFromLineups) = crash loop at launch. Fix: use `uniquingKeysWith: { a, _ in a }` at those four sites (as ManagedGuideMatcher already does) and run the cloud result through mergeDevice. CONFIRMED (trap semantics), trigger unlikely.

##### [SEV nit] AppState.swift:1966-1973 / 1980-1995 — prefetchChannelIcons assigns @Published channelIconImages (and statusMessage) unconditionally, even when nothing changed or the menu is open
Warm path always does `channelIconImages = channelIconImages.merging(fetched)` (fires objectWillChange every guide refresh/ensureGuideLoaded even with an identical dictionary) and is not gated on `menuIsOpen`, unlike the other periodic writers (Menu rebuild churn invariant). Also AppState holds every decoded NSImage ever fetched with no cap while ChannelIconCache.mem is capped at 600. Fix: only assign when `fetched` adds/changes keys and `!menuIsOpen` (else defer to menu close). CONFIRMED.

##### [low] WebServer.swift:1517-1519,2254 — `?duration=` unbounded Int → `DispatchTime + Double` may trap / absurd timers
`/auto/v<ch>?duration=9223372036854775807` is parsed with only `max(0, $0)`. Even if it doesn't trap, the raw path just never expires. LAN-reachable, no auth, needs an active FEED recording + transcode request. Fix: clamp duration to e.g. 24h at parse time (like handleEdit's length cap). PLAUSIBLE.

##### [low] WebServer.swift:2086-2104 — no cap on concurrent connections / SSE subscribers; per-read idle timer lets slowloris hold sockets

- **Strict-concurrency build (`swift build -Xswiftc -strict-concurrency=complete`) — 2026-08-11 follow-up audit** — remarkably little noise (8 warnings, 5 distinct causes), none a real live race:
  - **`ConfigManager.swift:77` (`iso8601Formatter`), `Models.swift:69/71` (`logDateFormatter`/`logFile`), `DiscordNotifier.swift:9/14` (`discordLogDateFormatter`/`discordLogFile`)** — "not concurrency-safe, may have shared mutable state" on module-level `ISO8601DateFormatter`/`RotatingLogFile` globals. All three are compiler-pedantry, not real races: `ISO8601DateFormatter` is thread-safe per Apple docs (same reasoning as the `ConfigManager` hoist, see `issues_resolved.md`'s guide-detail-adjacent commit `a6d67de`); `logFile`/`discordLogFile` are only ever touched from inside their own serial `logQueue`/`discordLogQueue` `.async` closures (already commented as such at both call sites) — safe by construction, just not statically provable to the Sendable checker without `nonisolated(unsafe)` annotations this audit deliberately isn't adding (audit, not a Swift 6 migration).
  - **`VLCBridge.swift:57`** — `capture of 'ctx' with non-Sendable type 'AudioDeviceChangeContext'` + `sending 'ctx' risks causing data races`, both on the CoreAudio `audioDeviceChangeProc` C callback dispatching `ctx.callback()` onto `DispatchQueue.main.async`. This is the same code region as the CoreAudio teardown-race entry two bullets up — the compiler is (correctly) flagging that `AudioDeviceChangeContext` isn't `Sendable`; in practice it's immutable after `init` (`let callback`), so the cross-thread hand-off is safe, but the pointer stays freeable by `stopDeviceChangeMonitoring()` while a hop is in flight (the actual, narrower accepted risk). Confirms rather than adds to the existing accepted item.
  - **`AddShowView.swift:470`** — `webView(_:decidePolicyFor:decisionHandler:)` "nearly matches optional requirement" of `WKNavigationDelegate`. Not a race — WebKit's headers now declare the protocol's `decisionHandler` as `@escaping @MainActor @Sendable (WKNavigationActionPolicy) -> Void`, but this override's closure type omits `@MainActor @Sendable`, so Swift's strict-concurrency-aware overload matching no longer considers it an exact witness (only surfaces under this flag; a normal build has zero warning here). Since `WKNavigationDelegate` is an `@objc` protocol, conformance is resolved via Objective-C selector dispatch, not the Swift witness table, so this method almost certainly still fires normally — a widely-seen, largely cosmetic warning as WebKit's SDK headers pick up Sendable annotations ahead of app code. Not verified at runtime as part of this audit (out of scope); low priority, trivial fix (add `@MainActor @Sendable` to the closure param) if ever revisited.
