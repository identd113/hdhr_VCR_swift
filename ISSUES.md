##### [SEV med] AppState.swift:3398-3405 — Bonus Time padding is re-applied (and persisted) on every start retry
startRecording does `var endDate = show.show_end ...; endDate += Sports_padding_minutes; shows[index].show_end = endDate` BEFORE recordingManager.start. show_end is only reset by scheduleNextAir (success/skip paths). Any failed attempt (LAUNCH ERROR, mid-recording curl death -> recordShowFailure -> retry after 2-3 ticks, relaunch after app-quit while still in window) re-enters startRecording with the already-extended show_end and adds another +N min. With Fail_count_setting=3 a flaky sports recording can end up +60/+90 min past guide end (recording/tuner held, idle-loop natural-stop delayed, wrong "Ends" in Discord). Fix: compute padded end from a non-mutated base (e.g. only add padding if not already applied -> track `bonusAppliedForEpoch` in ShowRuntimeState, or derive from show_next+show_length / guide end each time) and don't write the padded value back until start succeeds. CONFIRMED by reading (no reset of show_end between attempts).

##### [SEV low-med] AppState.swift:4420-4421 — organizeSeriesRecordings prefix match mis-files other series sharing a title prefix
Files are selected with `hasPrefix("\(safeFolderTitle)_") || hasPrefix("\(safeFolderTitle) ")`. The `" "` branch (meant for the legacy "Title SxxExx guests" format) also matches any longer title that starts with the same words, e.g. show "Law & Order" claims "Law & Order SVU_S01E02_5.1_date.ts" (new-format name) or "Star Trek" claims "Star Trek Voyager_..."; they are moved into "Law & Order/Season 01/". ##### [SEV med] AppState.swift:5265-5267 (+Models.swift:765, RecordingManager.swift:339/427) — FEED cache path built from unvalidated remote DeviceID => arbitrary-path curl write/delete
`sessionId = "\(device.DeviceID)-\(UUID)"` and `cachePath = "~/Library/Caches/hdhrVCRplus/feed-cache/\(sessionId).ts"`. HDHRDevice.DeviceID is decoded straight from the JSON of whatever LAN host answered discovery (`try c.decode(String.self, forKey: .DeviceID)`, no charset check; UDP path formats hex but then replaces the device with fetchDeviceInfo's JSON). A hostile LAN host advertising `HdhrVCRplusVirtualRelay:true` with DeviceID like "../../../../tmp/x" and a lineup entry makes "Recording on Another Mac" -> startFeedCacheSession spawn `curl -o <traversed>.ts <remote body>` (arbitrary *.ts file write, attacker content) and later `removeItem(cachePath)` (arbitrary *.ts delete) on stop/fail. Also lineup `URL` is passed to curl unvalidated (any scheme incl. file://). Needs a user click, LAN-only, hence med. Fix: build sessionId from the UUID only (or sanitise DeviceID to [A-Za-z0-9_-]{1,32} at decode); require http(s) scheme + host==device.LocalIP for remoteURL. CONFIRMED by reading.

##### [SEV med] ChannelSignalStore.swift:44 vs :113/:128 — history is written with .secondsSince1970 but read with the default Date decoder
`flush()`/`scheduleSave()` set `enc.dateEncodingStrategy = .secondsSince1970`; `load()` uses a bare `JSONDecoder()` (deferredToDate = seconds since 2001). Every persisted sample comes back with `ts` ~31 years (978,307,200 s) in the FUTURE (2057). Consequences after every relaunch: `needsSample` computes a negative age => `age > 86_400/259_200/604_800` is false => poor/fair/good channels are never re-sampled by the adaptive scan (only a forced scan or channels with no history), and `stats().lastSampled` shows 2057 in the signal popover. In-session samples are fine, so it only shows up across restarts. Fix: set `dec.dateDecodingStrategy = .secondsSince1970` in load() (and consider a migration: treat values > ~2.5e9-as-2001-offset... simplest is to detect ts > now+1y and subtract 978307200). CONFIRMED by reading both ends.

##### [SEV low-med] AppState.swift:6275-6362 — signal scan opens real tuners with no occupancy check and records snq=0 when the tuner is busy
startSignalScan never consults tunersFull/recordingShows/deviceTunerOccupancy before opening a stream per channel (`URLSession.shared.data(from: entry.URL)`). If every tuner on the device is in use (recording, or another client) the stream request is refused, no VctNumber ever matches, and the `!gotSample` branch records `snq: 0` for that channel, poisoning the (device-agnostic, GuideName-keyed) history with red/poor readings; it also steals a tuner for ~1.5 s per channel which can collide with a recording start (TUNER FULL retry). ##### [SEV low] ConfigManager.swift:11-14 — config (and its .bak fallback) is keyed by ProcessInfo.hostName, which is volatile and can block
`hdhr_VCR-\(ProcessInfo.processInfo.hostName).json` is the only lookup key for both the main file and the `.bak`. `ProcessInfo.hostName` is derived (reverse DNS / DHCP / Bonjour name) and can change between launches (VPN, different SSID/DNS suffix, ".local" vs ".lan", "-2" Bonjour collision suffix); on change load() finds neither file and logs "No config found — fresh install", and the next saveConfig() creates an empty config under the new name (all shows appear lost; old file orphaned). PLAUSIBLE (not reproduced; code path CONFIRMED).

##### [SEV low] RecordingManager.swift:139-141 — stop() SIGKILLs a stored pid without verifying it is still our curl

##### [SEV nit] RecordingManager.swift:357-372 — respawn appends at an arbitrary byte, shifting the 188-byte packet alignment of everything after
A dropped curl usually leaves a partial trailing TS packet; the `>>` append then makes every later packet start at (size % 188) offset. AppState.byteOffset aligns scrub offsets to 188 from byte 0, so seeks past the splice land mid-packet (VLC resyncs on 0x47, so cosmetic). Fix: before respawn, truncate the cache file to `size - size % 188` (reader already past that point is unaffected only if it has not consumed the tail; safest is to pad the tail to a full packet with 0xFF null-packet bytes). ##### [med] WebServer.swift:1699-1707,1924 — legacy throwing-less FileHandle API (seek/readData/closeFile) raises uncatchable NSException on I/O error
streamGrowingFile/pumpGrowingFile use `handle.seek(toFileOffset:)` and `handle.readData(ofLength:)`. These raise Objective-C exceptions (NSFileHandleOperationException) on EIO/ENXIO/unmounted volume — Swift can't catch them, so the whole app aborts. Scenario: recordings are on an external/network volume (the file comments already call out "slow/contended external or network-mounted volume") that disconnects while a Watch Now / FEED viewer is mid-stream. Fix: use `try handle.seek(toOffset:)` / `try handle.read(upToCount:)` (macOS 10.15.4+, app targets 15) and end the stream on throw. PLAUSIBLE (API behaviour documented; not reproduced).

##### [low] WebServer.swift:1517-1519,2254 — `?duration=` unbounded Int → `DispatchTime + Double` may trap / absurd timers
`/auto/v<ch>?duration=9223372036854775807` is parsed with only `max(0, $0)`. Even if it doesn't trap, the raw path just never expires. LAN-reachable, no auth, needs an active FEED recording + transcode request. ##### [low] WebServer.swift:2086-2104 — no cap on concurrent connections / SSE subscribers; per-read idle timer lets slowloris hold sockets
Idle-close is re-armed on every received chunk (30s), so a client trickling 1 byte/29s keeps a connection for up to 128KB*29s; nothing limits total `liveConns` or `sseConns` (each SSE client gets every multi-hundred-KB guide-change event). LAN-only but the app is otherwise explicit that every route is unauthenticated. Fix: set `NWListener.newConnectionLimit`, add an absolute header-complete deadline (e.g. 10s from accept), cap SSE subscribers. CONFIRMED (code), impact LAN-only.

##### [low] WebServer.swift:504-516 — SSE fan-out has no backpressure; a stalled-but-not-closed client accumulates every event in NWConnection's send queue
broadcastEvent fires `conn.send` for each SSE conn with no in-flight tracking. Fix: track pending-send count per conn (increment before send, decrement in completion) and drop/cancel a subscriber above a threshold. PLAUSIBLE.
